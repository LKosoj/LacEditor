# Правила разработки LacEditor

## Общение и границы задачи

- Общаться с пользователем на русском языке. Объяснять просто; специальные термины сопровождать кратким пояснением.
- Перед изменениями изучить текущий код и состояние `git status`. Сохранять чужие и незакоммиченные изменения.
- Для задачи из нескольких шагов сначала изложить краткий план и способ проверки результата. Существенные неоднозначности уточнять до реализации.
- Если задача расширилась или затронула новую область, заново полностью перечитать `AGENTS.md`, затем прочитать файлы новых областей из `docs/agents/`.
- Всегда выбирать минимальное решение. Без отдельного разрешения не добавлять режимы, инфраструктуру, защитные механизмы, зависимости, рефакторинг и соседние улучшения вне согласованного плана.
- Если после двух самостоятельных проходов не найдено решение проблемы, обязательно искать решение во внешних источниках: сначала через Xcode DocumentationSearch/официальную документацию Apple, затем через интернет-поиск; найденные рекомендации проверять на проекте и фиксировать результат в статусе задачи.
- UI-тесты macOS переносить в target `LacEditorUITests` только если unit-тест не может корректно воспроизвести реальную доставку пользовательского ввода (например, синтетические AppKit `keyDown`/IME/first responder). Обычные существующие UI-проверки не переносить без отдельной причины; `LacEditorTests` использовать для unit/integration-тестов и стабильных AppKit-проверок.
- Менять только необходимые участки, соблюдать существующий стиль. Не переформатировать соседний код и не удалять ранее существовавший неиспользуемый код.
- При изменении поведения кода в рамках той же задачи актуализировать соответствующие правила и описания в `AGENTS.md` и `docs/agents/`, чтобы они отражали фактическую реализацию.
- Использовать доступные скиллы, если они помогут решить конкретную задачу
- Не создавать коммиты, не публиковать и не выпускать приложение без явного запроса пользователя.

## Завершение задач
- Для запросов на реализацию не ограничивайся анализом или планом.
- Доводи изменения до сборки и релевантных проверок.
- Если проверка не прошла, исправляй причину в рамках задачи.
- Перед финальным ответом сопоставляй результат со всеми требованиями.
- В финале указывай: что изменено, что проверено, что осталось.
- При реальном блокере сообщай о нём; не заявляй о полном завершении.

## Устройство проекта

- Приложение для macOS 26+ на SwiftUI и AppKit; редактор использует TextKit, предпросмотр Markdown — WebKit и cmark-gfm, разбор кода — Tree-sitter.
- `LacEditor/App` — состояние приложения, окна, команды и настройки; `Views` — интерфейс; `Editor` — редактирование; `Models` — модели; `Services` — операции с файлами и текстом; `Preview` — предпросмотр.
- `LacEditorTests/` содержит тесты XCTest; при поиске и запуске тестов использовать этот каталог напрямую. `Verification` — дополнительные проверки, `Scripts` — команды сборки и приёмки.
- Поддерживать сборку через Swift Package Manager (`Package.swift`) и Xcode (`LacEditor.xcodeproj`). При добавлении исходников или ресурсов обновлять необходимые списки сборки, включая прямые вызовы `swiftc` в скриптах проверок.
- Для production-сборки без запуска тестов использовать `LACEDITOR_SKIP_TESTS=1 zsh Scripts/build-production.sh`.
- На сервере разработки (Linux) есть Swift 6.0.3: `/home/claude-bot/tools/swift-6.0.3-RELEASE-ubuntu24.04/usr/bin/swift` и `/home/claude-bot/tools/swift-6.0.3-RELEASE-ubuntu24.04/usr/bin/swiftc` (перед использованием: `export PATH=/home/claude-bot/tools/swift-6.0.3-RELEASE-ubuntu24.04/usr/bin:$PATH`). AppKit, SwiftUI и NaturalLanguage там нет, поэтому полная сборка невозможна; изменённые файлы проверять минимум через `swiftc -frontend -parse <файл>`, а файлы с `#if compiler(>=6.2)` — через `swiftc -typecheck -swift-version 5 <файл>` (ошибка `no such module 'AppKit'` ожидаема). Стенды с заглушками: `/home/claude-bot/tools/lac-check` (разбор Markdown, инструкция `check-howto.md`) и `/home/claude-bot/tools/lac-writer-check` (сборка и тесты кода писательского режима; запуск — `/home/claude-bot/tools/lac-writer-check/run-tests.sh`, новые файлы дописывать в его `lib-files.txt` и `test-files.txt`). Как запускать стенды и читать их результат — [`docs/agents/linux-stands.md`](docs/agents/linux-stands.md).
- Production-скрипт не очищает `.build`, SwiftPM или DerivedData перед сборкой и повторно использует кэш; для такой сборки применять ту же команду без запуска `clean`.
- После подготовки версии release notes сохраняются в `docs/releases/<версия>.md`, а опубликованные архив и `.sha256` должны соответствовать этой версии.
- Не менять содержимое пользовательских документов, правила сохранения, восстановления и совместимость существующих настроек ради несвязанной задачи.
- Текущая основа редактора — TextKit 1. Переход на TextKit 2, `NSDocument` или другую модель окон не считать обычной частью исправления ошибки. `docs/ROADMAP.md` и `NEXT_OPTIMIZATIONS.md` содержат также будущие работы: сверять их статус с кодом, не описывать планы как реализованные возможности.

## Написание тестов

- Перед новым тестом найти похожий проходящий тест и взять его стенд: fixture, создание окна, порядок вызовов и освобождение. Не изобретать свой стенд, если в файле уже есть helper (`makeEditor`, `show` и т. п.).
- Проверять реальный путь кода (Coordinator, контроллер, сервис), а не его копию в тесте. Не добавлять в production-код ветки и флаги только ради теста; если нужен доступ, использовать `@testable import` и существующие internal-методы.
- Каждый тест независим: не опираться на порядок запуска, общее состояние и уже открытые окна. Временные файлы — в уникальном каталоге с удалением; изменённые `UserDefaults`, окна и наблюдатели возвращать в `defer` (`window.close()`, `coordinator.updateActivity(false)`, `NSApp.abortModal()` для модальных окон). Тесты идут параллельно, подробности — в `docs/agents/testing.md`.
- Undo, first responder и key window есть только у текстового вида внутри окна: такие тесты создают `NSWindow` (`isReleasedWhenClosed = false`) по образцу соседних тестов.
- Асинхронный результат ждать опросом условия с пределом (например, 30 раз по 100 мс), затем проверять его отдельным assert. Фиксированная пауза не доказывает результат.
- Данные — минимальные, но настоящие: рабочий PNG вместо обрезанного base64, если байты декодируются. Где важны диапазоны, добавлять не-ASCII (кириллица, CJK, эмодзи) и `\r\n`; позиции считать в UTF-16 (`NSString`, `NSRange`).
- Проверять наблюдаемое поведение: текст, сохранённый файл, выделение, видимый результат (глифы, `markdownImageLocation`), а не порядок внутренних вызовов. Повторяющиеся проверки в цикле или helper сопровождать `message`, чтобы было видно, какой шаг упал.
- Ожидания не ослаблять и не подгонять под текущий результат. Если тест противоречит правилам `docs/agents/`, сначала выяснить, что верно, и при необходимости спросить пользователя; исправлять либо код, либо тест вместе с правилом.
- Имя теста описывает сценарий и ожидание (`testDataImageIsAnchorInSourceModeAndImageInFormattedMode`); над неочевидным тестом — короткий комментарий на русском, зачем он нужен.
- Новый файл теста класть в `LacEditorTests/` (Xcode и SwiftPM берут файлы из папки сами, fixture — в `LacEditorTests/Fixtures`); тест кода писательского режима дописывать в `test-files.txt` стенда `lac-writer-check`.
- На Linux новый тест проверять минимум `swiftc -frontend -parse` и, если возможно, на стенде с заглушками; в `docs/TEST_STATUS.md` отмечать, что на Mac он ещё не запускался.

## Делегирование

- Если нужно целиком или почти целиком изучить файл длиннее 800 строк, передать его агенту `large-file-explorer`, указав путь, задачу и конкретный вопрос. Получить краткую выжимку и нужные диапазоны строк. Для небольшого участка использовать `rg` и точечное чтение.
- Повторяющийся код по существующему образцу передавать агенту `code-generator` только после самостоятельного выбора решения: указать пример, разрешённые файлы и критерии готовности.
- При делегировании явно распределять файлы, предупреждать о работе других участников и запрещать соседние улучшения. Не редактировать файл одновременно с агентом, который его изменяет.
- После работы агента проверять diff и нужные участки самостоятельно. Если задача требует независимого ревью, поручать его другому агенту.
- Сабагенты по задачам тестирования только анализируют причины и исправляют
  код в явно выделенных файлах. Запуск targeted-тестов, полного прогона и
  проверку предупреждений выполняет только основной агент.
- Перед исправлением каждого падающего теста искать похожие проходящие тесты
  и сравнивать их fixture, оконный стенд, ожидания и lifecycle; рабочий
  проходящий тест использовать как образец исправления.
- Не запускать сборку или тесты «просто для проверки»: каждый запуск должен
  следовать за подтверждённым изменением кода/fixture либо быть отдельным
  диагностическим запуском с явно записанной причиной. Если тест раньше
  проходил и теперь зависает, сначала анализировать регрессию и логи, а не
  повторять тот же запуск без изменения.

### Полный прогон тестов

- Запущенный через Xcode `RunAllTests` нельзя прерывать по таймауту или заменять
  повторным запуском. Нужно дождаться его штатного завершения и сохранить
  итоговый отчёт; длительность полного прогона сама по себе не считается
  зависанием.
- Пакетный запуск разрешён только после завершения полного прогона либо для
  отдельного диагностического запуска по согласованной причине.

## Последовательные проходы через CLI Claude и Grok

Для независимого чтения репозитория сначала запускать Claude, дожидаться его завершения, затем запускать Grok. Оба прохода должны быть только исследовательскими: в запросе явно указывать «не изменяй файлы, не коммить» и использовать режим без вопросов о разрешениях.

Шаблон для Claude из корня проекта:

```sh
runuser -u claude-bot -- /home/claude-bot/.local/bin/claude -p "$(cat /tmp/laceditor-review-prompt.txt)" \
  --permission-mode dontAsk \
  --allowedTools 'Bash(rg *)' 'Bash(sed *)' 'Bash(cat *)' 'Bash(wc *)' 'Bash(rtk *)' \
  --no-session-persistence
```

Шаблон для Grok из корня проекта:

```sh
grok --single "$(cat /tmp/laceditor-review-prompt.txt)" \
  --cwd /srv/git_projects/LacEditor \
  --permission-mode auto \
  --always-approve \
  --no-subagents \
  --output-format plain
```

Вывод сохранять отдельно, например через `tee /tmp/laceditor-claude-review.txt` и `tee /tmp/laceditor-grok-review.txt`. Не запускать оба CLI параллельно: второй проход начинается только после получения полного вывода первого.

Не прерывать запущенный проход Claude или Grok до его штатного завершения: исследование крупных файлов может занимать несколько минут. Ожидать полный вывод и только после этого переходить к следующему проходу или к анализу результата.
