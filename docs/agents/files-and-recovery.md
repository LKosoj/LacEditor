# Файлы, сохранение и восстановление

Читать при изменении чтения и записи файлов, кодировок, статуса сохранения, сессии, аварийного восстановления и изоляции данных сборок.

- Операции чтения и записи проводить через существующие пути `FileService` и `AppState`. Для невалидного UTF-8 сохранять выбор пользователем кодировки; при записи использовать выбранную кодировку и запрещать преобразование с потерей символов. Существующая запись выполняется атомарно — через безопасную замену файла.
- Перед перезаписью исходного файла сохранять проверку внешних изменений и выбор пользователя: отмена, перезагрузка, другой файл или явное перезаписывание. `FileRevisionSnapshot` сравнивает идентичность, дату и размер; не описывать его как полную проверку содержимого по контрольной сумме.
- Статус сохранения: `DocumentRecoveryStore.persist` возвращает на главный поток `DocumentRecoveryPersistResult` (`written`/`failed`/`noSession`); тип объявлен в `EditorDocument.swift`, потому что этот файл входит в прямые списки `swiftc` без хранилища. `EditorDocument.recoveryCopy` временный, применяется только при совпадении токена, документа, `textRevision`, отсутствии несинхронизированных правок и `isDirty`; инвалидируется правкой. Подтверждение копии не означает сохранения файла и не влияет на `isDirty`. `lastSavedAt` — временная отметка успешной записи. Метка «未保存» одинакова с копией и без неё (против мерцания), различие — значок и подсказка; ошибка записи копии показывается отдельно.
- `WorkspaceSessionStore` хранит обычную сессию, `DocumentRecoveryStore` — восстановление после сбоя. Не объединять их жизненные циклы и не превращать сохранение сессии в автоматическую запись пользовательских файлов.
- По умолчанию выход сохраняет рабочее пространство; альтернативный режим спрашивает о несохранённых документах. В режиме сохранения сессии ошибка её записи отменяет выход. При успешном обычном выходе аварийные данные завершаются соответствующим существующим путём.
- Сохранять совместимость формата сессии: одна запись окна представляет группу системных вкладок в порядке AppKit. Восстанавливаются текст, путь, идентификатор, язык документа, кодировка, несохранённость, выделение, прокрутка, предпросмотр, выбранная вкладка, боковая панель и геометрия окна. `allowsRemoteImages` в сессию не пишется и после восстановления выключен.
- Хранилища используют каталоги снимков и маркеры текущей сессии. Не менять порядок записи, переключения маркера, потребления и очистки без проверки сбоев и совместимости. При объединении восстановлений аварийный снимок того же идентификатора имеет приоритет.
- Изоляцию данных определяет `AppEnvironment`: официальная, development, experiment и acceptance сборки используют соответствующие пространства Application Support. Одной смены идентификатора приложения недостаточно для изоляции файлов; не прописывать общий путь вручную. Настройки проверять также в соответствующем `UserDefaults`.
- Первое открытие использует временный документ: до успешного чтения его нельзя сохранять поверх исходного файла, включая результат ошибочного чтения. Отмена удаляет временный документ и освобождает URL; поздний результат проверяет идентичность действующей операции. Отмена повторного чтения сохраняет прежний документ.
- Перед захватом рабочего пространства для выхода ожидать чтения и сохранения. После фоновой записи сравнивать снимок с актуальным состоянием; при новых правках или чтении повторять ожидание и запись. Очистка аварийных данных и подтверждение этого выхода выполняются без промежутка для нового события главного потока.
- `FileService.prepareRead` связывает содержимое с отметкой, проверенной до и после чтения и декодирования. Байты для отложенного выбора кодировки должны оставаться неизменными; не захватывать новую исходную отметку независимо от уже прочитанного текста.
- `WorkspaceSessionStore.load` не уничтожает данные: `consume` допускается только после успешной передачи несохранённых документов в активное аварийное хранилище. Ошибка чтения или запуска восстановления прекращает запуск с сообщением, без обычного сохранения пустой сессии и без очистки прежних данных.
- Восстановление сначала читает метаданные и копирует файлы снимков без одновременного декодирования всех текстов. Все необходимые источники надёжно передаются до потребления рабочего пространства; затем тексты читаются по одному, выбранные вкладки имеют приоритет.
- Ожидающая восстановление вкладка использует существующее состояние opening и исходный EditorDocument. Отмена её загрузки проходит обычное подтверждение закрытия несохранённого текста; единственная аварийная копия удаляется только после явного отказа от сохранения. Она участвует в проверке идентичности файла, закрытии и ожидании чтения; её пустой текст нельзя редактировать, сохранять или отправлять в аварийный снимок.
- Необязательное isDirty в существующей аварийной JSON-записи сохраняет чистые вкладки при файловой передаче. Старые записи без поля по-прежнему считаются несохранёнными. Формат рабочего пространства version 1 сохраняется; повторный аварийный запуск имеет прежнее ограничение по группировке окон.
- Файл на диске и сессия хранят настоящие `data:`; круг открытие → сохранение побайтный, в том числе для адресов, похожих на токен. Сохранение, печать и все экспорты сначала зовут `AppState.rejectUnknownMediaTokens`: токен `#lac-media-…` без записи в таблице документа запрещает операцию с сообщением «请撤销最近的修改». Новый путь записи или вывода документа обязан вызывать ту же проверку.
- Сниппеты хранятся в `Snippets.json` (`{"version":1,"snippets":[…]}`) в каталоге `AppEnvironment.dataDirectoryName` внутри Application Support; запись атомарная. Файл не входит в сессию и аварийное восстановление. Повреждённый файл переносится рядом как `Snippets.json.corrupt` (затем `-2`, `-3`, прежние копии не затираются), список пуст, запись разрешена; нечитаемый файл, файл новее известной версии или неудавшийся перенос переводят хранилище в режим только чтения, файл не трогается. Ошибка записи оставляет список в памяти прежним.
- История диктовок хранится в `DictationHistory.json` (`{"version":1,"entries":[…]}`, даты ISO 8601) в том же каталоге и по тем же правилам, что `Snippets.json`: атомарная запись, `.corrupt`/`-2`/`-3` для повреждённого файла, режим только чтения для нечитаемого файла или версии новее известной. В файле не больше 20 записей не старше 14 дней; просроченные удаляются при загрузке и добавлении. Файл не входит в сессию и аварийное восстановление.
- Копия последней замены в папке лежит в `FolderReplaceBackup` внутри `AppEnvironment.dataDirectoryName`, отдельно от `Recovery`, и не входит в сессию и аварийное восстановление.
- Слежение за открытыми файлами: `WindowManager.openFileWatcher` (`OpenFileWatcher`) держит один поток FSEvents по родительским каталогам документов с `url` и baseline (вложенный каталог отдельно не добавляется; заглушки открытия и восстановления пропускаются). События фильтруются по каталогу файла и откладываются на 0,3 с; флаги переполнения, смены корня и монтирования проверяют все документы. Проверка идёт и при активации приложения (сетевые диски без событий). Фоновая проверка снимает `FileRevisionSnapshot` (идентичность, дата, размер, не содержимое) и только записывает результат в `EditorDocument.externalChange` через `noteDiskState`; текст документа она не меняет, автоматического перечитывания нет, настройки отключения нет. Пока `ioState` — `.saving` или `.opening`, проверка повторяется с паузой; `.failed` пропускается без повтора. Результат применяется, только если за время чтения не изменились `url`, baseline и `ioState == .idle`, иначе проверка повторяется (так собственное сохранение не даёт ложной плашки). Нет файла (`ENOENT`, `ENOTDIR`, нет такого файла) даёт `.missing`, любая другая ошибка чтения состояние не меняет.
- Плашка: «Оставить мою версию» запоминает состояние диска (`dismissedExternalState`) и скрывает плашку до следующего изменения; любой `updateFileRevisionSnapshot` (загрузка, сохранение, перечитывание, перенос) гасит плашку и запоминание. Перечитывание по кнопке «重新载入» идёт через `reloadExternalChange` → `reloadFromDisk` → `finishReload`; при несохранённых правках сначала спрашивается подтверждение, при системном вводе (marked text) перечитывание ждёт, а `finishReload` сохраняет локальный текст. «Сравнить» открывает режим `presentVersionHistory(mode: .disk)`. `finishReload` не подменяет одинаковый текст (отмена и выделение остаются), иначе ставит одноразовую отметку `externalReplacementRevision`, и пересчитывает профиль производительности. Ограничение: запись того же размера в ту же секунду без смены файла не видна.
- Переименование открытого файла (`updateLocationAfterRename`) переснимает baseline по новому адресу, если идентичность файла, дата и размер совпали со старыми (путь не сравнивается); иначе прежний baseline остаётся и плашка корректно сообщит об изменении. Ошибка чтения при перечитывании по плашке возвращает документ в `.idle` (`reloadFromDisk(releasesOnReadFailure:)`), чтобы следующая проверка показала «удалён или перемещён»; остальные пути перечитывания оставляют `.failed`. Каталог файла для сопоставления событий `OpenFileWatcher` считается один раз на адрес документа (кэш по `id`), в событиях сравниваются строки.
- `WorkspaceSessionStore` хранит необязательное `writerProject: WriterProjectSession?` (корень и `projectID`); поле читается мягко, старые файлы сессии совместимы. Манифест проекта `.laceditor/project.json` пишется атомарно с проверкой ревизии; новее поддерживаемой версии и повреждённый файл не перезаписываются.
- Каталог `Application Support/<dataDirectoryName>/SearchIndex` хранит только производные индексы поиска «По словам» (`.sqlite`, `-wal`, `-shm`); удаляются вместе, повреждённая база пересоздаётся. В сессию и восстановление индекс не входит.
- Снимки (`DocumentSnapshotStore`) — именованные копии текста одного файла, отдельные от файла и от системных версий (`NSFileVersion`). Каталог снимков: `index.json` (`{"version":1,"snapshots":[{id,name,date,byteCount,sha256,encoding}]}`, дата с точностью до секунды) и `<id>.txt` в UTF-8; запись атомарная, сначала `.txt`, потом индекс (при ошибке индекса `.txt` удаляется). Ключ хранения: файл в проекте рукописи — `<корень>/.laceditor/snapshots/<id узла>/` (переименование файла ничего не ломает); иначе `Application Support/<dataDirectoryName>/Snapshots/<первые 32 символа sha256 от стандартизованного пути>/`. Внутри проекта ни одна из папок `.laceditor`, `snapshots`, `<id>` не должна быть символической ссылкой (`.unsafePath`).
- Снимки при чтении: `sha256` и UTF-8 проверяются, несовпадение или нет `<id>.txt` — `.corrupted`. Повреждённый индекс переименовывается в `index.json.corrupt` (затем `-2`, `-3`…), список пуст, новый снимок создаёт чистый индекс. Индекс с `version` больше 1 читается, но `add/rename/delete` бросают `.readOnly` и ничего не переименовывают. Лимит «сколько хранить» (`snapshotKeepLimit`, 0 — все) удаляет самые старые снимки вместе с `.txt`; только что созданный снимок не удаляется никогда. Операции синхронные, под одной блокировкой: вызывать вне главного потока. После `add/rename/delete/moveFile` на главной очереди приходит `DocumentSnapshotStore.didChangeNotification`.
- Переименование файла вне проекта (`updateRenamedFileReference`) переносит каталог снимков (`moveFile`); если у нового пути каталог уже есть — не перезаписывается. Переименование или перенос файла в Finder снимки под старым путём оставляет. Снимки внутри проекта лежат в `.laceditor/snapshots` рядом с рукописью и могут попасть в синхронизацию или Git пользователя; `.laceditor` исключается из обходов папки.
- Автосохранение (`AutosaveController`, по умолчанию выключено; интервал 30/60/300 с) пишет через тот же `AppState.write`, но с `SaveOrigin.autosave`. Пишет только документы с путём на диске, изменённые, с `ioState == .idle`; не пишет: при marked text в выбранном документе (повтор на следующем проходе), при `externalChange`, при `hasUnknownMediaTokens`, пока идёт закрытие или вопрос «Сохранить изменения?» (`isClosingOrConfirmingDocument`), после `terminationApproved`, при блокировке `isFolderMoveBlocked`, для заглушек открытия. Новые документы без пути не трогает (у них есть аварийная копия). `DocumentSnapshotStore.add` при повреждённом индексе переименовывает его в `.corrupt` и продолжает с пустым.
- Автосохранение никогда не обходит конфликт с диском (`bypassExternalConflict: false`): вместо окна выбора — статус `pausedExternalChange`. Пауза держится, пока `fileRevisionSnapshot` документа равен записанному в момент паузы; «Оставить мою версию» пауза не снимает, перезагрузка или ручная запись — снимают. Ошибка записи не показывает окон и не переводит `ioState` в `.failed` (возврат в `.idle`, статус `failed`, повтор через интервал). Успешная автозапись не пишет `statusMessage`. Версия `NSFileVersion` при автосохранении записывается не чаще раза в 5 минут на документ (при ручном сохранении — всегда).
- Карточки мира создаются через `FileService.createWorkspaceTextFile` без перезаписи; существующие файлы и папки не трогаются. Содержимое открытой карточки меняется только через редактор (`applyStoryCardEdit`, `applyStoryCardFacts`), а не прямой записью в файл. Установка шаблонов карточек в папку шаблонов не перезаписывает существующие файлы.
- Заметки хранилища (этап 4) лежат в `Application Support/<dataDirectoryName>/Vaults/<vaultID>/open/` (`AppState.isVaultLocalFile`). Они не попадают в «Недавние» и индекс «По словам». После каждой успешной записи вызывается `noteSavedForVault(url)`: файл сверяется с базой, `modified` ставится только при отличии. Перед `noteClosed` делается такая же сверка, чтобы не потерять правки. Серверная версия применяется отменяемой заменой минимального диапазона (`VaultTextDiff`), затем `updateFileRevisionSnapshot` и `markSaved`; запасной путь — `reloadFromDisk`.
- Повреждённый `state.json` хранилища уходит в `state.json.corrupt` (затем `-2`…), пока он есть, `VaultSyncEngine.cleanupAfterCrash` ничего не удаляет (так же при файлах в `open/` без записей). После решения пользователя вызывается `acknowledgeQuarantine()`: копии переименовываются в `state.json.acknowledged…` (не удаляются), уборка и открытие заметок снова разрешены. Файл без записи перед заменой версией сервера сохраняется в снимок `VaultSyncEngine.preservedSnapshotName` (событие `.localTextPreserved`); при сбое снимка (в том числе не UTF-8) файл не трогается, а такой снимок не удаляется при закрытии заметки. Сбой записи состояния даёт событие `.stateBlocked`.
- Файлы `open/` без записи `cleanupAfterCrash` удаляет так: равный `open-state/<sha>.base` — без снимка; отличающийся от базы — после снимка `preservedSnapshotName` и события `.localTextPreserved`; без базы — без снимка (обычные сироты не копятся): такие файлы `acknowledgeQuarantine()` сохраняет в снимок сразу, не дожидаясь уборки. Не UTF-8 или сбой снимка при уборке — файл остаётся (не UTF-8 без записи так и лежит в `open/`: текст хранилища всегда UTF-8, такой файл возможен только как мусор, и удалять его молча не нужно). Символические ссылки не читаются и снимка не дают, сама ссылка удаляется. О карантине при входе сессия узнаёт по `VaultSyncEngine.hasQuarantinedState`.
- Отправка правок хранилища (этап 5): `VaultSyncEngine+Upload.swift`. Очередь по записи `queuedSHA256`; сохранение вкладки ставит отправку с паузой, «Отправить сейчас» и выход ждут через `VaultWaiter` с таймаутом. PUT идёт с `If-Match` от базы; ответ принимается всегда, отправка на лету не отменяется. «409 своей записи» (`currentETag` равен отпечатку отправляемого текста) считается успехом. При 409/412 сервер читается, `VaultMerge.merge` считается вне главного потока (`Task.detached`). Порядок при объединении строго такой: файл становится объединённым, затем база сдвигается на версию сервера, затем PUT с `If-Match`; менять порядок нельзя. Открытая вкладка меняется только через `VaultUploadHost` (`replaceVaultNoteText`: одна отменяемая замена, запись файла, `markSaved`); без вкладки файл пишет движок. Объединение без конфликтов остаётся незаметным, кроме строки «已添加服务器的修改» с «Показать» и «Отменить».
- Конфликт и отказ сервера: при конфликте запись получает `.conflict`, текст остаётся в файле `open/`; снимки обоих текстов делаются при решении конфликта (`saveConflictSnapshots`, при сбое снимка конфликт не меняется), лист `VaultConflictSheet` решает каждый кусок отдельно; невыбранная версия остаётся в снимках. После выбора база сдвигается на версию сервера. Отказ сервера (403, 413, не UTF-8 и т. п.) пишется в `uploadIssue` записи, автоповтора нет, пока текст не изменился или человек не нажал «Отправить сейчас»; временные ошибки повторяются сами. Текст отказанных, конфликтных и удалённых на сервере заметок не пропадает: он остаётся в `open/` до явного «Отменить мои правки…». Снимок «до отмены» делается только для открытой вкладки (она возвращается к основе одной отменяемой заменой); закрытая заметка после вопроса стирается без снимка.
- Закрытие и выход: вкладка заметки хранилища закрывается через `AppState.confirmClosing` → `vaultConfirmClosing` (отправка до 2,5 с, затем вопрос «Закрыть» / «Отменить правки…» / «Отмена»). Выход из приложения спрашивает один раз (`WindowManager.confirmVaultUnsentBeforeQuit`), потом `vaultQuitApproved` отключает вопросы по вкладкам; то же при переключении хранилища (`confirmVaultSwitch`). Сводка «Неотправленное»/«Конфликты» строится из записей чистой моделью `VaultUnsentSummary` и показывается в боковой панели, в строке статуса (клик по «Нужно внимание» ведёт в «Неотправленное») и в меню приложения.
- Остановка и 401 (этап 5): после `shutdown()` ответ идущего запроса выбрасывается (после каждого `await` проверяется `isShutdown`): база не пишется, файл не удаляется, запись остаётся `modified`/`uploading` — следующий запуск распознает «409 своей записи». `.unauthorized` в запись не пишется (хватает `isAuthPaused`). При 401 движок шлёт событие `.authPaused(Bool)`; `VaultSession` ставит `isAuthPaused` и `connectionIssue` «服务器不接受令牌», текст виден в строке статуса и в вопросе при выходе. Пауза снимается (`clearAuthPause`, событие `.authPaused(false)`) при новом сохранении (`enqueueUpload`), в `uploadNow`, `uploadPending`, при возврате связи и при любом успешном ответе сервера (`perform`); новое подключение — новая сессия. `cleanupAfterCrash` не удаляет запись `.synced`, если файл отличается от базы: она становится `modified` без вкладки.
- Внимание и объявления (этап 5): значок «Нужно внимание» и раздел «Неотправленное» показывают отказы, удалённые на сервере, отсутствие связи и записи, ждущие дольше `VaultUnsentSummary.attentionDelay` (только что сохранённая заметка уходит сама); `VaultSession` сама обновляется по таймеру. «Правки отправлены» объявляется после очереди, накопленной без связи (`hadOfflineSpell`), или более одной заметки. Вопрос при выходе различает отправляемое, конфликты и «нерешаемое» (`blockedCount`: отказ сервера, удаление); отправить предлагается только при наличии отправляемого. Имена отмены в редакторе у объединения («合并服务器的修改»), отмены правок и решения конфликта свои; «Отменить» в сообщении об объединении отменяет только объединение.
- Лист конфликта (этап 5): с клавиатуры без особых настроек macOS — карточка куска `.focusable()`, ↑/↓ между кусками, ←/→ выбор (`VaultConflictSelection.step`), Delete снимает выбор, Return применяет или переходит к невыбранному; кнопки «целиком» без сочетаний (⌥⌘1–6 заняты заголовками), доступны через Tab. Версии куска показываются строками сравнения с основой (`TextDiffRow`, номера строк внутри куска), длинное свёрнуто до 12 строк с «Показать все». Отклонения: список автоматически объединённых строк (`autoMergedChanges`) не показывается, только число.
