# README, сборка, версии и выпуск

Читать при изменении README, скриптов, настроек сборки, версии и при подготовке выпуска.

## Синхронизация README

- Поддерживать три равноправные версии: `README.md` — китайская, `README.en.md` — английская, `README.ru.md` — русская.
- Любое изменение сведений о возможностях, требованиях, настройках, установке, сборке или выпуске переносить во все три README в рамках той же задачи.
- Сохранять одинаковый смысл и полноту разделов. Версии, команды, пути, имена файлов и адреса ссылок должны соответствовать друг другу.
- В начале каждого README сохранять ссылки на две другие языковые версии и проверять их после переименований.
- README описывает функциональность текущего кода. Не писать в нём статусы работы («не проверено», «не доработано», «подготовлено», «в текущей ветке»), планы и ссылки на файлы вне репозитория; ограничения функции описывать как её поведение. Различие с опубликованным выпуском вести в `CHANGELOG.md`: не приписывать скачиваемому релизу ещё не выпущенные изменения.
- Список скриптов в разделе сборки README поддерживать в соответствии с папкой `Scripts`.
- Синхронизация относится к основным README; перевод технических отчётов требует отдельной задачи.

## Сборка, версии и выпуск

- Требования и процедуры сверять с `Package.swift`, `LacEditor.xcodeproj`, `Config`, `VERSIONING.md` и текущими скриптами. Официальный пакет предназначен для Apple Silicon; не менять платформу и архитектуру побочно.
- Обычный Debug использует отдельную development-идентичность и данные, Release — официальную; экспериментальная схема и приёмочная сборка имеют отдельные настройки. Кандидат в выпуск использует официальные данные, поэтому его нельзя считать изолированной экспериментальной сборкой.
- При изменениях ресурсов сохранять три языка в Xcode и Swift Package Manager, английский язык по умолчанию и работу `Bundle.module` / `Bundle.main` в соответствующих сборках. Вызовы `swiftc` в проверках имеют собственные списки файлов: зависимость от `L10n` требует включения `L10n.swift` в такой список.
- `.github/workflows/osv-scanner.yml` сканирует оба `Package.resolved` и `LacEditor/Resources/LegacyDiagrams/vendored-package-lock.json`; при обновлении vendored JavaScript синхронизировать manifest и зафиксированные хеши. Локальное исключение `MAL-2025-23922` действует только до указанной даты и при CI-проверке sequence-файла; оно не отменяет предупреждение для npm-пакета. Revision-only пины Yams и SwiftSoup текущий OSV-Scanner не сопоставляет с уязвимостями, поэтому чистый результат их не покрывает.
- В рамках выпуска согласовывать `VERSION`, `MARKETING_VERSION`, запись `CHANGELOG.md`, тег `v<версия>` и возрастающий `CURRENT_PROJECT_VERSION` по `VERSIONING.md`. Не повышать версии и не создавать тег для обычной правки без задачи выпуска.
- Пользовательские изменения описывать в разделе невыпущенных изменений `CHANGELOG.md`, как требует `VERSIONING.md`; техническую правку или изменение документации не выдавать за пользовательскую функцию. Журнал ведётся на русском языке, в разделе выпускаемой версии нет статусов работы («в текущей ветке», «ожидает проверки на Mac», планы); разделы: «Не выпущено», «Добавлено», «Улучшено», «Исправлено», «Изменено», «Безопасность». Заголовок версии `## [версия] - дата` читают скрипты выпуска, его формат не менять.
- Смена версии выполняется только в рамках задачи выпуска и в таком порядке:
  1. Выбрать номер по `VERSIONING.md`; он должен быть выше текущего из файла `VERSION`.
  2. В `CHANGELOG.md` перенести содержимое «Не выпущено» под `## [версия] - ГГГГ-ММ-ДД` с датой запуска `prepare-release.sh`, вернуть пустые подразделы «Добавлено», «Улучшено», «Исправлено» и убрать из записей статусы работы.
  3. Создать `docs/releases/<версия>.md` по образцу предыдущей версии: на эту запись ссылается команда публикации из `build-production.sh`. Указать версию и новый номер сборки; контрольную сумму архива до сборки не писать.
  4. Выполнить `./Scripts/prepare-release.sh <версия>`: он меняет `VERSION`, `MARKETING_VERSION` и `CURRENT_PROJECT_VERSION` (текущий + 1) во всех блоках `LacEditor.xcodeproj/project.pbxproj` и запускает `verify-release.sh`. Эти значения вручную не менять, а если macOS недоступна, правка вручную обязана дать тот же результат: один номер версии и один номер сборки на все блоки, иначе `verify-release.sh` и `prepare-release.sh` останавливаются с ошибкой.
  5. Вручную обновить `MARKETING_VERSION` и `CURRENT_PROJECT_VERSION` в `Config/UIExperiment.xcconfig`: скрипт этот файл не меняет.
  6. Коммит, тег `v<версия>`, `./Scripts/build-production.sh` и публикацию выполнять только по явному запросу пользователя.
- `Scripts/prepare-release.sh` меняет версии и запускает проверки; это не команда только для чтения. Выполнять её в рамках согласованной подготовки выпуска. Официальную упаковку выполнять существующим `Scripts/package-release.sh`, без отдельного обходного сценария; `Scripts/build-production.sh` — полный путь для выпуска: `verify-release.sh`, `package-release.sh` и `.sha256` рядом с архивом в `dist`. Он не меняет версию, не пишет в Git и не публикует.
- Сборочный экземпляр приложения имеет `LSHandlerRank=None` — не предлагается как обработчик файлов; только архивная официальная копия получает `Alternate`. Приёмочная сборка не объявляет `CFBundleDocumentTypes`. Сохранять проверки и очистку регистраций сборочных копий в существующих скриптах.
- Для кандидата сохранять проверку стадии `RCn`, для официального пакета — пустой стадии, а также проверки подписи и целостности архива. Не устанавливать и не публиковать подготовленный пакет без соответствующего поручения.
