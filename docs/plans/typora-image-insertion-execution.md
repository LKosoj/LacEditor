# 10: обычная вставка изображений — миниплан до кода

Статус: только план. Никаких изменений продукта, новых зависимостей, настроек, CSS-тем или AI-процесса. Цель этапа — обычная вставка существующего файла/данных буфера и редактирование alt/адреса/заголовка с действительным Markdown и одной отменой. Отдельный нативный образец 02/10 уже поддерживает local/data URI для отдельного абзаца, но ещё не доказывает весь 10: удалённые изображения, встроенные в текст/контейнеры, размеры `<img>`, полное отображение и приёмка остаются обязательными.

## Текущее устройство

`MarkdownPresentationParser` возвращает `MarkdownImage(range, paragraphRange, url, alt, title)` только для подтверждённого cmark отдельного абзаца. `MarkdownPresentationController` разрешает локальный адрес относительно `document.url`, `file:` и `data:`; у несохранённого документа базы для относительного пути нет. `LacTextView.paste` пока передаёт данные AppKit, обработчика обычной вставки картинки нет. Меню и `MarkdownLinkEditingService` уже имеют редактирование ссылок через актуальное выделение/снимок и проверяемую замену; это пример цикла, а не разрешение считать изображение обычной ссылкой. `AIWritingController.insertImage` создаёт data URI для AI и не является требуемым путём обычных файлов.

## Входы и размещение

1. **Выбор файла:** пункт меню существующего Markdown-меню запускает `NSOpenPanel` выбора одного существующего изображения. Для сохранённого `.md` строить относительный URI от каталога документа к выбранному файлу; рядом лежащий файл получает короткий относительный путь, пробелы, Unicode, `%`, `#`, `?` и скобки кодируются как компоненты URL. Файл не копируется и не меняется. Если относительный путь невозможно корректно выразить (например разные тома), использовать корректный абсолютный `file:` URL; поведение проверяется на текущем local loader. Для несохранённого Markdown не брать cwd/временную папку: записать явный абсолютный `file:` URL выбранного файла. Это сохранит доступность до первого сохранения, но не обещает переносимость; поле адреса отображает фактическое значение.
2. **Вставка из буфера:** когда в pasteboard есть поддерживаемые бинарные данные изображения, а обычный текстовый ввод не должен иметь приоритет, предложить `NSSavePanel` для явного места и имени файла. Не записывать никуда до выбора; сверять реальный формат по ImageIO/UTType и расширение с данными, не выдавать JPEG за PNG. Сохранять в явно выбранное пользователем место без перезаписи (`.withoutOverwriting` либо эквивалентная проверяемая эксклюзивная запись); если путь занят, сообщить и предложить выбрать другой. Для сохранённого Markdown сформировать относительный URI, для несохранённого — абсолютный `file:`. Никакого автоматического удаления файла после отмены текста или последующего undo: это уже пользовательский файл.
3. **Drag-and-drop:** сначала различать один `file URL` существующего изображения, непосредственно сброшенный в целевую точку `LacTextView`; использовать ту же ссылку, что в п. 1, без копии. Бинарные данные без файла — тот же явный выбор назначения из п. 2. Несколько файлов, неподдерживаемые данные и существующие виды drag не должны молча заменяться первой картинкой или ломать системное поведение: зафиксировать/реализовать все требуемые варианты по матрице 01, пока неопределённые маршруты передавать штатному AppKit. Определить точное UTF-16 место падения через текущую геометрию редактора, включая оформленные блоки; не применять устаревшую позицию после модального диалога.
4. **Редактирование alt/address/title:** существующий Markdown-элемент по подтверждённому cmark и актуальной позиции открывает минимальный стандартный диалог с тремя полями. Сохранить title, Unicode и структуру соседнего текста; пустой alt допустим для декоративного изображения, пустой адрес — отказ с понятным сообщением. Не изменять ссылку, код или неоднозначную reference-форму, пока точное преобразование не подтверждено; reference/встроенные формы остаются обязательной частью полного 10. Существующая модель standalone даёт проверенный исходный `range`, но поиск/редактирование изображений в тексте требует точного cmark-разбора, не угадывать по regex.

## Изменение исходника и диалоги

- Минимальный `MarkdownImageEditingService` по примеру проверенного сервиса ссылок: `initial(in:selection:)` и `edit(in:selection:input:) -> MarkdownFormattingEdit?`; input содержит `alt`, `address`, optional `title`. Срезы и итоговое выделение — UTF-16. Для обычной вставки на пустом курсоре генерировать корректный `![alt](<address> "title")`, для выделения использовать выделенный текст как начальный alt; тип окончания строки и окружающий текст не изменять. После выбранного файла/clipboard служба формирует один новый элемент; выбор вокруг существующего изображения приводит к его редактированию, а не дублированию. Проверять результат действительным cmark image node с ожидаемыми адресом/title/alt, включая пробелы, скобки, угловые скобки, backslash, символы `]`, `"`, Unicode и emoji. Не конструировать Markdown слепой конкатенацией без проверки escape.
- Позицию, выделенный текст, document ID, актуальную editor revision, `DocumentTextSnapshot`, язык и editability получить через существующий `EditorTextExtractionRequest` (`requiresEditable: true`) **до** панели, затем повторно проверить после каждого модального шага и после фоновой файловой записи. Использовать проверяемый `EditorRangeReplacementRequest`/имеющийся цикл `shouldChangeText → replace → didChangeText`, одно название действия и одну группу undo. Не использовать `document.text` как актуальный набор. При переключении вкладки/окна, изменении source или выделения, отмене диалога, незавершённом системном вводе, readonly или изменении URL документа не применять устаревшую замену.
- Для clipboard взять зафиксированные данные и тип из pasteboard в момент запуска, не перечитывать подменённое содержимое после панели. Файловое чтение/проверку и запись выполнять вне main, UI/состояние и применение — на main; проверить отмену и идентичность после возврата. Отмена до записи не создаёт файл. Если файл уже записан, но документ успел измениться/закрыться и замена не применима, сохранить файл на выбранном пути и сообщить об этом явно; не удалять его автоматически и не вставлять в другой документ. Если запись не удалась, исходник не меняется. Повторное применение не должно повторно писать файл.
- Переименование или перенос `.md` меняет базу относительных ссылок: на этом этапе не переписывать документ молча. Сохранение под новым именем и то, что текущий loader использует новый `document.url`, проверить; невозможность автоматически перенести ресурс не считать выполнением будущих требований размещения из 25.

## Минимальные файлы и последовательность

1. `Services/MarkdownImageEditingService.swift` и `MarkdownImageEditingTests.swift`: cmark-подтверждение и UTF-16 преобразования локального файла/адреса/title, без UI, сети и записи файла. Если общий код ссылок реально совпадает, извлечь только необходимую общую чистую функцию после отдельной проверки, не делать новый loader framework. Системные прямые `swiftc` и Xcode-списки новых файлов обновляет основной агент.
2. После передачи `AppState.swift` и раздела Markdown меню: стандартная панель выбора/редактирования, параметры, `EditorCoordinator` для проверки/применения; `MarkdownImageInteractionTests.swift` с настоящим NSTextView. Использовать существующие три локализации — новые ключи согласовать с основным агентом. Никаких новых сочетаний клавиш без отдельного решения.
3. После передачи `LacTextView.swift` добавить paste/drop только для подтверждённого изображения, сохраняя текст, форматированный буфер, текущие AI/list handlers и IME. Системная панель должна быть привязана к вызывающему окну и не направлять результат в ставшее активным другое окно; клавиатурную вставку обычного текста не перехватывать. Интеграция записываемых clipboard данных и file URL имеет один проверяемый путь вставки, без дублирования кодирования и преобразования Markdown.
4. В `MarkdownPresentationController`/layout проверять, что фактический результат первого нативного образца отображается после вставки и исходник раскрывается при редактировании. Сеть, сложное размещение, inline, размеры и дополнительные форматы выполняются отдельными обязательными шагами задачи 10 и согласованной 15; не называть данный этап полной 10.

## Проверка и риски

- XCTest чистого сервиса: пустой alt/существующий title, выбранный текст, пустой курсор, Китай/emoji/составные символы, UTF-16 позиции, URL с пробелами/`%`/скобками/кавычками, синтаксические escape и cmark node; URL по относительной базе сохранённого файла и `file:` для несохранённого. Проверить соседние inline markup, code/fence, невалидный адрес и неподтверждённые формы без изменения source.
- Файловые XCTest: реальная временная папка, файл рядом/вложенный/снаружи, Unicode и пробелы, проверка байтов/формата, занятой путь/симлинк/ошибка прав, отсутствие перезаписи и удаления на undo, отмена до записи, stale после записи с сохранённым файлом. Тесты не заменяют проверку Finder и многотомной файловой системы на Mac.
- AppKit interaction: actual paste file URL/PNG, перетаскивание и расположение, исходный и оформленный режимы, актуальный документ в другом окне, изменение selection/документа/URL пока открыта панель или выполняется запись, readonly и marked text, один undo/redo, отмена диалога, повторная активация и недоступная картинка. Синхронизацию результата контролировать детерминированно, без тестовых production hooks кроме необходимости на границе записи/диалога.
- Отдельно проверить пользовательский выбор при pasteboard с одновременными текстом и изображением: системный текстовый путь не должен неожиданно создавать файл. Риски временных/пустых ссылок, файлов в других томах и невозможности записать после диалога показывать явно; не изобретать облачную загрузку, файловую уборку или новые папки.
- После каждого подэтапа — независимое ревью и исправление; Swift/XCTest и реальная приёмка панели, ввода, drag/clipboard, отображения и загрузки выполняются на Mac позже. До этого результат не объявлять готовым. `AppState` сейчас у files, общий parser/controller/layout/LacTextView у владельца 09; не редактировать их параллельно.
