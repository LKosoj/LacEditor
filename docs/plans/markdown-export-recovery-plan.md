# Восстановление, экспорт и редактирование оформленного Markdown

## Запрос и границы

Пользователь просит проверить восстановление открытых документов, включая новые
несохранённые, добавить сохранение в другие форматы через Pandoc и редактирование
оформленного Markdown по примеру Typora. Дополнительно требуется исследовать
остальные возможности Typora и подробно спланировать доработки.

Работа не включает выпуск, установку приложения, создание коммитов, смену
текстового движка, облачную инфраструктуру и несвязанные улучшения.
Объём «всё, что делает Typora» требует уточнения: это существенно больше одного
способа редактирования. До ответа отдельные функции из сравнительного списка
ниже считаются предложениями, а не разрешёнными изменениями.

## Исходное состояние проекта на момент начала аудита

- Чистое исходное состояние git; приложение на SwiftUI/AppKit, macOS 26+.
- `AppPreferences` по умолчанию выбирает `preserveWorkspace`.
- `WorkspaceSessionStore` хранит текст, необязательный путь, язык, кодировку,
  признак несохранённых изменений, выделение и прокрутку. Отсутствие пути
  предусмотрено форматом, в том числе для документов без первого сохранения.
- `DocumentRecoveryStore` отдельно хранит аварийные снимки. Есть проверки
  передачи несохранённого документа из обычной сессии в аварийную.
- Аудит подтвердил, что обычный выход уже сохраняет актуальный текст новых
  документов через `synchronizedText()`. Доработка этого пункта — усиление двух
  существующих тестов отложенным вводом, без нового механизма восстановления.
- `WindowManager` восстанавливает окна и вкладки; выход ожидает чтения/записи.
- `MarkdownRenderer` использует cmark-gfm: таблицы, зачёркивание, задачи,
  автоматические ссылки. `MarkdownPreview` показывает HTML в отдельной панели.
- `EditorTextView`/`LacTextView` редактируют исходный текст. Возможность
  редактировать непосредственно оформленный документ пока не обнаружена.
- Команд экспорта и интеграции Pandoc не обнаружено.
- Среда работы — Linux без Swift и AppKit. Pandoc установлен. Проверки настоящего
  интерфейса, сборки и XCTest потребуют Mac; статический разбор их не заменяет.

## 1. Восстановление документов

### Ожидаемое поведение

При обычном выходе с настройкой сохранения рабочего пространства следующий
запуск возвращает новые документы без пути и правки существующих файлов.
Исходные файлы не перезаписываются. Закрытие вкладки с явным отказом от
сохранения отличается от выхода: отвергнутый текст не должен воскресать.
При принудительном завершении восстанавливается последний завершённый
аварийный снимок; обещать сохранность последнего нажатия клавиши нельзя.

### Шаги

1. Проследить путь `requestApplicationTermination` → снимок рабочего пространства
   → атомарная запись → завершение → чтение → передача в аварийное хранилище.
2. Проверить использование `synchronizedText()`/`synchronizedSnapshot()`:
   последнее введённое содержимое может ещё находиться в NSTextView.
3. Проверить новый документ с `sourceURL == nil`, несколько окон, порядок
   вкладок, выбранную вкладку, dirty-состояние, кодировку и выделение.
4. Проверить ошибку записи, выход во время сохранения и отмену закрытия.
5. Дополнить только отсутствующие проверки. Менять реализацию лишь при
   воспроизводимом недостатке; новый механизм восстановления не нужен.

### Готовность

Проверки `WindowAndSessionTests` и `DocumentRecoveryStoreTests` должны подтвердить
после запуска на Mac
возврат актуального текста без пути, сохранение несохранённости и отсутствие
потери данных восстановления. Отсутствие записи исходных файлов проверять
в ручном сценарии сравнением содержимого файла до выхода и после запуска.
На Mac вручную: новый текст → Cmd+Q → запуск;
изменённый файл → Cmd+Q → запуск; принудительное завершение; явный отказ от
сохранения при закрытии; недоступный каталог снимков.

## 2. Экспорт через Pandoc

### Выбор решения

| Вариант | Преимущества | Цена и ограничения |
| --- | --- | --- |
| Установленный Pandoc, фиксированное меню форматов | Минимум кода; преобразование выполняет готовая программа | Pandoc устанавливается отдельно; PDF требует дополнительный движок |
| Встроенный в приложение Pandoc | Работает без отдельной установки | Упаковка, обновления, размер и лицензирование отдельного компонента |
| Собственные преобразователи каждого формата | Полный контроль | Большой объём кода, слабая совместимость, повторение Pandoc |

**Утверждённое решение:** пользователь выбрал встроенный Pandoc и дополнительно
попросил импорт документов и FB2. Используется официальный Pandoc 3.13 arm64.
Автоматическая загрузка при работе, менеджер расширений, произвольные команды,
шаблоны и смена PDF-движка не входят в эту доработку. PDF пока по-прежнему требует
дополнительный движок; импорт PDF Pandoc не поддерживает.

### Встраивание: подробный план

1. Сохранить официальный ZIP в `Vendor/Pandoc`, проверить SHA-256 по GitHub
   Release. Бинарник занимает около 186 МиБ, поэтому в Git хранится сжатый архив
   около 41 МиБ. `Scripts/prepare-pandoc.sh` распаковывает его без сети и сохраняет
   права запуска; генерируемый файл не включается в Git.
2. В Xcode подготовка предшествует копированию `pandoc` в `Contents/MacOS`.
   Бинарник подписывается при копировании; лицензии и доверенный Lua-фильтр
   копируются отдельно в `Contents/Resources/Pandoc`.
3. Для SPM добавить `.copy("Resources/Pandoc")`; перед прямыми командами
   `swift build/test` явно выполнять подготовку. Приёмочные скрипты делают это
   сами до первой сборки или проверки. Поиск через `Bundle.module` для SPM и
   `Bundle.main` для Xcode не должен обращаться к системному PATH за Pandoc.
4. Включить исходные уведомления `COPYRIGHT` и `COPYING`; зафиксировать сведения
   о версии и условиях предоставления соответствующих исходников перед выпуском
   в `Vendor/Pandoc/README.md`. Публикация и предложение исходников от имени
   пользователя в эту задачу не входят.
5. Проверить архитектуру и зависимости бинарника, права запуска, контрольные
   суммы архива и распакованного файла. На Mac дополнительно проверить запуск
   при PATH без системного Pandoc, подпись вложенного файла и всего приложения,
   сохранность после упаковки/распаковки. Не объявлять эти Mac-проверки пройденными
   по статическому просмотру на Linux.
6. Реальные XCTest не должны пропускать отсутствие встроенного файла: для
   рабочего комплекта это ошибка сборки. Ошибка комплекта локализуется на трёх
   языках и не предлагает пользователю устанавливать Pandoc вручную.

### Импорт: подробный план

1. В «Файл → Импорт…» выбрать один DOCX, ODT, RTF, EPUB, FB2, HTML/HTM или
   LaTeX/TEX. TXT и Markdown уже открываются обычной командой; PDF не предлагать.
   Для расширений использовать фиксированное сопоставление средств чтения.
2. `PandocImportService` запускает встроенную программу в фоне, с исходным
   каталогом как рабочей папкой. Источник передаётся отдельным аргументом после
   `--`, результат читается как UTF-8 только после успешной конвертации.
   stderr хранится в файле; временный каталог удаляется по завершении.
3. Доверенный `import-images.lua` берёт вложенные изображения из mediabag —
   хранилища изображений Pandoc — и локальные файлы относительно источника,
   превращая их в data URI: изображение целиком находится в тексте Markdown.
   Это исключает ссылки на удаляемую временную папку и не требует нового
   хранилища ресурсов. Внешние ссылки фильтр не скачивает. При недоступном
   локальном изображении не выдавать повреждённый результат за полный успех.
4. HTML читать как `html+raw_html`, чтобы Pandoc не загружал содержимое iframe
   до запуска фильтра. Неподдерживаемый сырой HTML остаётся в Markdown и может
   не отображаться в безопасном предпросмотре. Сложное оформление, размеры
   изображений и ссылки на файлы не получают обещания точной переносимости.
5. После конвертации проверить существование исходного состояния окна.
   Создать новый `EditorDocument` с Markdown, `url == nil`, `isDirty == true`
   и `requiresExplicitSave == true`, передав его существующему
   `WindowManager.openNativeTab`. Не заменять открытый документ и не менять
   исходный файл. Закрытое окно не должно самопроизвольно открываться из-за
   позднего результата.
6. Проверки: реальные DOCX/ODT/EPUB/FB2 с PNG, китайским, русским и emoji;
   HTML с локальной картинкой и внешней ссылкой; отсутствующая картинка;
   iframe без загрузки содержимого; ошибка процесса; неизменность источника;
   несохранённый Markdown и изображение в синхронизированном снимке.
   На Mac — меню, новая системная вкладка, закрытие, сохранение и восстановление.

### Пользовательский путь

1. «Файл → Экспорт» для Markdown: HTML, DOCX, ODT, RTF, EPUB, LaTeX,
   FB2, обычный текст, PDF. Это фиксированный начальный набор, а не обещание всех
   форматов Pandoc. Для кода и JSON нельзя молча трактовать содержимое как Markdown.
2. Стандартный диалог выбора имени и назначения; отмена ничего не меняет.
3. Снимок актуального текста снимается после выбора назначения.
4. Преобразование выполняется в фоне отдельным `Process` без командной оболочки.
5. Успех или ошибка показываются в контексте исходного документа.
6. Экспорт не меняет путь, кодировку, dirty-состояние и историю отмены документа.

### Реализация

- Поиск только встроенного Pandoc в предусмотренном сборкой каталоге.
- Перечисление форматов: отображаемое имя, расширение, аргумент Pandoc.
- UTF-8 снимок в отдельном временном каталоге; отдельный выходной файл там же.
- Рабочий каталог и поиск относительных ресурсов привязать к папке исходного
  Markdown; для нового документа не придумывать исходный путь.
- Запуск с массивом аргументов; имена с пробелами, кавычками и `$` не исполняются.
- Не писать сразу в выбранный итоговый файл: переносить результат лишь после
  успешного преобразования; ошибка не должна уничтожать прежний файл.
- Не позволять экспортом перезаписать открытый исходный документ, в том числе
  через символическую ссылку; использовать существующую идентичность файлов.
- Не блокировать основной поток ожиданием процесса; не читать переполняемые
  stdout/stderr каналы только после завершения.
- Ошибки отсутствия Pandoc, дополнительного PDF-движка, ресурсов и записи
  сообщать понятным текстом. Не устанавливать зависимости автоматически.
- Подключить меню к активному AppState; смена вкладки во время экспорта не
  перенаправляет результат на другой документ.
- Новые строки сразу добавить на zh-Hans/en/ru; обновить правила, три README,
  невыпущенный раздел CHANGELOG и списки сборки для новых файлов.

### Проверки

Настоящие HTML/DOCX/ODT/RTF/EPUB/LaTeX/TXT преобразования с Pandoc; PDF с
установленным движком и понятная ошибка без него. Текст русский/китайский/emoji,
заголовки, ссылки, таблицы и код. Относительное изображение в папке с пробелами.
Документ без пути. Ошибка Pandoc сохраняет прежний выходной файл. Снимок содержит
последний ввод. Экспорт не сбрасывает dirty и не меняет исходник. Отмена диалога,
двойной запуск, закрытие и смена вкладки не применяют результат к чужому документу.

## 3. Редактирование оформленного Markdown

### Это отдельная задача, а не редактируемая панель предпросмотра

Typora показывает оформление непосредственно при вводе, раскрывая служебные
символы в зависимости от позиции курсора. Обычный HTML `contenteditable`
с последующим преобразованием обратно в Markdown не подходит: теряются
исходные пробелы, синтаксис, структура и история отмены.

| Вариант | Польза | Ограничения |
| --- | --- | --- |
| TextKit 1, оформление и скрытие разметки поверх исходного Markdown | Сохраняет текущий редактор, снимки, UTF-16, undo, поиск | Таблицы и изображения требуют отдельной работы; оформление меняет геометрию |
| Отдельный специализированный веб-редактор | Богатое оформление блоков | Новая зависимость, мост текста/выделения/undo, отдельная проверка безопасности |
| Расширить только предпросмотр | Быстрее | Не выполняет требование редактировать оформленный текст |

Рекомендуемое направление — TextKit 1, но окончательный выбор требует
детального плана и ранней проверки на Mac. Без этого нельзя объявлять обычную
подсветку «аналогом Typora».

### Поэтапная реализация

1. Определить контракт: Markdown остаётся источником истины; оформление не
   переписывает файл; явное переключение исходного и оформленного представления.
2. Получать разбор и диапазоны элементов из существующего Markdown-парсера.
   Экспериментально проверить координаты cmark и перевод в UTF-16, включая
   табуляцию, CRLF, кириллицу, китайский и emoji. Позиции узла не всегда дают
   границы отдельных маркеров; неподдерживаемые конструкции оставлять видимыми.
   Не разбирать вложенный Markdown регулярными выражениями.
3. Первым реализовать абзацы, заголовки, курсив, жирный, зачёркивание,
   встроенный код, ссылки, цитаты, списки и блоки кода.
4. Раскрывать разметку редактируемого элемента; скрытая разметка остаётся в
   строке. Курсор, мышь, выделение и копирование соответствуют исходнику.
5. Разделить оформление и обычную подсветку, чтобы они не стирали атрибуты друг
   друга. Согласовать метрики со строками, FoldLayoutManager и линейкой.
6. Сохранить marked text — незавершённый ввод китайского и других языков:
   не менять строку, оформление и метрики до завершения ввода.
7. Добавить действия форматирования через существующий цикл изменения AppKit,
   с одной отменой и сохранением выделения. Продолжение списков использовать
   существующее, не создавать второй алгоритм.
8. Следующим шагом таблицы: перемещение по ячейкам, вставка/удаление строк и
   столбцов, экранирование `|`, многострочное выделение. Проверить обычный текст
   при неподдерживаемой конструкции, без потери данных.
9. Изображения: отдельно решить хранение вставленных файлов для нового
   документа; относительные пути, доступность, изменение размера и перетаскивание.
10. Восстановление и перенос окон должны сохранять сам документ и выделение.
    Формат сессии менять только если действительно требуется сохранять выбор
    представления; предусмотреть чтение старых записей.
11. Использовать существующие ограничения больших документов. Не добавлять
    принудительный полный разбор на каждую клавишу и новые численные пороги.

### Готовность

Строка документа и выбранная кодировка до и после переключений одинаковы
при отсутствии правок.
Оформленный текст действительно редактируется; ввод, выделение, отмена,
повтор, поиск, сохранение, восстановление и перенос вкладок согласованы.
Ручные проверки китайского ввода, VoiceOver, масштабирования и большого файла
на Mac обязательны. Крупный риск — геометрия курсора и скрытых символов;
сначала проверять её, затем развивать таблицы и изображения.

### Уточнение после разбора GPT-6.1-Terra

`MarkdownRenderer` сейчас освобождает дерево сразу после получения HTML.
`FoldLayoutManager` задаёт высоту строк по базовому шрифту, а подсветка меняет
лишь временный цвет: этого недостаточно для заголовков разного размера.
Прозрачные маркеры сохраняют ширину и не выполняют требование Typora.
Имеющееся сворачивание одного диапазона строк нельзя переиспользовать как
готовый механизм скрытия многих маркеров.

Первый технический шаг — небольшой проверочный пример на Mac с заголовком
и жирным текстом. Проверить вход/выход курсора, мышь, стрелки, удаление,
выделение через скрытые границы, копирование, поиск, отмену и китайский ввод.
Только после этого зафиксировать конкретный способ оформления и скрытия.
Пример не должен превращаться в новый пользовательский режим сам по себе.
Здесь, на Linux, подтвердить такой выбор экспериментом невозможно.

### Продолжение: первый этап реализации

Пользователь подтвердил продолжение и явно потребовал переключение исходного
и оформленного редактирования. Подготовлен первый этап на TextKit 1 с тем же
NSTextView и исходной строкой. Это подготовленная реализация с тестами, а не
успешно пройденная приёмка на Mac. Кандидат со скрытыми глифами остаётся
непроверенным визуально до запуска Mac-проверок.

1. В меню «Вид → Редактирование Markdown» — два явных выбора: «Исходный
   Markdown» и «Оформленный текст». Выбор хранится в `EditorDocument` только
   в текущем запуске, переносится с документом, не меняет формат сессии.
   Восстановление запускается в исходном представлении.
2. `Models/MarkdownPresentation.swift` содержит диапазоны и виды оформления.
   `MarkdownPresentationParser` использует дерево cmark, переводит байтовые
   позиции в UTF-16 компактным индексом поправок для символов вне ASCII.
   Строки с табуляцией, неоднозначные позиции, таблицы и изображения не получают угаданных
   скрытых диапазонов. Маркеры списков остаются видимыми.
3. Первая версия оформляет заголовки, жирный, курсив, зачёркивание, код,
   ссылки, цитаты и блоки кода. Подтверждённые маркеры скрываются вне выделенных
   абзацев; выделение раскрывает затронутый элемент. Сохраняется копирование
   исходного Markdown. Таблицы-сетки, изображения внутри текста, формулы,
   диаграммы и команды форматирования остаются следующими отдельными задачами.
4. `FoldLayoutManager` скрывает маркеры отдельно от сворачивания строк и
   рассчитывает высоту заголовка по пересечению диапазона всей строки, в том
   числе с отступом или внутри цитаты. При вводе инвалидируется только видимая
   область; при явном возврате к исходнику — все ранее скрытые глифы.
5. `MarkdownPresentationController` объединяет быстрые правки перед фоновым
   разбором. Результат проверяет поколение, документ, текущую версию редактора,
   активность и отсутствие незавершённого системного ввода. Смена выделения
   использует готовый результат; оформление обновляется только в видимой
   области, включая изменение размеров окна. Новых порогов размера нет.
6. Шрифты оформления меняют атрибуты отображения, не строку. При возврате в
   исходник восстанавливаются базовый шрифт, шрифт нового ввода и скрытые знаки.
   Собственный фон согласован с подсветкой парных скобок. Изменение геометрии
   обновляет карту строк линейки. Незавершённый системный ввод откладывает
   изменение оформления до окончания композиции.
7. Тесты: `MarkdownPresentationParserTests`, `MarkdownLayoutTests`,
   `MarkdownPresentationTests`. Покрытие: Unicode и окончания строк, вложения,
   неподтверждённые маркеры, нулевая ширина/раскрытие, заголовки в цитатах,
   независимость сворачивания, восстановление знаков за экраном после быстрой
   правки и выключения, неактивная вкладка, ввод после возврата к исходнику,
   история отмены/повтора и обновление линейки. Эти XCTest ещё не запускались.
8. Новые исходники добавляются в Xcode; SPM подхватывает каталог. Чистые модели
   диапазонов включены также в четыре прямых вызова `swiftc`, использующих
   `FoldLayoutManager`; C-парсер не нужен самостоятельным проверкам раскладки.

На Mac обязательны: сборки Debug/Release и все XCTest; мышь/стрелки/удаление
возле скрытых знаков; выделение нескольких абзацев и копирование; китайский
ввод и переключение вида во время него; отмена/повтор после форматирования;
поиск и переход к результату; перенос вкладки и восстановление прежнего текста;
шрифты CJK, размеры окна и номера строк; глубокая прокрутка и правки крупных
смешанных документов. До этих проверок нельзя объявлять решение стабильным
или соответствующим всем возможностям Typora.

### Следующий этап: команды форматирования и оглавление

По запросу продолжения выбраны два пункта исходного плана, не требующие новых
зависимостей и смены редактора. Реализация подготовлена; приёмка на Mac не
проведена. Остальные функции Typora не считаются частью этого этапа.

**Команды форматирования:**

1. «Формат Markdown» содержит жирный (`⌘B`), курсив (`⌘I`), зачёркивание,
   встроенный код, заголовки 1–6 и цитату. Сочетания `⌘1…9` для вкладок сохраняются.
   Команды работают в исходном и оформленном представлениях активного Markdown.
2. `MarkdownFormattingService` читает актуальный NSString и выделение в UTF-16,
   возвращает один диапазон замены, строку и итоговое выделение. При вставке
   внешние пробелы остаются вне знаков оформления; повтор снимает только точно
   распознанную пару вокруг того же выделения. Без выделения вставляется пара
   знаков с курсором внутри. Для кода выбирается длина обратных кавычек с учётом
   самого текста и краевых пробелов.
3. Несколько абзацев не обрамляются общей inline-парой; экранированные границы
   не удаляются и не получают ошибочно экранированную вставку. Заголовки и цитаты
   не применяются к fenced/indented коду. Точное исходное написание окончаний
   строк CRLF, CR и LF сохраняется. Создание списков в этот этап не входит.
4. `AppState` направляет команду выбранному документу; `EditorCoordinator`
   проверяет активность, доступность ввода, язык, состояние чтения/записи,
   единственное выделение и отсутствие marked text. Применение синхронно через
   `shouldChangeText → replaceCharacters → didChangeText`, отдельную группу
   отмены и обновление выделения. Модель не заменяется напрямую.
5. Проверки: `MarkdownFormattingServiceTests` — Unicode, суррогатные границы,
   пробелы, экранирование с обеих сторон, backtick, разные окончания строк,
   конец выделения на следующей строке, цитаты и код. Часть ожидаемой разметки
   сопоставляется с настоящим cmark. `MarkdownFormattingInteractionTests` —
   активный NSTextView, одна отмена/повтор, запрет read-only и раскрытие
   свёрнутого участка при переходе курсора. XCTest пока не запускались.

**Оглавление:**

1. В существующей боковой панели добавлен свёрнутый раздел «Оглавление».
   Он содержит ленивый список заголовков с отступом по уровню; файловая
   библиотека и её перетаскивание не перестраиваются. Раскрытие — временное
   состояние окна; после перезапуска раздел снова свёрнут.
2. Результат `MarkdownPresentationParser` содержит и оформление, и заголовки.
   Названия получаются из дочерних узлов cmark: текст, код, подписи ссылок и
   изображений, а не удалением знаков регулярным выражением. ATX/setext,
   вложенное оформление, китайский и emoji покрыты тестами; заголовок с
   неоднозначными координатами табуляции использует безопасное начало строки.
3. `MarkdownPresentationController` выполняет один разбор, если нужен
   оформленный вид или фактически видимое оглавление. В исходном виде он не
   меняет атрибуты. Готовый результат используется повторно при включении
   второй функции. При выключении обеих работа отменяется.
4. `markdownHeadings` и `isMarkdownOutlineCurrent` относятся к документу.
   Принятая правка и внешняя замена текста сразу отменяют актуальность.
   Поздняя публикация проверяет документ, поколение, активность и версию
   редактора; переключение вкладок не смешивает списки.
5. Нажатие проверяет выбранный документ и принадлежность актуальному списку,
   затем использует существующий путь выделения/прокрутки. Пустой диапазон
   курсора ограничивается явно, без потери позиции; свёрнутый текст раскрывается.
6. Проверки: `MarkdownOutlineTests`, дополненный parser-тест и тест перехода
   через Coordinator — исходный вид без оформления, повторное использование
   результата, неактивность, правка, внешняя замена, запрет старого/чужого пункта,
   UTF-16 и переход не в начало документа. XCTest пока не запускались.

Новые `MarkdownFormattingService.swift` и `MarkdownOutlineView.swift` включены
в Xcode; SPM подхватывает исходники/тесты из каталогов. Прямые проверки раскладки
не используют новые меню и сервис, дополнительных зависимостей в них нет.
Переводы и документация обновлены на трёх языках. На Mac обязательны сборки,
XCTest, команды в обоих представлениях, undo/redo рядом с обычным вводом,
настоящий китайский ввод, раскрытие/скрытие панели и переход к заголовку после
правки и сворачивания. Локальная среда Linux этого не подтверждает.

Остальные части остаются отдельными задачами со своими проверками:

1. Структура и исходные диапазоны Markdown — новый небольшой компонент в
   `Preview`, тесты структуры и Unicode; жизненный цикл cmark остаётся единым.
2. Отображение и позиционирование — `EditorTextView`, `FoldLayoutManager`,
   `LineNumberRulerView`; размеры строк, курсор, выборка и очистка оформления.
3. Интеграция обновлений — точечные участки `EditorCoordinator`, применение
   только для текущей версии/выделения, отложенное обновление при marked text.
4. Базовые команды форматирования реализованы через `LacEditorCommands` и
   существующий путь изменений AppKit; проверка одного шага отмены ещё требует
   запуска на Mac. Создание списков и задач остаётся отдельной доработкой.
5. Таблицы — отдельное решение для сетки и ячеек; обычный текст таблицы не
   объявлять готовым оформленным редактором таблиц.
6. Изображения — отдельное решение хранения ресурсов документа без пути;
   политику локального предпросмотра менять только в согласованном объёме.
7. Состояние представления — определить, нужен ли возврат выбора после запуска;
   если да, проверить совместимость старых сессий до изменения их структуры.
8. Производительность — измерить на Mac; существующие ограничения разных
   подсистем не означают автоматически проверенный предел нового оформления.

## 4. Сравнение остальных функций Typora и дальнейшие задачи

Ниже инвентаризация семейств возможностей по официальной документации, а не
утверждение полного совпадения всех настроек и расширений Typora.

| Возможность | LacEditor сейчас | План и критерий проверки |
| --- | --- | --- |
| Исходный Markdown и отдельный предпросмотр | Есть | Сохранить оба при добавлении оформленного редактирования |
| Таблицы, задачи, зачёркивание | Есть в предпросмотре | Отдельно добавить действия редактирования, навигацию и undo |
| Заголовки и оглавление | Оформление, команды заголовков и панель оглавления подготовлены | Проверка на Mac; вставка `[TOC]` остаётся отдельной задачей |
| Ссылки внутри документа и между файлами | Предпросмотр открывает внешне только HTTP(S), остальные переходы отменяет | Согласовать идентификаторы заголовков, Unicode и дубликаты; использовать обычное открытие файлов |
| Изображения | В предпросмотре политика разрешает data URL | Локальные ресурсы и вставка требуют отдельного согласования текущей политики; пути и переносимость проверять без сети |
| Формулы LaTeX | Нет | Выбрать локальный движок и лицензию; встроенные/блочные формулы; совпадение экспорта и редактора |
| Диаграммы | Локальный Mermaid 12.2.0 подготовлен для предпросмотра; проверен в Chromium, ожидает Mac/WebKit | SVG/PNG при экспорте и другие синтаксисы остаются отдельными задачами |
| Сноски, YAML, alerts, подсветка, индексы | Полного набора нет | Утвердить диалект Markdown; cmark и Pandoc разбирают его отдельно, различия проверять примерами; тесты вложений и экранирования |
| Дерево папок и быстрый поиск файлов | Есть недавние, избранное и группы | Дерево не подменяет библиотеку; обход папок, порядок и поиск — отдельная задача |
| Поиск по папке | Есть поиск в документе | Отдельная операция чтения файлов с отменой; переход к найденному месту; без скрытого изменения файлов |
| Фокус и печатная машинка | Добавлено скрытие инструментов текущего окна; ожидает проверки на Mac | Затемнение неактивного блока и удержание курсора по высоте ещё не реализованы |
| Статистика | Есть текущая статистика | Сначала сверить покрытие: слова/символы/выделение; добавлять только выбранные показатели |
| Темы и пользовательский CSS | Есть системная/светлая/тёмная тема | Произвольный CSS относится к HTML; не обещать применимость к TextKit без отдельного решения |
| Умная вставка и копирование HTML | Обычное текстовое редактирование | Определить форматы буфера и правила преобразования; одна отмена; исходный Markdown сохраняется |
| Импорт, экспорт, шаблоны, повтор экспорта | Встроенный Pandoc, импорт и экспорт с FB2 добавлены в текущую ветку, ожидают проверки на Mac | Шаблоны и повтор — отдельные доработки после выбора |
| HTML, видео и встраивания | Предпросмотр ограничен локальной политикой | Нельзя включать исполнение HTML/JS и сетевые ресурсы под видом паритета; отдельное решение |
| Загрузка изображений и публикация | Нет | Только отдельный явный запрос: внешние сервисы, доступы и передача данных |
| Командная строка | Открытие файлов через существующий запуск | Сначала согласовать конкретные команды, затем реализовать без второй модели окон |

Эта таблица — предварительная инвентаризация остальных возможностей.
Она не заменяет подробные задачи на их реализацию: после выбора пунктов
потребуются отдельные планы с точными файлами, зависимостями и проверками.
До согласования выбор не сделан, зависимости не добавляются.

## Последовательность, исполнители и ревью

1. Закончить аудит восстановления и исходный общий план.
2. GPT-6.1-Terra подробно планирует каждую принятую задачу до её разработки.
3. Восстановление и экспорт можно разрабатывать параллельно, распределив файлы;
   общие README, AGENTS и CHANGELOG редактирует один участник.
4. Для оформленного Markdown сначала выбрать подход и пройти раннюю проверку
   курсора и ввода, затем реализовывать блоки, таблицы и изображения по порядку.
5. После каждой задачи другой GPT-6.1-Terra проводит ревью конкретного diff.
   Замечания исправляются в границах задачи, без соседних улучшений.
6. После реализации запустить запрошенный `/goal`: повторять независимое ревью
   и исправления до отсутствия ошибок и предупреждений. Отдельно перечислять
   проверки, которые не удалось выполнить; ревью не заменяет запуск приложения.
7. Основной агент читает итоговый diff, проверяет привязку изменений к запросу,
   `git diff --check`, переводы и списки сборки.
8. На macOS: `sh Scripts/prepare-pandoc.sh`, `swift build`, `swift build -c release`, `swift test`, затем
   относящиеся к задаче проверки `Verification` и ручная приёмка. Выпуск не делать.

- Повторное независимое ревью первого этапа GPT-6.1-Terra не обнаружило новых

## Панель, рабочая область и Mermaid: согласованный следующий этап

Запрос: показывать/скрывать левую панель, оставлять редактор на всю рабочую
область окна без инструментов и отображать Mermaid. Выбран минимальный путь:
использовать существующую панель и редактор, локальную библиотеку в существующем
предпросмотре. Системный полноэкранный режим, новая модель окон и экспорт
диаграмм изображениями в эту задачу не входят.

1. **Переключатель панели.** Существующие кнопку и `⌃⌘B` сохранить, команду
   перенести в меню «Вид». Проверить обычное скрытие/показ и согласование
   системного разделителя с состоянием окна.
2. **Рабочая область без инструментов.** Команда «Вид → Включить режим без
   отвлечений», `⇧⌘J`. Временно скрывать боковую панель, предпросмотр, номера
   строк, строку состояния, начальные подсказки и панель инструментов. Хранить
   только флаг текущего окна и прежнюю видимость его панели инструментов;
   существующие настройки и состояние документов не переписывать. При выходе
   восстановить прежний вид; `⌃⌘B` выходит и показывает боковую панель. Системные
   вкладки и кнопки окна остаются. При смене окна восстановить прежнюю панель.
   Проверки: другое окно не затронуто, скрытая до входа панель остаётся скрытой,
   выделение и отмена редактирования сохраняются, разделитель раскрывается.
3. **Mermaid в предпросмотре.** Встроить неизменённый Mermaid 12.2.0 и лицензии,
   подключить ресурсы SPM и Xcode. Собственный небольшой `render.js` обрабатывает
   только блоки `mermaid` в существующем HTML. Выполнять библиотеку в изолированной
   среде приложения, сохраняя запрет JavaScript документа и внешних ресурсов.
   Исходный код остаётся в DOM — дереве элементов страницы; после успешного
   преобразования он скрывается, рядом появляется SVG. Ошибка показывает код и
   перевод сообщения. Тема перерисовывает диаграммы из исходного кода.
   Очередь и номер обновления не дают старому результату заменить новый;
   скрытие предпросмотра отменяет применение текущего результата. Защищённые
   настройки Mermaid, включая стандартные ограничения библиотеки, сохраняются.
   Проверки: блок-схема, последовательность, Unicode, отдельная ошибка,
   смена темы, отмена, отсутствие сетевых запросов и исполнения HTML из меток.
4. **Проверка и описание.** Новые тексты на трёх языках; README на трёх языках,
   AGENTS и CHANGELOG обновить. Две независимые задачи GPT-6.1-Terra: интерфейс
   и Mermaid, каждой предшествует подробный план; затем отдельное ревью.
   Повторять ревью после исправлений и проверить итог основным агентом.

### Результат текущего этапа и границы проверки

- Шаги 1–3 подготовлены в исходниках; добавлены XCTest для интерфейса и WebKit.
- Независимые ревью GPT-6.1-Terra завершились без подтверждённых ошибок и
  предупреждений после исправления списка защищённых настроек Mermaid.
- Основной агент запустил реальный Chromium с локальной библиотекой и кодом
  приложения: блок-схема, последовательность, русский/китайский текст,
  сообщение об ошибке одного блока, смена темы, сохранение исходного кода,
  запрет исполнения HTML/событий и отсутствие сетевых обращений проверены.
  Отдельно проверены отмена устаревшего результата и удаление временных элементов.
- Проверка Chromium не подтверждает поведение WKWebView. Сборка Swift,
  XCTest и работа интерфейса на macOS остаются непроверенными на Linux.
- Экспорт Pandoc сохраняет Mermaid как исходный код; превращение диаграмм в
  изображения при экспорте не добавлено. Другие возможности Typora не объявлены
  реализованными этим этапом.
