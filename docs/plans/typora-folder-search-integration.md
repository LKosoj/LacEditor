# 20: подключение поиска по папке — миниплан до кода

Статус: только план; продуктивное подключение не выполнено. `FolderSearchController`/`FolderSearchView` и их контракт уже реализованы отдельно и остаются без изменений до отдельного решения. На Linux Swift/XCTest и macOS-интерфейс не запускались.

## Владение и интерфейс

- Один `FolderSearchController` принадлежит одному `AppState` окна, как и `folderWorkspace`. Создать лениво через замыкания со слабыми ссылками на состояние/менеджер; не хранить второй глобальный контроллер и не переносить его вместе с документом в другое окно.
- `SidebarLibraryView`: после существующего заголовка папки отдельный компактный раскрываемый раздел `FolderSearchView(controller:)` в общей прокрутке. Существующий фильтр библиотеки по имени/группам, дерево, выбор файлов и сообщения файловых операций остаются действующими. Корень поиска берётся только из `appState.folderWorkspace.rootURL`; `setRoot` при его изменении немедленно отменяет предыдущие результаты. `close()` в `closeAuxiliaryWindows` и `resetClosedWindow` отменяет задачи; при повторном раскрытии после очистки назначить текущий корень заново. Не запускать обход при наборе каждого символа.
- `FolderSearchView` сейчас содержит собственный обычный `VStack` с `ForEach` результатов. Встраивание как одной строки общего `LazyVStack` не делает тысячи внутренних результатов ленивыми. Первое подключение должно либо отдавать строки результатов непосредственно в существующий ленивый список, либо явно оставить эту часть незавершённой до согласованного изменения view; второй ScrollView и принудительное ограничение результатов не добавлять. Это потребует узкой правки view, несмотря на текущую заморозку файлов 20; заранее согласовать её, а не молча менять.

## Снимки и открытие

1. `WindowManager` на главном потоке собирает документы всех зарегистрированных состояний окон, включая dirty (несохранённые) документы. Для каждого имеющего URL и не являющегося незавершённым placeholder получить `synchronizedSnapshot()`, затем снова проверить принадлежность объекту окна, URL, `fileIdentity` и ревизию; передать `FolderSearchService.OpenDocument` как значение. Не читать модельный `text` вместо живого редактора и не передавать объекты документа в фон. Пропавший с диска открытый файл по-прежнему входит по своему пути и снимку. Быстрый поиск имён снимки не запрашивает.
2. Есть важная граница текущего контракта: `snapshots` возвращает массив и не может сообщить ошибку, если синхронизация вызвала повторное изменение документов/окон. Нельзя молча пропустить такой документ и выдать неполный поиск как успешный. Предлагаемое минимальное разрешение — отдельно согласовать изменение callback на необязательный массив (nil = устаревший запуск) и явный отказ в `start/select`; либо доказать устойчивость собираемого набора другим конкретным способом. До этого не считать защиту от повторного входа завершённой.
3. Для открытого совпадения callback `reveal` на главном потоке находит тот же объект и состояние по ID, проверяет текущее владение, URL/идентичность и повторный `synchronizedSnapshot` с ожидаемой ревизией, проверяет границы UTF-16 и точную подстроку. Для `.open` дополнительно использовать `FolderSearchService.isCurrent`. Активировать окно через существующий `WindowManager.focus`, затем **снова** проверить ID/снимок и выбранный документ: активация может вызвать обработчики. Установить `document.selectionRange` и отправить существующий `EditorSelectionRequest` через `revealSelection`, который раскрывает свёрнутый диапазон и прокручивает его. Если документ не выбран, закрыт, текст изменился или проверка повторного входа не прошла — вернуть false. Текст/dirty/readonly/история отмены не меняются.
4. Для дискового совпадения `open` перед фактическим вызовом `WindowManager.openFile` проверяет `Task.isCancelled` и принадлежность текущему root; после любого ожидания контроллер сам повторно проверяет поколение. Открытие использует существующую проверку `DocumentFileIdentity` среди окон: уже открытый файл активируется, иначе создаётся штатная системная вкладка/placeholder через тот же `openFile`. Не вызывать отдельный `FileService.read` и не создавать `EditorDocument` самостоятельно.
5. Нужен узкий сигнал **фактической загрузки**: после `openFile` найти через менеджер реально выбранные состояние и документ по идентичности; если он `.opening`, дождаться изменения существующего `ioState` и удаления placeholder из состояния с помощью краткоживущей подписки Combine, без polling (периодических опросов). `@Published` выдаёт событие до присваивания: после события проверить свойства на следующем обороте главного потока. Успех — тот же зарегистрированный объект, больше не placeholder, `.idle`, актуальный URL/идентичность и синхронизированный снимок; `.failed`, отмена выбора кодировки, закрытие окна/placeholder или отмена задачи дают nil. Подписки и continuation (ожидание результата) освобождаются ровно один раз при любом исходе. Открытие могло уже начаться: отменять общий файловый read без доказанного эксклюзивного владения нельзя; позднее выделение отменённого запроса запрещено.
6. После загрузки `FolderSearchController` уже ещё раз проверяет диск, наличие того же снимка среди всех окон и точный фрагмент. Callback `reveal` повторяет проверку перед выделением; если пользователь переключил документ/окно во время чтения, не возвращать его принудительно к старому результату. Проверка состояния диска опирается на дату/размер/идентичность и фрагмент, не является полной контрольной суммой. Быстрое открытие через `openFile` не задаёт выделения.

## Точные места изменений и проверка

- `AppState.swift`: ленивый controller, привязка корня/очистки, узкий callback проверенного выделения; не менять read/write/закрытие документов. `WindowManager.swift`: сбор снимков и поиск открытого объекта по ID/идентичности; адаптация **существующего** `openFile` для получения состояния/объекта и короткого ожидания загрузки. Обработать ранние отказы `openFile` (включая блокировку файловой операции), уже открытый `.opening`, отмену диалога кодировки, ошибку и закрытие. Не нарушать текущую проверку единого открытого файла.
- `SidebarLibraryView.swift`, при необходимости `FolderSearchView.swift`: только размещение и ленивые строки в одной общей прокрутке. Существующая секция папки и список библиотеки сохраняются. Возможное минимальное изменение `FolderSearchController.swift` для достоверного отказа снимка описано выше и требует отдельного согласования.
- `FolderSearchIntegrationTests.swift`: два реальных состояния/окна, dirty снимок из live provider при несовпадении с `document.text`, поиск существующего документа через алиас, UTF-16/emoji и раскрытие свёрнутого диапазона; отказ после смены ID/revision/пути/фрагмента/окна. Для ожидания загрузки — управляемый существующий `readFile`, реальный placeholder, успех, ошибка, отмена и закрытие, смена запроса до фактического open и во время чтения. Два независимых вызывающих открытия одного файла не создают вторую вкладку. Проверить позднее завершение и отсутствие утечки подписки/повторного completion.
- На Mac позже: сборка обоими способами и XCTest, клавиатурный выбор в боковой панели, реальный live editor и выделение, чтение большого файла/ошибка/выбор кодировки, переключение вкладки во время загрузки, IME (незавершённый системный ввод), доступность и отзывчивость длинного списка. Приёмка 20 не включает теги из задачи 14 и не считается завершённой только по подставным callbacks.
