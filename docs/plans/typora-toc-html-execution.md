# 13б/07: `[toc]`, заголовки и якоря в HTML и PDF — миниплан

Статус: план до кода. Использовать уже закреплённый cmark, текущие `MarkdownRenderer`/`MarkdownPreview` и существующий PDF-вывод; второй разбор того же снимка, новая библиотека, CSS-темы и ослабление CSP не нужны. Исходный Markdown не изменять. HTML/PDF — отдельная часть 13б; Pandoc-экспорт и полная задача 07 остаются обязательными последующими частями.

## Подтверждённая возможность и ограничение

`MarkdownRenderer.renderPage` сейчас один раз разбирает текст cmark, рендерит безопасный HTML без `CMARK_OPT_UNSAFE`; `MarkdownPDFExportService` использует `MarkdownRenderer.render` и тот же HTML. Предпросмотр разрешает внутреннюю навигацию только для фрагментов сносок `fn-*`/`fnref-*`; для заголовков сейчас нет ID. Существующий нативный `[toc]` работает по заголовкам общего presentation-разбора и целевым диапазонам редактора; сюда нельзя включать повторный вызов `MarkdownPresentationParser.parse`.

На C-бинарнике точного тега swift-cmark 0.8.0 (`924936d0427cb25a61169739a7660230bffa6ea6`) проверено: cmark разрешает добавить в заголовок `CMARK_NODE_CUSTOM_INLINE` с собственным `on_enter`, заменить подтверждённый абзац на `CMARK_NODE_CUSTOM_BLOCK`, затем `cmark_render_html` без `CMARK_OPT_UNSAFE` выводит собственные `<span id=…>`/`<nav>…</nav>`, а пользовательский `<script>` по-прежнему заменяет комментарием. Результаты `prepend_child` и `replace` проверены; это доказательство C API, не Swift-сборка и не проверка WebKit/PDF. Вставляемый HTML должен создаваться только приложением из проверенных и экранированных значений; пользовательский raw HTML нельзя помещать в custom node.

Отдельная C-проверка подтвердила `cmark_node_insert_before` с custom-block перед заголовком: прежний `<hN>…</hN>` остаётся неизменным. Первая реализация renderer/preview подготовлена для независимого ревью; Swift, XCTest, WebKit и PDF на Mac не запускались. Правило текста заголовка вынесено в общую функцию `MarkdownPresentationParser.headingText`. Pandoc-экспорт и нативные Cmd-якоря остаются обязательными частями.

## Один разбор, общий текст заголовка и обнаружение маркера

1. В `MarkdownRenderer.swift` после `cmark_parser_finish` обходить полученное дерево в порядке документа; не брать заголовки из второго parser. Получать уровень и отображаемый текст тем же правилом, что в `MarkdownPresentationParser` (текст и inline code, пробел для переноса, дочерние узлы). При интеграции выделить это небольшое чистое правило в общее место существующего parser/renderer после завершения работы 09, чтобы нативное и HTML-оглавление не расходились. Указатели cmark живут только до `cmark_node_free`; в результат страницы передавать только значения.
2. Пропускать заголовки в определениях сносок, как уже делает presentation parser; одинаковый порядок H1–H6 и текст сверить с ним в XCTest на одном исходнике. Изображения/вложенная разметка внутри заголовка и пустые заголовки проверять отдельно — не подменять доказанный результат догадкой.
3. Для `[toc]` использовать те же ограничения текущей нативной части: cmark-узел paragraph — прямой ребёнок document, единственный child типа text, а точный исходный диапазон самого абзаца равен `[toc]`. Проверять исходные байтовые позиции cmark по строкам и перевод их в UTF-16 либо переиспользовать точечный общий конвертер, без поиска регулярным выражением и замены исходного Markdown. Экранированный маркер, реальная ссылка `[toc]`, код, цитата, список и соседний текст остаются обычным выводом. Для пустого списка заголовков сохранить обычный `[toc]`, как в нативном представлении. Несколько подтверждённых маркеров используют один и тот же список.

## Якоря и внутренние ссылки

1. Для каждого заголовка вычислять детерминированный безопасный внутренний ID с отдельным префиксом `lac-heading-`, чтобы не пересекаться с cmark `fn-*`/`fnref-*` и случайным пользовательским HTML. Предложенное правило slug: NFC, независимое от пользовательской локали приведение к нижнему регистру; буквы, цифры, объединяющие знаки и `_` сохраняются, пробельные последовательности становятся `-`, прочая пунктуация удаляется, крайние `-` снимаются; пустой результат получает `section`. При коллизии выделять первый свободный `-1`, `-2` и т. д. с учётом уже занятых ID, включая заголовки с такими суффиксами. Пример `A`, `A-1`, `A` → разные ID даже при встрече заранее занятого суффикса. Проверить это правило на матрице 01 и при необходимости согласовать совместимость внешних якорей до полной 07; оно не объявляется уже доказанным правилом Typora.
2. Непосредственно перед каждым заголовком добавить пустой custom-block `<span id="…"></span>`; текст и разметка заголовка остаются в оригинальных cmark-узлах, прежний HTML заголовка не меняется. Для оглавления заменить только подтверждённый paragraph на custom-block `<nav>` со ссылками по уровню/порядку и текстом заголовка; брать текст как текст, отдельно экранировать `&`, `<`, `>`, кавычки в атрибутах. URL-фрагмент кодировать как UTF-8 URI, ID — как HTML-атрибут. Не доверять строкам заголовков как готовому HTML. При неуспехе cmark-операции освободить временный узел и оставить исходный paragraph/heading читаемым; не включать unsafe.
3. Пользовательские обычные Markdown-ссылки `#slug` согласовать с тем же отображением: для подтверждённого cmark link, у которого локальный фрагмент соответствует известному slug, заменить только URL узла в дереве на внутренний ID; повторный slug относится к первому подходящему заголовку, полное имя с суффиксом — к соответствующему. Не переписывать внешние URL, неизвестные фрагменты, исходник или ссылки, созданные cmark для сносок. Однократное percent-decoding и нормализацию проверить для китайского, emoji, `%`, кавычек и некорректных последовательностей; неоднозначные адреса не угадывать. Native Cmd-переходы и кросс-документные ссылки 07 требуют отдельно того же сопоставления и тестов, их не объявлять готовыми из HTML.
4. `MarkdownRenderedPage` получает множество сгенерированных ID и использует его вместе с соответствующей страницей/версией. `MarkdownPreview.Coordinator` разрешает `about:blank#…` для заголовка только при точном совпадении декодированного фрагмента с ID текущей применённой страницы; прежний путь сносок сохраняется, внешние http/https и прочие схемы не расширяются. Смена снимка/страницы не должна разрешать якорь старой страницы. CSP и существующая изоляция сценариев не меняются; произвольный JavaScript пользователя не запускается.

## PDF, экспорт и проверки

1. PDF через `MarkdownPDFExportService` получает тот же HTML готового снимка и отображает оглавление без второго разбора. Проверить, что ожидание Mermaid/шрифтов, отмена, revision снимка и цикл печати не изменились. Наличие визуального списка не доказывает работающие PDF-ссылки или закладки: на Mac открыть PDF в PDFKit, проверить координаты, переходы по ссылкам и многостраничный вывод; при отсутствии встроенных ссылок/закладок оставить эту часть явно открытой в 23.
2. HTML/Pandoc/DOCX/EPUB и другие писатели 24–25 не считаются согласованными по одному renderer: каждый получает отдельную таблицу возможностей и XCTest с реально встроенным Pandoc 3.13. Определить, принимает ли его reader `[toc]`, как он создаёт ID/дубли/Unicode и как сохранить исходные метаданные/сноски. Без проверки не менять общий формат reader и не обещать один и тот же HTML. Не создавать автоматически user-файлы или дополнительные зависимости.
3. XCTest renderer: один/несколько standalone `[toc]`, absence headings, inline стили/китайский/emoji, CRLF, экранирование и code/quote/list/обычная ссылка, повторные и пустые заголовки, зарезервированные имена и `a`/`a-1`/`a`, точное соответствие имён, ID и ссылок. Сравнить порядок/названия с `MarkdownPresentationParser` в тесте (только для проверки, не production-разбор). Проверить сноски с заголовками внутри определений и ссылки туда/обратно, неизвестный фрагмент, безопасное экранирование, raw `<script>`/опасные URL и неизменность источника.
4. XCTest navigation: передать известный/неизвестный fragment и новую/старую страницу через существующий delegate; если `WKNavigationAction` нельзя создать публичным API, не добавлять тестовые production-крючки ради фиктивной проверки и выполнить реальный WebKit-тест на Mac. PDF XCTest проверяет использование актуального снимка и результат PDFKit; визуальная ширина/перенос, реальный клик, CSP, сноски, печать и закладки — отдельная Mac-приёмка.

Файлы после передачи владения: точечные `Preview/MarkdownRenderer.swift`, `Preview/MarkdownPreview.swift`, небольшое общее правило текста заголовка в существующем parser, при необходимости структура `MarkdownRenderedPage`, существующие renderer/preview/PDF XCTest. `MarkdownPresentationController`, FoldLayoutManager и редактор 09 не изменять параллельно. Новые build lists/строки согласуются с основным агентом; статус «реализовано» только после независимого review, а «проверено» — после реального запуска на Mac.
