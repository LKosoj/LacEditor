# 08: чистые операции над Markdown-таблицей

Статус: предлагаемый контракт до реализации. Это только текстовые операции, не оформление 09 и не пункты меню. Разработка без Mac разрешена; реальный запуск XCTest и приёмка интерфейса остаются отдельными незавершёнными проверками. Параллельно работают другие агенты. Разрешённые файлы для последующей реализации: `LacEditor/Services/MarkdownTableEditingService.swift` и `LacEditorTests/MarkdownTableEditingTests.swift`. Сборочные списки и интеграцию выполняет основной агент; новые зависимости не нужны.

## Контракт вызова и подключения

Использовать существующий результат `MarkdownFormattingEdit`: `range` — заменяемый диапазон исходной строки, `replacement` — вставляемый текст, `selectionRange` — абсолютный диапазон в строке после применения; всё в UTF-16 (`NSString`/`NSRange`). Предлагаемый API: `MarkdownTableEditingService.edit(in: NSString, selection: NSRange, command: MarkdownTableCommand) -> MarkdownFormattingEdit?`. Команда содержит создание с размерами, вставку до/после, удаление, перемещение на одну позицию и выравнивание; строка/колонка определяются по курсору. Вне подтверждённой таблицы, при некорректном выделении или неприменимой команде возвращается `nil`. Распознавание контекста и применение результата будущими командами должны использовать актуальный `NSTextView` и существующий цикл `shouldChangeText` → изменение → `didChangeText` с одной группой отмены: сервис не изменяет документ и не управляет интерфейсом. Интеграция через существующий путь форматирования — следующий отдельный этап, без него функциональность не считать доступной пользователю.

Сервис не принимает сырые координаты ячеек от интерфейса без подтверждения по текущей строке. В тестах применить каждую возвращённую замену к копии и проверить итоговую строку и допустимый курсор. Нативные таблицы 09 и точная привязка экрана к ячейке остаются отдельными задачами после образца 02.

## Распознавание и неизменность исходника

Использовать текущий cmark-gfm с расширением table как источник подтверждения границ таблицы и её контекста, чтобы не считать таблицей похожие строки внутри блока кода или другого синтаксиса. Позиции строк/табуляции и вложенных цитат/списков сопоставлять с исходным UTF-16 только там, где точность доказана тестом; при неоднозначности возвращать `nil`, не угадывать. Ячейки сопоставлять с исходными срезами, без разборки и повторной сериализации Markdown-разметки. Разделители искать с учётом экранирования и реального поведения cmark-gfm для последовательностей обратных кавычек и `|`; примеры внутри встроенного кода, включая разные длины кавычек, проверить непосредственно на этом же cmark. Нельзя просто игнорировать каждый `|` между кавычками: правило должно соответствовать фактическому разбору GFM. Непарные кавычки и нечётные/чётные обратные слеши тоже включить в примеры. Если точное соответствие не подтверждено, не изменять эту таблицу.

Заголовок и строка разделителей задают число колонок; короткие строки имеют отсутствующие пустые ячейки, лишние ячейки обрабатываются согласно фактическому cmark. Сохранить имеющийся исходный текст, пробелы, крайние `|`, inline-разметку и тип переноса; добавлять минимальный синтаксис только для затронутых ячеек. Для недостающих ячеек определить исходную точку вставки, не менять соседнее содержимое и не нормализовать таблицу целиком. Проверить операции на строках с табуляцией и без крайних `|`; если точное преобразование в конкретном контексте не доказано, вернуть `nil`. Для новой строки использовать перенос соседней строки, при создании таблицы — перенос текущего документа либо LF для пустого документа; CRLF сохраняется как единое окончание.

## Операции и крайние случаи

- Создание: вставка таблицы с заголовком, разделительной строкой и заданным числом пустых строк/колонок в допустимом месте; курсор в первой ячейке. Размер и поведение непустого выделения определяет будущая команда меню; сервис не заменяет произвольный выделенный текст без явного контракта. При вставке в непустой абзац до согласования возвращать `nil`.
- Вставка строки до/после выбранной строки данных; курсор в новой ячейке соответствующей колонки. Заголовок не переставлять с телом. Вставка колонки до/после — во всех строках включая заголовок и разделители, с пустыми ячейками; курсор в соответствующей новой ячейке.
- Удаление строки данных удаляет именно её. **Предлагаемое стандартное поведение последней строки данных:** остаются заголовок и разделитель, то есть корректная GFM-таблица с нулём строк данных; курсор переносится в ячейку заголовка той же колонки. Удаление заголовка отдельной командой строки не допускается.
- Удаление колонки убирает соответствующие ячейки и выравнивание. **Предлагаемое поведение последней колонки:** вернуть `nil`, поскольку удаление её превратило бы всю таблицу в не-таблицу и неявно удалило содержимое заголовка; отдельное удаление таблицы этим планом не вводится. Это явное предложение для согласования, не утверждение о поведении Typora.
- Перемещение строки данных вверх/вниз меняет её с соседней строкой данных; заголовок фиксирован. Перемещение колонки меняет содержимое и соответствующее выравнивание всех строк. Курсор переходит вместе с выбранной ячейкой; шаг за границы возвращает `nil`.
- Выравнивание колонки: стандартное, слева, по центру, справа — изменение соответствующей ячейки строки разделителей; остальные ячейки и содержимое таблицы сохраняются. Курсор остаётся в выбранной ячейке.

Выделение внутри одной ячейки и позицию курсора переносить вместе с ячейкой с учётом UTF-16; при вставке выбрать точку ввода в новой пустой ячейке. Выделение через несколько ячеек, границы таблицы или внутри строки разделителей до определения точной семантики не изменять (`nil`). При удалении ячейки курсор переводить в соседнюю сохранившуюся ячейку того же ряда, а при удалении последнего ряда — как описано выше. Никаких изменений за границами returned `range`.

## Проверки до передачи интеграции

1. XCTest на валидные и ложные таблицы, заголовок/разделитель, цитату и список, fenced-код, выделение в разных местах, крайние `|` и их отсутствие; сравнение с cmark для табов, пустых и отсутствующих ячеек и лишних ячеек.
2. Каждая операция в обоих направлениях и на границах; последняя строка/колонка; сохранение неизменённых ячеек, пробелов, встроенной разметки и переносов LF/CRLF, начало и конец файла. Проверка переноса выравнивания при перестановке колонок.
3. `\\|`, чётные/нечётные слеши, одинарные и кратные обратные кавычки, незакрытый кодовый фрагмент; китайский, emoji и составные символы, UTF-16 диапазоны замены/выделения. Проверить cmark-вывод до и после преобразования, чтобы ячейки не изменили смысл.
4. Зафиксировать неприменимость и неизменность входа при неверном диапазоне или спорном контексте; проверить все применимые операции на коротких строках. Тесты готовятся для Swift, здесь не объявляются запущенными. После интеграции отдельно проверить одну отмену и повтор через AppKit, IME и таблицы в интерфейсе на Mac.

Сравнение со спецификацией [GFM tables](https://github.github.com/gfm/#tables-extension-) подтверждает, что строк данных может не быть; спецификация и фактический cmark остаются источником поведения разделителей. Никаких заимствований кода Milkdown этот этап не предполагает.

## Уточнение по разбору cmark

Исследование исходного [table.c cmark-gfm](https://github.com/github/cmark-gfm/blob/master/extensions/table.c) показывает: разбиение строк на ячейки предшествует разбору inline Markdown; `\|` обрабатывается на уровне таблицы. Нельзя считать все разделители `|` внутри обратных кавычек текстом ячейки без проверки конкретной версии cmark. Точное соответствие вложенных цитат/списков, отсутствующих ячеек и координат UTF-16 пока не доказано; сервис и тесты ещё не реализованы. Нужен проверенный алгоритм преобразования, обеспечивающий сохранность исходной строки. Отсутствие Mac не является причиной прекращать реализацию.

## Подключение к существующим командам — миниплан до кода

Статус: предложено, ожидает рассмотрения; зависит от независимого ревью и исправлений первого этапа сервиса. Разрешённые файлы интеграции: `MarkdownFormattingService.swift`, только раздел `CommandMenu("Markdown 格式")` в `LacEditorCommands.swift`, `MarkdownFormattingServiceTests.swift`, `MarkdownFormattingInteractionTests.swift` и ранее назначенные два файла таблиц. Локализации и списки сборки меняет основной агент последовательно. Никаких новых путей редактирования или обработчиков `NSTextView` не добавлять.

1. `MarkdownFormattingCommand` уже имеет `Equatable`; добавить `case table(MarkdownTableCommand)` и обеспечить `Equatable` для `MarkdownTableCommand` и вложенного `MarkdownTableAlignment`, чтобы синтез компилятора оставался доступен. В `MarkdownFormattingService.edit` после общих проверок передать `.table(command)` в `MarkdownTableEditingService.edit(in:selection:command:)`, вернуть тот же `MarkdownFormattingEdit?` без изменения результата. В `actionName` возвращать локализованное название соответствующего действия из списка ниже, включая каждый вариант выравнивания; так системная отмена показывает осмысленное название.
2. В существующий `CommandMenu` добавить вложенное меню «Таблица». Создание 2 × 2 означает две колонки и две видимые строки: заголовок и одна строка данных, то есть `.table(.create(rows: 1, columns: 2))`. Остальные пункты передают существующие команды вставки, удаления и перемещения строк/колонок и вложенное меню выравнивания. Не добавлять диалог, горячие клавиши или отдельное окно. Сохранить общую существующую недоступность команд для не-Markdown и занятого документа; неприменимая операция возвращает `nil`, включая удаление последней колонки.
3. Существующий путь: `appState.formatMarkdown` → уведомление с ID документа → `EditorCoordinator.applyMarkdownFormatting` → `MarkdownFormattingService.edit` → `shouldChangeText` / замена / `didChangeText`, выделение и одна группа undo. Изменять `AppState`, координатор и реализацию применения не требуется. Сохранить их проверки активного редактора, языка, доступа, одной области выделения, незавершённого IME и актуальности версии/выделения.
4. XCTest службы: проверить через `MarkdownFormattingService` создание 2 × 2 и представительные операции над строкой, колонкой и выравниванием, точное выделение и `nil` для последней колонки/не-таблицы. Тесты логики всех операций остаются в `MarkdownTableEditingTests` и не дублируются целиком.
5. XCTest взаимодействия с реальным `LacTextView` по текущему примеру: команда создания в пустом документе, операция на таблице с Unicode, совпадение выделения, undo и redo одним действием в исходном и оформленном виде; недоступное редактирование, marked text и другой ID документа не меняют текст. Тесты готовятся без заявления о запуске; на Mac дополнительно проверить меню, реальный ввод и отмену.

### Ключи для локализации и названия undo

Вызовы `L10n.tr` используют следующие исходные китайские ключи; основной агент добавляет переводы в три существующих файла. Название каждого пункта одновременно используется как `actionName` соответствующей команды; дополнительных ключей для отмены не нужно.

| Ключ | Название по-русски | Команда |
|---|---|---|
| `表格` | Таблица | заголовок меню |
| `插入表格` | Вставить таблицу | `create(rows: 1, columns: 2)` |
| `在上方插入行` | Вставить строку выше | `insertRowBefore` |
| `在下方插入行` | Вставить строку ниже | `insertRowAfter` |
| `删除行` | Удалить строку | `deleteRow` |
| `上移行` | Переместить строку вверх | `moveRowUp` |
| `下移行` | Переместить строку вниз | `moveRowDown` |
| `在左侧插入列` | Вставить столбец слева | `insertColumnBefore` |
| `在右侧插入列` | Вставить столбец справа | `insertColumnAfter` |
| `删除列` | Удалить столбец | `deleteColumn` |
| `左移列` | Переместить столбец влево | `moveColumnLeft` |
| `右移列` | Переместить столбец вправо | `moveColumnRight` |
| `列对齐` | Выравнивание столбца | заголовок вложенного меню |
| `默认对齐` | Выравнивание по умолчанию | `align(.unspecified)` |
| `左对齐` | Выровнять по левому краю | `align(.left)` |
| `居中对齐` | Выровнять по центру | `align(.center)` |
| `右对齐` | Выровнять по правому краю | `align(.right)` |
