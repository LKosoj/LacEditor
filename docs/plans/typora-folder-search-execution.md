# 20: поиск по папке и быстрое открытие — миниплан backend

Статус: план до кода, только независимый backend. UI, подключение окна, проверки на Mac и полная задача 20 не готовы. Не добавлять постоянный индекс, базу, новую библиотеку, настройки или глобальный поиск. Теги остаются задачей после YAML из 14.

## Входы и ответственность

- Новый `Services/FolderSearchService.swift` получает нормализованный URL выбранного корня, запрос, признак учёта регистра и неизменяемые снимки уже открытых документов. Снимок содержит URL файла, `DocumentFileIdentity` и `DocumentTextSnapshot` с ID, текстом и revision (версией); сервис не обращается к AppKit или `EditorDocument`.
- Будущий владелец UI на главном потоке собирает каждый `synchronizedSnapshot()` для всех окон, сверяет актуальное расположение и идентичность и передаёт значения в фон. Сервис принимает только пути внутри корня по компонентам пути, не по строковому префиксу; снимки вне области не используются. Отдельно учитывать открытый файл внутри корня, который исчез с диска: его несохранённый снимок остаётся доступным для поиска.
- Один открытый документ имеет приоритет над дисковым содержимым того же файла. Если на входе ошибочно пришли различные документы с одной идентичностью и разными снимками, не выбирать один случайно: вернуть явную проблему для этого пути, оставить решение вызывающему коду. Одно и то же содержимое не выдавать дважды через разные пути одной идентичности.
- Два отдельных вызова: поиск файлов по имени/относительному пути и поиск текста. Оба выполняются вне главного потока вызывающим кодом, принимают проверку отмены; пустой запрос возвращает пустой результат без обхода. При отмене возвращается `CancellationError`, не частичная выдача как успех. Новая задача и номер поколения принадлежат будущему владельцу UI, не создаются как новый глобальный координатор.

## Обход и результаты

1. Обходить только выбранный корень и его настоящие вложенные каталоги, включая скрытые файлы без дополнительных фильтров. Не следовать символическим ссылкам-каталогам; символические ссылки на файлы могут быть показаны в быстром открытии как путь, но для поиска содержимого пропускаются с явной причиной: цель может находиться вне корня. Перед чтением проверять тип корня и компонентов пути свежими значениями, по примеру `FolderWorkspaceStore`; между проверкой и обращением остаётся обычная файловая гонка, атомарная защита от внешней подмены не заявляется. Ошибки каталогов/файлов и невалидный UTF-8 возвращать с URL и типом причины, не показывать как отсутствие совпадений.
2. Быстрое открытие сравнивает запрос с относительным путём файла (а значит и именем), учитывает переданный регистр, возвращает URL и относительный путь, не читает содержимое. Сортировка результата — естественный порядок относительных путей с устойчивым разрешением равенства по полному пути. Совпадающие имена в разных папках остаются отдельными строками. Дерево перечитывается по запросу, без постоянного индекса.
3. Текстовый поиск: для дискового файла строго `String(data:encoding: .utf8)`, без угадывания и диалогов; невалидный UTF-8 — отдельная причина пропуска. Для открытого документа используется только снимок. Совпадения — `TextSearchService.allRanges`, те же literal/caseSensitive и неперекрывающиеся результаты. Пустой запрос не ищется; диапазон — `NSRange` в UTF-16, текст совпадения и контекст — исходные подстроки. Контекст брать по `NSString.lineRange(for:)` для полного совпадения, включая многострочный запрос; хранить и диапазон контекста, и диапазон совпадения в документе. Не использовать `String.count` для координат.
4. Дисковый источник хранит `FileRevisionSnapshot` до и после чтения; при несовпадении не выдавать результат этого чтения, сообщить об изменении файла. Перед переходом повторно снять состояние и проверить сохранённый исходный фрагмент по диапазону на актуальном тексте; если файл изменился, удалён, стал ссылкой или фрагмент расходится — результат устарел и вызывающий код обновляет поиск. Снимок файла включает идентичность, дату и размер, а не полную контрольную сумму; совпадение этих полей и одного фрагмента не доказывает неизменность всего содержимого.
5. Источник открытого файла хранит documentID, revision и исходный фрагмент. Перед переходом владелец окна получает новый синхронизированный снимок, сверяет документ, путь/идентичность, revision, границы и фрагмент, затем открывает/активирует существующее окно и использует текущий путь выделения. Если документ закрыт, перемещён или изменён — результат устарел и поиск обновляется. Никакого чтения живого текста из фона.
6. Проверки отмены выполняются между каталогами, файлами и при поиске совпадений через имеющийся callback `TextSearchService.allRanges`; системное чтение и отдельный вызов `NSString.range` не обязаны прерываться. После каждого такого вызова снова проверить отмену. Смена корня, запроса, документов и закрытие окна требуют от UI отменить старую задачу и проверить свой ID/поколение перед публикацией и переходом; один только backend не может гарантировать это без подключения.

## API и проверка

Результат файлового поиска: корень, URL, относительный путь; результат текстового поиска дополнительно содержит диапазон, контекст, точный найденный фрагмент и источник (`open(documentID, revision, identity)` либо `disk(FileRevisionSnapshot)`). Общий ответ содержит результаты и отдельные проблемы с URL/причиной; порядок совпадений внутри файла — по позиции UTF-16. Функция проверки результата получает актуальный снимок открытого документа либо заново проверенный дисковый текст и состояние и возвращает current/stale, не делает переход и не создаёт UI. При невозможности прочитать файл — stale/причина, а не переход к старому диапазону.

Новый `LacEditorTests/FolderSearchTests.swift`: временная папка, вложенность, одинаковые имена, путь с Unicode/emoji, поиск имени и пути, относительные границы похожих корней; `中文😀` и составные символы до совпадения, CRLF и многострочное совпадение, регистр и поведение `TextSearchService`; открытый несохранённый снимок вместо диска и открытый удалённый файл, снимок вне корня, конфликт идентичности; изменённый/удалённый файл и изменённый открытый revision/фрагмент, отказ доступа и невалидный UTF-8; цикл/внешние символические ссылки и подмена до проверки. Детерминированная отмена в callback, независимые последовательные запросы/корни, отсутствие частичного успешного результата. Прикладную смену запроса и окна проверять только после UI-подключения; тест backend не доказывает корректную публикацию.

После согласования создать только два новых файла backend/tests; сборочные списки, скрипты, общие документы и локализации обновляет основной агент. Нужен независимый review, затем `swift test`/Xcode и ручная проверка Mac: права доступа, актуальный несохранённый текст в разных окнах, переход, большая папка и время отмены. До этого не называть 20 завершённой.

## Миниплан интерфейса и контроллера (до кода)

Граница этого этапа: новые `Views/FolderSearchView.swift`, при необходимости `Services/FolderSearchController.swift` и XCTest; `AppState`, `WindowManager`, `EditorDocument`, `SidebarLibraryView`, локализации и сборочные списки сейчас не менять. До интеграции самостоятельное представление не доступно пользователю и пункт 20 не завершён. Два выбора в интерфейсе — уже согласованные функции: быстрое открытие по имени/пути и поиск текста, не новые пользовательские настройки.

1. **Владение и состояние.** `@MainActor FolderSearchController` принадлежит текущей боковой панели/окну; получает выбранный root, предоставленные владельцем замыкания для снимков и перехода, и хранит запрос, выбранную функцию, результаты, проблемы, состояние выполнения и номер запуска. Смена root/запроса/функции и закрытие отменяет предыдущую задачу, очищает старые результаты и немедленно запрещает переход по ним; пустой запрос не запускает обход. Окончание фоновой задачи проверяет root, запрос, функцию и номер запуска после возвращения на главный поток. Поколение проверяется также при root A → B → A и повторении одинакового запроса.
2. **Снимки.** Только на главном потоке, после запуска явного поиска текста и до фоновой работы, инжектированный provider возвращает значения `FolderSearchService.OpenDocument` со всех окон: каждый — актуальный `synchronizedSnapshot()`, URL и `DocumentFileIdentity`. Координатор не удерживает `EditorDocument` и не читает его в фоне. Перед передачей результата на экран владелец ещё раз подтверждает актуальность открытых ID/revision/путей; если снимок устарел, результаты этого запуска снимаются и пользователь получает предложение обновить поиск. Входы документа не копируются на каждую клавишу. Переключение на быстрый поиск не требует снимков.
3. **Фон и отмена.** Контроллер запускает существующий `FolderSearchService.files/search` вне главного потока, передаёт проверку отмены, отображает loading и отдельные ошибки/пропуски с путём и причиной (включая невалидный UTF-8). Не считать отменённую частичную выдачу успешной. Не добавлять отдельный постоянный индекс и не читать содержимое файлов при быстром открытии. Точный пользовательский запуск — явно по Return/кнопке, чтобы не копировать снимки всех окон на каждую букву; изменение поля сразу аннулирует прошлую выдачу.
4. **Переход к открытому документу.** Перед действием проверить, что строка принадлежит текущей выдаче, root/query/generation совпадают. Provider повторно получает снимок нужного открытого ID, затем `FolderSearchService.isCurrent` проверяет ID, revision, путь, идентичность и фрагмент. Инжектированный переход должен активировать существующее окно и применить `EditorSelectionRequest` с проверенным диапазоном через текущий revealSelection; непосредственно перед применением на главном потоке владелец повторно проверяет ID/revision и исходный фрагмент. Если документ изменён, закрыт или перенесён — отказ и сообщение об устаревшем результате, без старого выделения.
5. **Переход к закрытому файлу.** Сначала в фоне `FolderSearchService.isCurrent` проверяет файл, затем владелец вызывает существующий `WindowManager.openFile` и ожидает фактического окончания его асинхронной загрузки, не считая открывающийся placeholder документом. В это время другой пользовательский ввод/поиск может отменить действие. После загрузки повторно проверить disk snapshot и получить на главном потоке `synchronizedSnapshot()` реально открытого документа; его идентичность и исходный фрагмент в точном диапазоне должны совпасть с результатом. Снова проверить root/query/generation и только после этого выполнить reveal. Если файл уже открыт в другом окне либо открылся с другим/несохранённым текстом, применять те же проверки реального документа; при несовпадении не переходить и предложить обновить поиск. Между проверкой и открытием возможна обычная файловая гонка; защита на основе состояния и фрагмента не является контрольной суммой файла.
6. **Инжектируемый контракт.** Провайдер снимков и проверка/переход выполняются на `@MainActor`; фон получает только Sendable-значения. Асинхронное открытие возвращает подтверждённый снимок загруженного документа или явный отказ, а само финальное выделение выполняет отдельный callback с expected ID/revision/фрагментом и возвращает успех только после повторной проверки. Production callback открытия обязан проверять отмену непосредственно перед фактическим открытием: контроллер после await может запретить только последующее выделение, а не отменить уже открытое окно. Быстрое открытие повторно проверяет принадлежность строки текущей выдаче и root, затем использует обычный путь открытия; диапазон ему не назначается. Простейший test double замыкает эти callbacks, отдельный production-фреймворк навигации не вводить.
7. **View.** Компактный раздел текущей `SidebarLibraryView` показывает выбранный корень, два выбора, поле запроса и запуск; строки быстрого поиска — относительный путь, строки текста — путь и контекст, доступный клавиатуре выбор; отдельно loading, пустая выдача и причины пропусков. Не подменять существующий фильтр библиотеки и поиск документа, не открывать отдельное окно. Предложить локализуемые строки основному агенту; реальные языковые файлы он обновит при интеграции.
8. **XCTest.** В новом `FolderSearchControllerTests.swift` с управляемыми callbacks проверить root A→B→A, запросы A→B→A, смену функции/закрытие, отмену до завершения и отказ устаревшей строки; провайдер вызывается на главном потоке только для поиска текста. Открытый документ: revision/фрагмент/ID после выдачи и перед reveal; дисковый: изменён до открытия и во время задержанной загрузки, другой открытый документ, late callback после смены запроса, UTF-16/emoji; невалидный UTF-8 и недоступные файлы видны как проблемы, совпадения других файлов остаются. Тесты доказывают контракт контроллера с подставными callbacks, а не настоящую работу окон. После интеграции отдельный XCTest на два реальных состояния окон и фактическое открытие/reveal; на Mac — панель, клавиатура, права, реальные файлы и производительность большой папки.

**Точки дальнейшей интеграции:** `SidebarLibraryView` размещает view для собственного `AppState.folderWorkspace.rootURL`; `WindowManager` предоставляет снимки всех своих документов и поиск/активацию по идентичности; существующий асинхронный `beginOpeningFile` требует подтверждённого сигнала загрузки для точного перехода. Конкретный минимальный способ ожидания загрузки определить при передаче владельцем файлов 19, без обхода имеющихся проверок и без изменения их сейчас. Сборочные списки и ключи локализации согласуются с основным агентом.
