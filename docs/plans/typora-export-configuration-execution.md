## Текущая база и принцип

`AppState.exportMarkdown(as:)` уже владеет сохранением, берет актуальный `synchronizedSnapshot`, использует общий lock документа и дважды сверяет источник/открытые документы с назначением. `PandocExportService.prepare/install` делает временный результат и установку на том же томе; PDF делегирован `MarkdownPDFExportService`. Сохранять эти пути, ошибки и отмену. Не давать пользовательским настройкам silently обходить защиту источника/открытых файлов или выдавать несвежий результат за новый. Экспортируемый снимок и настройки фиксируются **после** пользовательских окон и проверок; сам документ, dirty, selection и текстовый undo не изменяются.

## Общие настройки и пункты меню

### Предлагаемый контракт первого сквозного этапа — до изменений `AppPreferences`

Сохранять одно значение JSON в уже переданном `AppPreferences(defaults:)` под отдельным ключом `markdownExportConfiguration`, не в документах или сессии. Типы рядом с существующими настройками, без нового хранилища:

```swift
struct MarkdownExportConfiguration: Codable, Equatable {
    var profiles: [MarkdownExportProfile]
}
struct MarkdownExportProfile: Codable, Equatable, Identifiable {
    var id: String                 // постоянный; встроенные — "pandoc.<rawValue>"
    var name: String               // пользовательское название
    var enabled: Bool
    var writer: String             // имя writer Pandoc, пустое = выбор по расширению
    var extensions: [String]       // без точки, по порядку; [] = без ограничения панели
    var rawType: String            // начально пустой; неподдержанный вариант не угадывать
    var arguments: String          // строка пользовательского поля, не shell-команда
    var templatePath: String?      // явно выбранный читаемый файл
    var referenceDocumentPath: String?
    var epubTOCDepth: Int?         // nil = системное значение Pandoc; для EPUB UI предлагает 3
    var epubCoverPath: String?
}
```

Модель относится только к изменяемым Pandoc-пунктам; неизменяемые HTML/PDF/PNG остаются существующими командами, без псевдопрофиля и без потери текущего HTML. HTML без оформления пока отсутствует и остаётся обязательным пунктом 24. В новых настройках доступны изменение названия/порядка/включения/удаления и добавление Pandoc-профиля, включая заполнение writer, расширений и перечисленных полей. `@Published var markdownExportConfiguration` записывает JSON через текущий `UserDefaults`, общий экземпляр остаётся общим для всех окон. Для отсутствующего ключа состав и порядок Pandoc берутся из `PandocExportFormat.allCases`, исключая HTML/PDF, с прежними writer/extension/title, `enabled=true`, пустыми rawType/arguments и nil остальных полей; PNG и HTML/PDF остаются на своих существующих путях. Сохранённый пустой список намеренно пустой и не восстанавливает удалённые пункты. Новые пользовательские ID — UUID в строке, повторы ID при чтении считаются ошибочными записями, не объединяются с другим профилем.

Декодирование каждого элемента независимо: неизвестный тип/неверные поля или ID не сбрасывают соседние валидные элементы и остальные настройки; сырой JSON такой записи сохраняется неизменённым при редактировании других профилей и показывается в настройках как неподдерживаемая запись с возможностью явного удаления. Неизвестные поля известного профиля также сохраняются при его изменении. Неверный JSON целиком не перезаписывается автоматически: использовать default только для текущего запуска и показать ошибку настроек до их явного сброса. Неизвестные записи в меню не исполняются. Это поведение сохраняет данные от более новой версии, а не молча стирает их; минимальная реализация — покомпонентное чтение/слияние через Foundation JSON, не общий механизм миграций.

**Аргументы и границы записи.** Текст arguments разбирать как список аргументов: пробелы вне одинарных/двойных кавычек разделяют, кавычки объединяют аргумент и не попадают в результат; `\\` экранирует следующий символ вне одинарных кавычек; пустые кавычки создают пустой аргумент, незакрытая кавычка/конечный `\\` — понятная ошибка. После разбора `${...}` подставлять внутрь того же аргумента, не выполнять shell и не создавать новые аргументы из значения. Имена с `currentPath`, `currentFolder`, именами файлов, `outputPath`, именами результата, `today` и scalar YAML — по документации Typora; `outputPath` обозначает выбранный пользователем конечный путь только как значение, но не разрешает обойти контролируемый output. Невычислимые значения, переменные страниц в Pandoc и неподдержанные YAML-структуры дают явную ошибку; пустая строка YAML остаётся пустой. Снимок текста/переменных берётся после диалога, значение даты фиксируется один раз.

На первом этапе дополнительные аргументы принимаются только из явного набора документированных параметров формата: `--wrap=auto|none|preserve`, `--columns=<positive integer>`, `--eol=lf|crlf|native`, `--tab-stop=<positive integer>`, `--ascii`, `--toc`, `--toc-depth=<positive integer>`, `--shift-heading-level-by=<integer>`, `--number-sections`, `--top-level-division=default|section|chapter|part`, `--variable=KEY:VALUE`, `--metadata=KEY:VALUE` (отдельные значения после `=` не разбиваются). Если выбранная опция имеет отдельное поле модели, повторное задание противоречивых значений отклонить. Все неизвестные опции, позиции без опции и краткие формы явно отклоняются: включая `-o`/`--output`, `-f`/`--from`, `-t`/`--to`, `--`, `--defaults`, `--log`, `--extract-media`, `--filter`, `--lua-filter`, `--pdf-engine` и `--data-dir`. Это ограничение первого этапа, не выполнение обещания Typora поддержать все аргументы; оставшийся набор нужно реализовать отдельно после определения побочных действий. Запрет управляет Pandoc-аргументами, но не является песочницей для произвольной внешней команды.

Сервис сам задаёт входной временный снимок, output во временном файле и `--from/--to`; путь назначения определяется только save panel и проверкой `conflicts/install`. При пустом writer временный output должен иметь расширение выбранного назначения для определения формата Pandoc; неизвестный writer/extension приводит к ошибке процесса без установки. Template/reference/cover передаются отдельными аргументами по выбранным путям, без подстановки в командную строку shell; reference только для совместимого DOCX/ODT, глубина/cover только EPUB. Исходные файлы выбранных шаблонов не изменяются.

Для YAML и fallback title нужен настоящий разбор данных из снимка: текущий parser 14 распознаёт и маскирует front matter, но в просмотренных путях не предоставляет значения YAML. Предлагается первая стадия встроенного Pandoc `gfm+yaml_metadata_block → json`, затем тот же AST (дерево документа) → выбранный writer: title из снимка, включая явно пустое значение, имеет приоритет; имя файла задаётся только при отсутствии title. Из JSON разрешать скалярные метаданные и вложенный путь `${a.b}`; остальные формы выдавать как неподдерживаемые, а не преобразовывать угадыванием. Обе стадии используют только встроенный Pandoc и временные файлы; реальные возможности 3.13 и сохранность изображений/метаданных требуют XCTest на Mac. Самостоятельных внешних команд в рабочей сессии не запускать.

1. В существующих `AppPreferences.swift`/`SettingsView.swift` добавить Codable-модель только для настроек экспорта: упорядоченные пункты с устойчивым ID, пользовательское название, включение и конкретный тип; отдельные параметры каждого пункта. Старые UserDefaults без записи декодируются в прежние существующие пункты; неизвестный/повреждённый вариант не ломает остальные настройки. Не хранить последнюю операцию внутри пользовательского Markdown или в сессии. Изменения списка/названий видны в существующем меню `LacEditorCommands.swift`. Typora оставляет HTML/PDF/Image основными неизменяемыми пунктами, остальные разрешает переименовывать, менять порядок, удалять и добавлять из предлагаемых шаблонов; порядок/default требуется сверить с фактическим приложением на Mac.
2. Общая начальная папка выбора — автоматическая, рядом с текущим файлом или явно выбранная пользовательская; это только стартовое значение `NSSavePanel`, пользователь всегда может выбрать иное. Несохранённый файл при варианте «рядом» использует обычный системный default, не создаёт фиктивный путь. Для успешного экспорта настройка может открыть Finder или результат; после ошибки показывать диагностику. Никакого автоматического внешнего вызова без пользовательской настройки.
3. Последний **успешный** экспорт хранить в текущем окне и для конкретного document ID: тип/снимок конфигурации и фактическое назначение, не только индекс изменяемого списка. Повтор с прежними настройками вновь спрашивает путь; отдельная явная команда повтора с перезаписью использует прежний путь. Каждый раз заново получать текущий текст, проверять open-document/source-conflict и существующие внешние изменения назначения, готовить отдельный временный результат, устанавливать только после успеха. Смена/удаление документа, ошибка и отмена не превращают новый экспорт в успешную историю; перенос документа между окнами не переносит историю исходного окна. Не обещать повтор при закрытии/новом процессе.

## Pandoc: пользовательские форматы и шаблоны

- Расширить существующий export descriptor вместо добавления новых `PandocExportFormat` для каждого из сотен вариантов: имя writer, предпочтительные расширения, raw type, опции и необязательный template/reference-doc. Конкретный writer проверяется по поставляемому 3.13 и через фактический процесс, пустой `--to` определяется по выбранному расширению согласно Pandoc. Недоступный writer или нераспознанное расширение — понятный отказ, не fallback на соседний формат. Сохранить стандартные enum/сопоставления и добавить custom пункт только по явной настройке; DokuWiki и Org не выдавать за стандартные пункты Typora.
- Типовые варианты: другие wiki через writer 3.13; Markdown (`gfm`, `commonmark`, `markdown` и документированные варианты), line wrapping/width, end-of-line, tab/indent и ascii/unicode через соответствующие поддержанные опции; RevealJS через `--to=revealjs` и явно определённые ресурсы. RevealJS часто требует JS/CSS и может обращаться к сети: не обещать автономную презентацию и не загружать CDN/новую библиотеку автоматически. Нативный экспорт показывает реальные ограничения до принятия результата.
- `raw type` должен воздействовать на доказанные элементы Typora, а не заменять GFM-строку произвольной регулярной заменой: минимум `[toc]` для mediawiki/latex по исходному источнику, затем остальные подтверждённые 12–15 элементы. Нынешний `--from=gfm` не является типоровским AST (деревом документа); неизвестные синтаксис и стили остаются исходным текстом/явной потерей. Нельзя объявить полную совместимость raw type, пока конкретные элементы и обе стороны renderer/export не проверены.
- `--template` и DOCX/ODT `--reference-doc` (документ-образец стилей) принимают явно выбранный файл; проверить формат, чтение и ошибку Pandoc; исходник шаблона не записывать. EPUB: глубина оглавления, cover-image и YAML-метаданные, в том числе относительные ресурсы относительно документа; fallback для несохранённого источника явный. Не добавлять выбор CSS-темы. Формулы Word/MathJax и подписи/номера — проверять как форматные ограничения, не утверждать точную семантику на всех writer.
- Сейчас экспорт всегда задаёт `--metadata title=имя`, а Pandoc 3.13 отдаёт CLI приоритет над YAML. После 14 разбирать YAML из того же снимка: документный title сохраняется; имя документа применяется лишь если title отсутствует. Пустой явно заданный title отличается от отсутствующего. Поля author/date/cover и другие разрешённые ключи должны доходить до формата без подмены AI-метаданными. Импорт `--standalone` и метаданные 22 остаются отдельной задачей с тестами, не менять их автоматически здесь.
- Произвольные дополнительные аргументы Typora должны сохранять кавычки/пробелы/Unicode и `${...}` после подстановки. Для Pandoc использовать `Process.arguments` как массив, а не интерполяцию shell. Определить лексический разбор кавычек и ошибок; значения переменных подставляются **внутри отдельного аргумента**, не порождают новых аргументов. При пустой или неизвестной переменной следовать задокументированным правилам Typora и показать отказ, где значение нельзя вычислить; не угадывать путь несохранённого файла. Встроенные `--from/--to/--output` и пользовательские конфликтующие опции требуют явной семантики: они не должны направить запись мимо подготовленного временного файла. Не заявлять поддержку всех произвольных аргументов до решения этого конфликта; filters/templates могут иметь собственные побочные действия.

## HTML, PDF и изображение без CSS-тем

- HTML со стилями приложения и HTML без стилей — отдельные пользовательские результаты; согласовать применение текущих cmark/рендеринга 09–15 вместо слепой подмены Pandoc. Опциональное оглавление и вставки head/body, а также `append-head`, `append-body` и `*-extra` из YAML при соответствующем разрешении — требования 25.4. Вставка пользовательского HTML/скриптов не равнозначна CSS-теме и должна оставаться явно настроенной функцией; текущая CSP preview не доказывает экспорт. Подстановка YAML-переменных в HTML должна сохранять экранирование соответствующего контекста, не запускать код при предварительном просмотре. Правила Typora различают глобальные значения и документные переопределения.
- PDF/печать и экспорт изображения разрабатываются в задаче 23: page size/custom size/margins, top-heading и footnote page breaks, header/footer с `${pageNo}`/`${pageCount}`, title/author/creator/subject/keywords/tags, bookmarks и HTML append. PDF через WebKit-печать ещё не доказывает корректное сопоставление заголовков страницам или системные колонтитулы; их надо реализовать и проверить, не вычислять страницы по приблизительным DOM-координатам. Доступный LaTeX/Pandoc PDF engine из 25.4 остаётся отдельной явной пользовательской возможностью, не заменяет уже встроенный PDF без LaTeX.
- Изображение: параметры ширины/шрифта и качества относятся к 23; длинный документ должен либо корректно записаться, либо дать явную ошибку до установки, без усечения и повреждения старого файла. Текущая согласованная работа 23 выбирает фактический системный API и проверяет пиксели на Mac. Не добавлять темы или автоматические CDN.

## Пользовательская команда и граница безопасности

Typora также описывает отдельный шаблон **custom command**: команда, возможная save panel, расширения, вывод stdout и детали ошибки. Это явное требование матрицы 01, но произвольный процесс сам может читать/менять любые файлы, игнорировать переданный output и запускать другие программы. Предложение для отдельного решения: явно созданный пользователем пункт с показом команды и предупреждением о её полном доступе; подставлять документный снимок и временный output как отдельные аргументы, при успехе проверять/устанавливать ожидаемый результат существующим путём, показывать stdout/stderr и не делать вид, что удалось запретить процессу побочные действия. Команды с shell-синтаксисом, отсутствие save panel и формат `${outputPath}` необходимо согласовать отдельно: без этого нельзя одновременно гарантировать Typora-совместимость и защиту всех пользовательских файлов. Никакой такой процесс сейчас не запускать; соглашение на общую реализацию Pandoc не является выбором сторонней программы.

### Оставшийся контракт raw type, аргументов и пользовательских команд — до кода

**Raw type.** Официальный пример Typora ограниченно доказывает две подстановки: отдельный `[toc]` в исходнике даёт `__TOC__` для mediawiki и `\\tableofcontents` для latex. Предлагаемый минимальный этап: на том же неизменяемом снимке получить подтверждённые cmark диапазоны только отдельных верхнеуровневых маркеров, как существующее оглавление; в *временной копии входа* заменить их уникальными маркерами задания, затем в Pandoc JSON AST (дереве документа) заменить только соответствующие отдельные абзацы на `RawBlock` с format `mediawiki` либо `latex`. Проверить, что все сгенерированные маркеры найдены ровно по одному, иначе явно отказаться. Не распознавать маркеры в коде, экранированный `\\[toc]`, цитаты, списки, ссылку или строку с другим текстом по совпадению содержимого AST: после обычного разбора эти разные исходники могут выглядеть одинаково. Оригинал, выделение и undo не изменяются. Остальные raw type/элементы остаются задачей 25.4, а не имитируются текстовой заменой. XCTest встроенного Pandoc: оба writer и output, несколько маркеров, Unicode/CRLF, код/escape/ссылки/вложенные блоки, совпадение пользовательского текста с похожим маркером, снимок с несохранённым изменением; реальный 3.13 и визуальное сравнение на Mac.

**Все Pandoc-аргументы.** Typora заявляет все дополнительные параметры Pandoc, тогда как текущий ограниченный набор — только первый этап. Минимальная дальнейшая реализация: документированные опции преобразования передавать как `Process.arguments` с сохранением порядка и повторов; поддержать обе документированные формы значения (`--name=value`, `--name value`, краткие формы), отдельное экранирование и подстановку YAML после разбиения на аргументы. При неизвестной или отсутствующей переменной — видимая ошибка; пустое значение YAML сохраняется. Примеры отдельно покрывают кавычки, переносы, Unicode, пробелы и `${...}` внутри значения, а не выполняют shell. Полный каталог опций и их кратких форм сверять с bundled 3.13; ошибка Pandoc не превращается в успешный экспорт.

`-f/--from`, `-t/--to`, `-o/--output`, позиционные входы и `--` конфликтуют с фиксированными снимком/форматом/временным результатом. Для них требуется согласовать либо явное сообщение о конфликте, либо нормализацию в те же контролируемые значения с отказом несовпадающего ввода; молча переписывать выбранный исходник или назначение нельзя. `--defaults` может содержать не только параметры, но и входные/выходные пути; `--log` и `--extract-media` пишут отдельные файлы; фильтры, Lua writer и PDF engine запускают пользовательский код. Их нельзя честно считать безопасными только потому, что последний `--output` указывает во временный файл. Для полного Typora-покрытия нужно отдельное решение о разрешённых побочных файлах и явном пользовательском запуске таких параметров, с пояснением в интерфейсе; первый allowlist не является полной реализацией. Pandoc прямо указывает, что `--sandbox` не ограничивает фильтры и PDF-движок ([3.13 manual](https://github.com/jgm/pandoc/blob/3.13/MANUAL.txt), [Lua filters](https://pandoc.org/lua-filters.html)); не объявлять его защитой чужого кода.

**Явный пользовательский процесс.** Пользователь выбрал shell-совместимость с Typora; точный контракт заменяет прежнее предложение прямого вызова программы и приведён ниже. Нельзя обещать отсутствие побочных действий и одновременно выполнить произвольную пользовательскую команду. В этой рабочей сессии сторонние команды не запускаются.

### Уточнение пользовательской команды после выбора shell — до кода

Для совместимости с Typora пользователь явно создаёт пункт **команды**; только по его выбору запускается `/bin/zsh -c <command>`, включая предусмотренные самим пользователем `&&`, каналы и перенаправления. Существующие Pandoc-профили по-прежнему вызывают встроенный Pandoc массивом аргументов без shell. Рядом с полем команды постоянно написать: «Команда выполняется с правами пользователя и может читать и изменять файлы». Это объяснение, а не новая панель подтверждения или обещание песочницы. Сам shell и вызванный им код могут самостоятельно выбирать пути и менять открытые файлы; защита приложения относится к **его собственной** установке результата и не может ограничить чужую программу.

Минимальная совместимая модель: расширить текущий `MarkdownExportProfile` необязательными `kind` (`nil`/`"pandoc"` для прежних записей, `"command"`), `command: String?`, `commandDestination: String?` (`"file"`, `"folder"`, `"none"`), `showCommandOutput: Bool?`; существующие `id`, название, enabled и extensions используются общим меню и порядком. Добавление пользовательской команды явно создаёт `kind="command"`, пустую команду, `file`, false; ранее неизвестный kind всё так же сохраняется неподдерживаемой записью. Неиспользуемые Pandoc-поля у команды остаются пустыми, не исполняются. Настройки и меню добавляют/меняют/перемещают/удаляют её в существующем списке; успешный повтор в текущем документе и окне сохраняет снимок команды и выбранное назначение аналогично остальным профилям. Режим folder показывает `NSOpenPanel` для папки, none не показывает save panel, file использует текущую save panel и предпочтительные расширения. Закрытие/смена документа и generation (номер запуска) проверяются после панели и после процесса.

**Точная подстановка без подстановки кода из данных.** Команда сама остаётся shell-текстом, но значения не вставляются в него как исходный текст. Для каждого `${имя}` сформировать уникальное служебное имя переменной окружения `LAC_EXPORT_<nonce>_<index>`, присвоить ему точное значение и подставить в исходник ссылку на эту переменную:

| Положение placeholder | Подставляемый фрагмент |
| --- | --- |
| Вне кавычек | `"${LAC_EXPORT_…}"` |
| В двойных кавычках | `${LAC_EXPORT_…}` внутри существующих кавычек |
| В одинарных кавычках | закрыть `'`, вставить `"${LAC_EXPORT_…}"`, открыть `'` без пробелов |

Значение из окружения zsh не выполняется повторно как shell-код; двойные кавычки сохраняют пробелы, кавычки, `$`, обратные кавычки, Unicode и переносы как часть одного аргумента. Разбирать состояния unquoted/single/double и обратный слеш; экранированный `\\${…}` остаётся буквальным текстом. Переменные приложения: `${inputPath}` — временный файл со **снимком**, `${outputPath}` — временный файл при file, выбранная папка при folder, недоступен при none; `${outputFileName}`/`${outputFileFullName}` отражают выбранное конечное имя, остальные `current*`, `today` и YAML scalar — как в Pandoc-профиле. `${currentPath}` означает фактический сохранённый путь Typora, а не снимок: чтобы экспортировать несохранённые правки, команда должна использовать `${inputPath}`. Неизвестное имя, недоступный путь, NUL в значении, незакрытые кавычки/escape — видимая ошибка до запуска.

Первый этап допускает подстановку в обычных аргументах, кавычках и целях перенаправления. Если команда содержит placeholder и одновременно неподтверждённые конструкции shell (например, here-document, `$()`, обратные кавычки, `$'…'`, арифметические выражения или неоднозначный комментарий), отказаться **от всей команды до запуска**: даже такая конструкция перед placeholder может изменить контекст последующих кавычек. Сами такие конструкции без переменных приложения могут выполняться как заданная команда. Это ограничение остаётся незавершённой частью полной совместимости Typora, а не тихой интерпретацией. Реализация не должна определять quote context простым подсчётом кавычек в неизвестном синтаксисе; неподтверждённый случай отказывается. Нужен отдельный дальнейший проверенный синтаксический охват, а не общий shell parser framework.

Файл input создать в закрытом временном каталоге; для file предварительно проверить источник/документы всех окон, сохранить ревизию назначения и выдать команде путь ещё не существующего временного output на том же томе. После успешного завершения проверить, что output — обычный файл, заново сверить документ/отмену, открытые пути и ревизию назначения, затем `install`; при ошибке или отмене удалить временное только после выхода процесса и не менять собственным кодом конечный файл. Для folder/none действия являются побочным результатом пользовательского процесса: не изображать атомарность или откат. Stdout и stderr писать в отдельные временные файлы, чтобы заполнение pipe (канала) не блокировало работу; при ошибке всегда показать stderr, по выбору показать stdout. Закрытие окна отменяет применение, но очистка ждёт фактического завершения процесса; не обещать прекращение shell-потомков без подтверждённого системного механизма. Историю помечать успешной только после нулевого exit и, для file, успешной установки.

**Исправление отмены пользовательского shell.** Согласовано заменить только запуск `/bin/zsh` на системный `posix_spawn` с `POSIX_SPAWN_SETPGROUP` и группой 0: собственная группа создаётся при запуске, до выполнения shell. Не вызывать `setpgid` после старта: между запуском и сменой группы дочерняя команда может успеть породиться. Задать через file actions рабочую папку, stdin `/dev/null`, stdout/stderr существующими файлами; сохранить точные `argv` и окружение с переменными. Проверять код каждого системного вызова, освобождать все указатели/дескрипторы; `waitpid(WNOHANG)` с обработкой EINTR ожидает лидера без блокирования основного потока. При отмене, пока лидер ещё не получен через `waitpid`, послать `SIGKILL` только группе этого задания, дождаться лидера до очистки и вернуть `CancellationError`. После получения лидера через `waitpid` повторный сигнал группе небезопасен: идентификатор может использоваться заново; если оболочка уже завершилась, оставленные ею фоновые процессы не гарантируется остановить. Проверка отмены также до spawn и после завершения. Успешный exit проверять как нормальное завершение, а не считать сигнал нулевым кодом. Изолированно запущенные пользователем процессы, которые сами выходят из группы, а также уже совершённые побочные действия откатить нельзя; не обещать это. Pandoc для YAML сохраняет собственный прежний Process-путь и отмену.

XCTest: обычная оболочка создаёт вложенную `/bin/sh`, которая после задержки записала бы marker; отменить после доказанного старта и проверить отсутствие marker, завершение лидера, удаление временных каталогов и неизменность destination. Отдельно сохранить тесты argv, пространства имён переменных, stdout/stderr, рабочей папки и exit. На Mac проверить реальную системную группу; тесты не запускать на текущем host. Используется штатный API Darwin, без нового пакета/общего менеджера. См. [Apple `posix_spawn`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/posix_spawn.2.html).

XCTest: чистые проверки всех трёх контекстов для значений `a b`, `'`, `"`, `$()`, обратных кавычек, переводов строки и Unicode; эскейп и отказ неясных контекстов/неизвестных переменных; на Mac отдельный тестовый zsh с безопасным `printf` проверяет фактический argv и отсутствие созданного файлика от значения-инъекции. Тесты file/folder/none используют временные каталоги и локальный тестовый скрипт, проверяют snapshot, подмену output временным путём, возврат кода, stdout/stderr, конфликт/изменение цели, повтор и поздний выход; не запускать реальные команды пользователя в этой рабочей сессии. Файлы: AppPreferences, SettingsView, AppState, LacEditorCommands, новый небольшой `Services/CustomMarkdownExportService.swift` и XCTest; о новом source сообщить владельцу сборочных списков. Общий Clipboard helper и renderer не менять.
