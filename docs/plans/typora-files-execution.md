Его [руководство версии 3.13](https://github.com/jgm/pandoc/blob/3.13/MANUAL.txt) перечисляет четыре writer (преобразователя выходного формата), а [исходное сопоставление расширений](https://github.com/jgm/pandoc/blob/3.13/src/Text/Pandoc/Format.hs) сопоставляет `.wiki`, `.rst`, `.textile` и `.opml` соответствующим форматам. В приложении формат явно задаётся через `--to`, поэтому расширение имени само по себе не определяет writer. Проверка действительно поставленного исполняемого файла на Mac остаётся обязательной.

| Добавить в `PandocExportFormat` | Заголовок меню `title` | `fileExtension` | `writer` |
|---|---|---|---|
| `mediawiki` | `MediaWiki` | `wiki` | `mediawiki` |
| `rst` | `RST` | `rst` | `rst` |
| `textile` | `Textile` | `textile` | `textile` |
| `opml` | `OPML` | `opml` | `opml` |

В текущем коде `ForEach(PandocExportFormat.allCases)` в `LacEditorCommands.swift` уже создаёт пункты меню, а `AppState.exportMarkdown` использует `fileExtension` для предлагаемого имени. Потому добавление четырёх случаев и специальных значений `title` и `fileExtension` достаточно; `writer` для всех четырёх совпадает с `rawValue`, существующий default пригоден. Сохранить `--from=gfm`, `--standalone`, метаданные заголовка и существующую подготовку, проверку конфликта источника/открытых файлов и установку результата. Не заявлять, что эти четыре текстовых формата сохраняют изображения как встроенные файлы или обеспечивают полное соответствие 24/25.4.

Проверки в `PandocExportTests.swift`:

1. Проверить для каждого случая точные `title`, `fileExtension`, `writer` и присутствие в `allCases`, чтобы подтвердить параметры и построение пунктов меню. Проверить сохранение состава прежних вариантов в `allCases`; свойства прежних вариантов не изменялись.
2. На Mac выполнить XCTest с `PandocExportService.findPandoc()` и настоящим встроенным Pandoc, как в существующих тестах: для каждого формата создать файл из GFM с Unicode и заголовком/вложенным пунктом, проверить непустой результат и признаки формата (для OPML разобрать XML и проверить структуру `opml`/`outline`, для остальных — содержимое и синтаксис соответствующего формата). Учитывать реальные правила преобразования OPML: не требовать сохранения произвольных элементов Markdown, не поддерживаемых этим форматом. Не привязываться к случайным пробелам или всей строке вывода.
3. В тесте убедиться, что исходный файл и заранее существующий файл назначения не меняются на этапе подготовки; удалить только созданные временные данные. Существующие тесты отдельно проверяют снимок, конфликты, отказ процесса и установку результата; их поведение не менять.
4. На Mac выполнить подготовку Pandoc через `sh Scripts/prepare-pandoc.sh`, затем `swift test` с результатом для `PandocExportTests`; проверить четыре пункта меню и реальные файлы в подходящем просмотрщике. Сохранить команду, версию Pandoc и результаты. Запуск Linux не заменяет тест поставленного macOS-бинарника; сейчас `swift` и `xcodebuild` здесь отсутствуют, поэтому фактические результаты, сборка и интерфейс не подтверждены.

Реализация: четыре значения добавлены в существующий enum; тесты проверяют соответствие свойств и реальное преобразование с сохранностью файлов, включая XML OPML. Тестовый процесс-заглушка не добавлялся. Проверки Swift и встроенного Pandoc пока не запускались: требуется Mac.
