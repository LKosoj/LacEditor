# 25.6: строгий и свободный разбор Markdown

Функция прямо входит в исходный пункт 25.6. Основание — [два правила Typora](https://support.typora.io/Strict-Mode/): пробел после маркера заголовка и достаточный отступ содержимого списка. Предварительный подробный план подготовлен GPT-6.1-Terra `native_execution`, независимо рассмотрен `blocks_execution` и `files_execution`.

1. Использовать существующий снимок настроек разбора (syntax snapshot), добавить в него сохраняемый `markdownStrictMode`. Значение по умолчанию true сохраняет прежнее поведение cmark. Передавать один снимок редактору, оглавлению, предпросмотру, Copy, командам форматирования, переходам по ссылке на раздел (anchor) и экспорту. При изменении настройки не переписывать документ, не менять признак несохранённости (dirty) и историю отмены; фоновые результаты сверяют также актуальность syntax.
2. Для свободного разбора `###Header` использовать публичную функцию расширения библиотеки разбора Markdown — callback cmark. Проверочный пример на C показал, что начало heading у первого байта текста сохраняет правильные позиции TEXT/strong/math. Исправлять только подтверждённый диапазон владельца в существующей локальной карте Source — таблице позиций исходника, а не вводить общий кеш или обращение к закрытому устройству библиотеки. Обычные Setext-заголовки, то есть заголовки с подчёркивающей строкой, `###Header` над `---` не теряют буквальные символы #.
3. Для двух описанных правил списка использовать публичное перемещение существующих узлов. Проверять исходные маркеры, реальные отступы строк, пустой промежуток, вид списка, начальный номер и разделитель, порядок и непересечение диапазонов. Обновлять диапазоны нового списка и расширенных родительских узлов в той же Source-карте; `range`, `wholeLines` и `firstPosition` используют исправленные значения. После собственного переноса допускается только доказанное объединение непосредственно соседнего совместимого нумерованного списка, чтобы native и Pandoc не расходились. Элемент задачи с флажком (tasklist) отличается строковым типом и не переносится как обычный item без подтверждения.
4. Экспорт использует только точечные подстановки маркеров и отступов в отдельной временной копии через существующую подготовку снимка. Сохранять оригинал YAML, Unicode/CRLF, служебные маркеры формул и пробелов, изображения, корневые пути ресурсов и метаданные. Документ, текущий текст редактора и его кодировка не нормализуются. Полная пересборка документа через CommonMark отклонён: фактические пробы показали изменение предупреждающих блоков и нижних индексов. Новый анализатор Markdown, собственная копия библиотеки и общий универсальный преобразователь не добавляются.
5. Подключить один запланированный переключатель (Toggle) к существующей настройке после проверки потребителей; прежнее значение по умолчанию true не менять. Использовать три локализации без дополнительных пользовательских режимов.
6. Проверки Swift: default/restore, обе формы заголовка, Unicode/CRLF и YAML, code/escape/Setext, два и три пробела в документационных списках, соседний список и настоящий разделитель, tasklist, Source ranges, Copy/formatting/undo и актуальность anchor. Экспортные fixtures используют реальный Pandoc 3.13 и подставной PDF engine, в том числе без формул. Они не доказывают качество PDF настоящего движка.

Код checkpoint подключён, оба независимых повторных review конкретных открытых статических дефектов не нашли. Публичные C-probes на закреплённом cmark и отдельные Pandoc-пробы подтвердили структуру документационных примеров. `git diff --check` чист. Неподтверждённые сложные списки и заголовки с неоднозначной tab-позицией сохраняют прежний строгий разбор. Swift/macOS frameworks здесь отсутствуют: компиляция, XCTest, реальный интерфейс, TextKit/WebKit, undo/IME и встроенный Pandoc требуют Mac.
