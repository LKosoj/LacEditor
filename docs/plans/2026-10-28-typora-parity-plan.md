# LacEditor: редактирование Markdown и возможности Typora

Дата анализа: 28 октября 2026 года.

Статус: выбран третий вариант — развивать нативный LacEditor и заимствовать конкретные решения Milkdown. Пользователь поручил выполнение полного плана без CSS-тем, с предварительным агентским планированием, разработкой, независимым ревью и тестами на Swift. Начата подготовка примеров, XCTest и независимых частей реализации. Текущие результаты и ограничения указаны в разделе 11; наличие плана или кода не означает готовность функции. Анализ исходников не заменяет запуск на Mac.

## 1. Цель и границы

Дать возможность писать и править Markdown непосредственно в оформленном документе: заголовки, списки, таблицы, изображения, формулы и диаграммы видны на своих местах; обращение к элементу позволяет изменить его содержимое. Файл остаётся обычным Markdown. Исходное представление доступно для точного редактирования.

Целевой объём — весь функционал Typora, описанный в этом документе и перечисленных источниках, включая расширенные функции раздела 25, за исключением CSS-тем. Поддержка, импорт и совместимость CSS-тем исключены по запросу пользователя. Остальные описанные функции обязательны для завершения плана, а не список необязательных идей. Уже работающие возможности LacEditor входят в приёмку; существующие функции сохраняются. Это реализация пользовательских действий, а не копирование закрытого кода Typora или её фирменного оформления.

Разработка не включает новые AI-функции, облачную синхронизацию документов, собственный сервер, учётные записи LacEditor, магазин расширений, другие операционные системы или замену системы окон. Пользовательская загрузка картинок в выбранный внешний сервис входит в задачу 25.2; это не синхронизация документов. Платформенные функции Typora для Windows/Linux заменяются соответствующими действиями macOS там, где это применимо.

Полного совпадения нельзя объявить по одному переключателю оформления. Для каждого пункта ниже нужны реализация, проверка и явный статус. Сборка, ручной ввод и приёмка требуют macOS 26+; текущая рабочая среда — Linux, Swift и Xcode отсутствуют.

В задаче 01 составляется построчная матрица функций по этим страницам. Неизвестная деталь означает необходимость уточнить поведение и проверить пример, а не разрешение исключить функцию. Бесконечная совместимость со всеми будущими версиями и произвольными сторонними расширениями не подразумевается.

Milkdown используется как открытый образец, а не замена редактора:

- [Возможности Crepe](https://github.com/Milkdown/milkdown/blob/0655111f3bb8393e959ce3f3d107c83edce29c3a/packages/crepe/src/feature/index.ts) — таблицы, изображения, списки, код, формулы и управление блоками. Из набора берём поведение, соответствующее требуемым функциям Typora; AI, совместное редактирование и новые панели не добавляются автоматически.
- [Операции над таблицами](https://github.com/Milkdown/milkdown/tree/0655111f3bb8393e959ce3f3d107c83edce29c3a/packages/plugins/preset-gfm/src/node/table) и [проверки Crepe](https://github.com/Milkdown/milkdown/tree/0655111f3bb8393e959ce3f3d107c83edce29c3a/e2e/tests/crepe) — кандидаты для переноса алгоритмов и сценариев в Swift/XCTest.
- [Преобразование в Markdown](https://github.com/Milkdown/milkdown/blob/0655111f3bb8393e959ce3f3d107c83edce29c3a/packages/transformer/src/serializer/state.ts) — пример архитектуры, которую не переносим целиком: повторная сборка всего Markdown не подходит для сохранения нетронутых участков исходника LacEditor.
- [Лицензия Milkdown](https://github.com/Milkdown/milkdown/blob/0655111f3bb8393e959ce3f3d107c83edce29c3a/LICENSE) — при фактическом заимствовании кода/тестов сохранить требуемые уведомления; условия зависимостей проверять отдельно. Ссылка на исходную ревизию хранится рядом с описанием заимствования.

Ревизия Milkdown зафиксирована для воспроизводимости анализа. Перед переносом конкретного решения проверить его ограничения и применимость к текстовой модели LacEditor; открытая лицензия не делает браузерный код нативным.

## 4. Выбранный подход и границы заимствования

| Подход | Преимущества | Цена и риск | Решение |
| --- | --- | --- | --- |
| Развивать текущий TextKit 1 и заимствовать решения Milkdown | Сохраняются документы, ввод, отмена, поиск, системные вкладки и режимы больших файлов | Сложно разместить редактируемые таблицы и графические блоки без изменения исходной строки | Выбрано пользователем; сначала проверить сложные блоки на небольшом рабочем образце |
| Отдельный веб-редактор для Markdown | HTML естественно описывает таблицы, формулы, темы | Новый путь ввода и отмены, пересчёт выделения, обмен с моделью, повторная проверка сохранения и производительности; понадобится выбрать компонент | Не выбран; не подменять им реализацию при трудностях |
| Оставить исходник рядом с предпросмотром | Большая часть уже есть | Не даёт редактировать оформленные сложные элементы на месте | Не выполняет основную цель |

Редактор, ввод, выделение, команды и отмена остаются нативными на Swift/AppKit/TextKit. Не переносим весь Milkdown, ProseMirror, Remark, браузерное дерево HTML или их систему расширений. Изучаем конкретный алгоритм или пользовательский сценарий и реализуем минимальный эквивалент в существующих путях LacEditor.

Нынешний TextKit 1 — исходная техническая основа, а не доказательство возможности реализовать любую веб-вёрстку. Если образец таблиц/графических блоков не проходит приёмку, зафиксировать конкретное препятствие и предложить минимальное изменение нативного решения. Не исключать функцию, не заменять весь редактор веб-компонентом и не переходить на TextKit 2 без отдельного решения пользователя.

Существующий WebKit остаётся для предпросмотра и вывода. Для математического/диаграммного движка и встроенного внешнего медиа план допускает проверку узкого компонента отображения с локальными ресурсами; текстовый редактор и его история действий не переезжают в браузер. Пользователь разрешил подключать библиотеки, необходимые для выполнения плана. Перед подключением проверяются назначение, версия, лицензия и минимальный состав; замена редактора и дополнительные функции вне плана по-прежнему требуют отдельного решения. Если требуется абсолютный запрет JavaScript даже для формул и диаграмм, это дополнительное ограничение, которого выбранный третий вариант сам по себе не устанавливает.

## 5. Общие условия реализации

- Markdown остаётся единственным сохраняемым содержимым. Картинка, таблица или формула в интерфейсе не заменяет исходник объектным символом в пользовательском файле.
- Изменения текста проходят существующий цикл AppKit. Обычный набор сохраняет нынешнее объединение действий отмены; явная программная команда получает отдельную группу отмены. Отображение и переключение представления не меняют текст, несохранённость и историю отмены.
- Диапазоны редактора — UTF-16, как в `NSString`, а позиции cmark переводятся из UTF-8. Emoji, китайский текст и составные символы обязательны в проверках.
- Незавершённый системный ввод не прерывается оформлением или командами. Это проверяется реальной китайской раскладкой на Mac.
- Результат фоновой работы применяется только к тому же документу, версии и актуальному запуску задачи; использовать существующую координацию задач.
- Сохраняются существующие профили больших документов. Не добавлять новые пороги и не отключать оформленное редактирование произвольным ограничением.
- Данные сессии и пользовательские настройки не меняются ради отображения. Новое сохраняемое предпочтение добавлять только когда оно нужно конкретной согласованной функции.

## 8. Цикл GPT-6.1-Terra для каждой задачи

Для каждой задачи, включая подзадачи 25.1–25.2 и 25.4–25.8, в пределах выбранного полного объёма:

1. Агент-планировщик GPT-6.1-Terra читает её описание и релевантные участки; возвращает точные изменения, файлы, критерии и риски. Он не добавляет соседние улучшения.
2. Основной агент проверяет, что подзадача остаётся в согласованном плане. Пользователь отдельно разрешил подключать библиотеки, необходимые для согласованного функционала. Перед подключением проверять первоисточник, лицензию и фиксированную версию; изменение выбранного нативного подхода всё ещё требует отдельного согласования. Обычный способ реализации внутри плана не требует повторного разрешения. Для переноса из Milkdown проверяются исходная ревизия, смысл алгоритма и применимость к UTF-16/отмене LacEditor.
3. Агент-разработчик GPT-6.1-Terra получает владельческие права только на перечисленные файлы, реализует подзадачу и её необходимые тесты. Ему явно сообщается, что другие агенты работают рядом и чужие изменения нельзя отменять.
4. Другой агент GPT-6.1-Terra проводит код-ревью — проверку сделанных изменений: читает весь относящийся к задаче diff и нужный контекст, ищет воспроизводимые ошибки, пропуски требований и неподтверждённые заявления о проверках.
5. Подтверждённые ошибки исправляются, связанные проверки повторяются, изменения снова проверяются. Чужой или несвязанный дефект фиксируется отдельно и не расширяет текущую задачу автоматически.
6. Основной агент самостоятельно проверяет изменения, результат тестов, простоту решения и обновлённые описания. Только после этого задача получает статус готовности.

Правило больших файлов: если требуется почти полное изучение файла >800 строк, использовать `large-file-explorer` и получить краткую выжимку с диапазонами. Для небольших вопросов достаточно `rg` и чтения нужного метода. Повторяющийся код по точному образцу делегировать `code-generator` по правилам AGENTS.md; этот специализированный тип имеет собственную фиксированную модель, поэтому его использование вместо требуемого GPT-6.1-Terra сначала нужно согласовать. Пока такого задания не возникло.

## 9. Финальная цель /goal

После реализации задач полного плана создать отдельную цель: «Повторять независимую проверку всех сделанных изменений агентом GPT-6.1-Terra, исправлять относящиеся к задаче ошибки и предупреждения, пока проверяющий не вернёт отсутствие ошибок и предупреждений; затем самостоятельно проверить итог». В итоговую проверку входит сопоставление с полной матрицей требований: чистый diff при отсутствующей функции не означает выполнение задачи.

Цель не создаётся и не объявляется выполненной на этапе одного анализа. Чистое статическое ревью не означает, что приложение прошло сборку и приёмку на macOS. При найденном ограничении проверки явно указать его; не просить проверяющего скрывать предупреждения ради завершения цикла.

### 11.1. Swift-тесты

Новая проверяемая логика и обнаруженные ошибки покрываются XCTest в существующем `LacEditorTests`, а не дублирующими тестами на Python.
