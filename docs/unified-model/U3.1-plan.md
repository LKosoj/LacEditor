# U3.1 — HTML-адаптер: основа вывода (Preview/MarkdownHTMLRenderer*.swift)

Статус: план (код не менялся), 05.11.2026. Опора: главный план (решения 1–9, этап 3), U0, U2.3,
`Models/MarkdownDocumentModel.swift`, cmark-gfm (`src/html.c`, `houdini_*`, `scanners.re`,
`extensions/{table,tasklist,strikethrough,tagfilter}.c`, `blocks.c: process_footnotes`) из стенда
`~/tools/lac-writer-check/cmark-local`. U3.1 идёт после U2.6 (нужны `MarkdownDocumentParser` и корпус модели).

## 0. Что делаем простыми словами

Сегодня `MarkdownRenderer` сначала правит дерево cmark (вставляет служебные узлы), потом просит cmark
выдать HTML (`cmark_render_html`). Новый адаптер не трогает cmark: он обходит готовую модель и сам пишет
HTML теми же правилами, по которым пишет cmark. U3.1 — «скелет» вывода: то, что есть в обычном GFM, плюс
оболочка предпросмотра (ID и номера заголовков, обёртки таблиц и `<pre>`, пустой экран). Медиа, формулы,
подсветка, выноски, wiki и CriticMarkup — U3.2/U3.3.

## 1. API

Заменяется не `renderPage` целиком, а строится рядом (старый живёт до U4.4). Имя типа — `MarkdownHTMLRenderer`
(после U4.4 `rg "MarkdownRenderer\b"` его не находит — `\b` не совпадает с `MarkdownHTMLRenderer`).

```swift
enum MarkdownHTMLRenderer {
    /// Основной вход: модель + исходный текст (нужен для срезов по `range`, см. п. 1.2).
    static func renderPage(_ model: MarkdownDocumentModel, text: String, darkMode: Bool,
                           forExport: Bool = false, includeHeadingNumbers: Bool = false, includeListStyles: Bool = false,
                           includeSourcePositions: Bool = false, isPreview: Bool = false) -> MarkdownRenderedPage
    /// Удобный вход: строит модель (`MarkdownDocumentParser.parse`) и зовёт основной. Для тестов и потребителей без модели.
    static func renderPage(_ markdown: String, darkMode: Bool, syntax: MarkdownSyntaxOptions = .init(), ...те же флаги...)
}
```

Результат — существующий `MarkdownRenderedPage` без изменений полей. `typography` задаёт потребитель, как сейчас.

### 1.1. Параметры старого `renderPage` и что с ними в U3.1

Старая сигнатура: `markdown, darkMode, includeHTMLMedia, renderEmoji, resolveLocalImages, documentURL, prepareRemoteImages,
syntax, forExport, includeHeadingNumbers, includeListStyles, staticWidgetFallback, preserveRawHTMLBlocks,
includeSourcePositions, isPreview, highlightCode, wiki, critic, embeds, hidesObsidianComments`.

| Параметр | Решение |
| --- | --- |
| `markdown`, `darkMode`, `syntax`, `forExport`, `includeHeadingNumbers`, `includeListStyles`, `includeSourcePositions`, `isPreview` | в U3.1 |
| `syntax` у основного входа | берётся из `model.options.syntax`: `HARDBREAKS`/`NOBREAKS` (`forExport ? preserveExportSoftBreaks ?? true : preserveEditingSoftBreaks`) и `preserveWhitespace` (`forExport ? preserveExportWhitespace : preserveEditingWhitespace ?? false`) считаются оттуда |
| `includeHTMLMedia`, `renderEmoji`, `resolveLocalImages`, `documentURL`, `prepareRemoteImages`, `staticWidgetFallback`, `preserveRawHTMLBlocks`, `highlightCode` | добавляет U3.2 (с теми же значениями по умолчанию) |
| `wiki`, `critic`, `embeds`, `hidesObsidianComments` | добавляет U3.3 (они же задают `Includes`/`isVaultNote` при построении модели) |

Параметров «про запас» нет: каждая подзадача добавляет свои, потребителей до U4 нет, поэтому ничего не ломается.
U3.4 сверяет итоговую сигнатуру с таблицей выше один к одному. Поля страницы в U3.1: `body`, `headingIDs`
(`Set(model.headingIDs)`), `preserveWhitespace`, `listDepths`; `formulas`, `diagrams` пусты, `omittedHTML == false`,
маркеры медиа и `rawHTMLBlocks` пусты (их наполняет U3.2).

### 1.2. Как U3.1 выводит узлы U3.2/U3.3 (без заглушек)

Адаптер получает `text`: срез `text[range]` — единственный честный «обычный текст» для узлов, чей вид ещё не реализован.
Правило: все виды узлов разобраны в `switch` без `default`; виды U3.2/U3.3 уходят в две функции в своих файлах
`MarkdownHTMLRenderer+Media.swift` и `+Obsidian.swift`. В U3.1 эти файлы существуют (по ~40 строк) и содержат
реальное поведение «как простой текст»; U3.2/U3.3 заменяют файл целиком, основные файлы не правят
(так U3.2 и U3.3 идут параллельно без конфликта правок одного `switch`). Поведение:

| Узел | Вывод в U3.1 | Кто заменит |
| --- | --- | --- |
| `.html(любой kind)`, `.rawHTML` | `<!-- raw HTML omitted -->` (безопасный режим cmark; `UNSAFE` страница не ставит, см. п. 2.9) | U3.2 |
| `.mathBlock`, `.formula` | экранированный срез исходника (с `$`) в `<p>`/в строке | U3.2 |
| `.codeBlock` с `diagram` | обычный блок кода без подсветки | U3.2 |
| `.media/.iframe/.svg/.emoji/.ruby/.inlineStyle/.underline/.keyboard/.highlight/.subscriptText/.superscriptText` | есть `children` — их вывод без обёртки; нет — экранированный срез | U3.2 |
| `.tableOfContents` | экранированный срез `[toc]` в `<p>` | U3.2 |
| `.callout`, `.alert` | как `.quote` (`<blockquote>` с `children`; заголовок выноски — первым абзацем) | U3.3 |
| `.wikiLink`, `.noteEmbed`, `.critic` | срез исходника (у `critic` — `children`) | U3.3 |
| `.comment`, `.frontMatter` | ничего (как сейчас: front matter и `%%` превращаются в пробелы) | `.comment` — U3.3 |

Как тест это учитывает — п. 4: список «до U3.2» с причинами и `fixIn`; пустеет к U3.4.

## 2. Правила вывода (по `html.c` cmark-gfm)

Основа — писатель `Writer` (строка + два приёма): `put(_:)` и `cr()` = «если вывод не пуст и не кончается `\n`, добавить `\n`».
Все переносы строк ниже повторяют вызовы `cmark_html_render_cr` и литералы `\n` из `html.c`. Атрибут позиции
`sp(node)` пишется там же, где `cmark_html_render_sourcepos`, и только при `includeSourcePositions && !forExport`.

| Узел | Вывод |
| --- | --- |
| paragraph (не в плотном списке) | `cr` `<p sp>` инлайны `</p>\n`; в плотном списке (родитель — пункт плотного списка) — только инлайны |
| heading | `cr`; если `id` не пуст — `<span id="ID"></span>` + `cr` (бывший `CUSTOM_BLOCK`: `cr`, текст, `cr`); затем `cr` `<hN sp>` + [`<span data-lac-heading-number="1. "></span>`] инлайны `</hN>\n` |
| quote | `cr` `<blockquote sp>\n` дети `cr` `</blockquote>\n` |
| list | `cr` `<ul sp>\n` / `<ol sp>\n` / `<ol start="N" sp>\n` (`start` только если ≠ 1; для маркированного атрибута нет) … `</ul>\n` / `</ol>\n` (без `cr` перед закрытием) |
| listItem | `cr` `<li sp>` … `</li>\n` |
| task | `cr` `<li sp>` + `<input type="checkbox" checked="" disabled="" /> ` или `<input type="checkbox" disabled="" /> ` (пробел после `/>` обязателен). Отмечен — состояние `x`/`X` (не «≠ пробела»: проверить `[-]` на корпусе). Отмеченный пункт дополнительно получает первым ребёнком `cr` `<span data-lac-checked-task></span>` `cr` (как сейчас) |
| метка стиля списка | при `includeListStyles`, у пункта без `task`: первым ребёнком `cr` `<span hidden data-lac-list-depth="D" data-lac-list-kind="ordered\|unordered"></span>` `cr`; `D = ListBlock.depth`; в `listDepths` попадают встреченные `D` |
| codeBlock | `cr`; `<pre tabindex="0" aria-label="…" sp>` (п. 2.4) `<code>` либо `<code class="language-X">`, где `X` — `info` до первого пробела (`isspace`), экранирован; тело `literal` экранировано; `</code></pre>\n`. `data-meta` не пишется (опция `FULL_INFO_STRING` не стоит) |
| thematicBreak | `cr` `<hr sp />\n` |
| table | п. 2.3 |
| footnoteDefinition / reference | п. 2.6 |
| text | экранированный текст; при `preserveWhitespace` — в `<span data-lac-whitespace>`…`</span>` (в экспорте `<span data-lac-whitespace style="white-space:break-spaces">`); оборачивается **каждый** узел `.text` (в т. ч. в заголовках, ячейках, ссылках), но не `alt` картинки |
| code | `<code>`+экранированный литерал+`</code>` |
| strong / emphasis | `<strong>`, `<em>`; вложенный `strong` прямо в `strong` не пишет теги (`parent.type != STRONG` у cmark) |
| strikethrough | `<del>`…`</del>` |
| softBreak | `hardBreaks` → `<br />\n`; иначе пробел (`NOBREAKS`). В режиме «ни то, ни другое» (`\n`) не нужен: приложение всегда ставит один из двух |
| hardBreak | `<br />\n` |
| link | `<a href="HREF"` + (title не пуст ? ` title="…"`) + `>`; `HREF` — п. 2.2; закрытие `</a>` |
| image | `<img src="HREF" alt="ALT"` + (title ? ` title="…"`) + ` />`; `ALT` — `Image.alt`, экранирован |

### 2.1. Экранирование текста (`houdini_escape_html0`, `secure = 0`)

Таблица по байтам UTF-8 (текст в Swift — по символам `String`, результат тот же): `&` → `&amp;`, `<` → `&lt;`,
`>` → `&gt;`, `"` → `&quot;`. Апостроф `'` и косая черта `/` **не** экранируются (в `secure`-режиме cmark писал бы
`&#39;`/`&#47;` — нам нужен режим `secure = 0`, как в `html.c`). Остальное — как есть. Одна функция заменяет три
копии `htmlEscaped`/`escape`/`escaped` в `MarkdownRenderer` (их удалит U4.4).

### 2.2. Адреса (`houdini_escape_href` + `_scan_dangerous_url`)

- Опасная схема: адрес (с первого символа, без обрезки пробелов, без учёта регистра) начинается с `javascript:`, `vbscript:`,
  `file:` или `data:`. Исключение — `data:image/png`, `data:image/gif`, `data:image/jpeg`, `data:image/webp` (безопасны).
  Для опасного адреса атрибут пишется пустым: `href=""` / `src=""`. `UNSAFE` страница не включает, поэтому проверка всегда.
- Безопасные символы адреса (остаются как есть): ASCII-буквы и цифры и `! # $ % ( ) * + , - . / : ; = ? @ _ ~`.
  Особые: `&` → `&amp;`, `'` → `&#x27;`. Все остальные байты UTF-8 (в т. ч. пробел, `" < > [ \ ] ^` обратная кавычка `{ | }`,
  любой не-ASCII) → `%XX` заглавными шестнадцатеричными, побайтно. Кириллица, CJK и эмодзи кодируются побайтно; уже стоящий `%` не трогается.
- Применяется к `href` ссылок, `src` картинок и идентификаторам сносок (п. 2.6).

### 2.3. Таблицы (`extensions/table.c`) и обёртка

```
cr <div class="table-scroll" role="region" aria-label="L10n.tr(表格，可横向滚动)" tabindex="0">   ← обёртка пишет адаптер
<table sp>
<thead>            ← строка заголовка: cr <thead> cr <tr sp> … cr </tr> cr </thead>
<tr>…
<tbody>            ← перед первой строкой данных: cr <tbody> cr; перед </table>: cr </tbody> cr
…
cr </table></div>\n     ← cr, </table>, </div>, затем cr
```

Ячейка: `cr` `<th`/`<td` + ` align="left|center|right"` (по `alignments[cell.column]`; `unspecified` — без атрибута) +
` colspan="N"`/` rowspan="N"` (только если > 1) + `sp` + `>` инлайны ячейки `</th>`/`</td>`. Порядок атрибутов: `align`, `colspan`,
`rowspan`, `data-sourcepos`. Обёртка сегодня добавляется строковой заменой в `renderPage` (`MarkdownRenderer.swift` ~456–466:
`<table>` → `tableWrapper + <table>`, `</table>` → `</table></div>`); адаптер пишет её сразу, результат побайтно тот же.
**Пробел модели:** в `Table.Cell` нет `colspan`/`rowspan` и признака «ячейка-заполнитель» (cmark при `TABLE_SPANS` не выводит ячейки
с `colspan == 0` или `rowspan == 0`). `virtualSeparators` покрывает только `colspan`. Нужно решение до U2.3a — см. «Спорное», п. 1.

### 2.4. `<pre>`

Сегодня `<pre>` → `<pre tabindex="0" aria-label="L10n.tr(代码块，可横向滚动)">` и `<pre data-sourcepos=…>` →
`<pre tabindex="0" aria-label="…" data-sourcepos=…>` — строковой заменой по всему телу. Адаптер пишет атрибуты сразу в таком порядке
(`tabindex`, `aria-label`, `data-sourcepos`). Побочный эффект старой замены, который U3.2 обязан сохранить: `<pre data-lac-diagram=…>` и
подсвеченный `<pre>` из `CUSTOM_BLOCK` замена не затрагивала, то есть без `tabindex` (проверяет эталон U0.1).

### 2.5. `data-sourcepos`

Формат `L1:C1-L2:C2`, как cmark: строка 1-based, колонка 1-based **в байтах UTF-8** строки, конец включительно (колонка последнего байта).
Считается из `range` (UTF-16) через `MarkdownSourcePositions.lineStarts` (U2.1): колонка = `utf8.count` префикса строки + 1. Потребитель —
`MarkdownPreview` (JS, ~933): берёт только номера строк (`^(\d+):\d+-(\d+):\d+$`), пропускает элементы с `start < last`, игнорирует `.footnotes`.
Поэтому критерий: **номера строк начала равны старому выводу**; колонки и конец у списков/пунктов могут отличаться — это в раздел
«Намеренные изменения HTML» (U3.4). Атрибут получают: `blockquote`, `ul`/`ol`, `li` (в т. ч. задачи), `h1–h6`, `pre`, `p`, `hr`,
`table`, `tr`, `th`/`td`. У `<span id>`, меток и `<div class="table-scroll">` атрибута нет. В экспорте не пишется никогда.

### 2.6. Сноски (`footnotes.c`, `blocks.c: process_footnotes`, `html.c`)

Предпроход по модели (один обход в порядке документа, определения — на своих местах):
1. Определения: ключ — нормализованная метка (свёртка регистра, обрезка, склейка пробелов; для `cmark_utf8proc_case_fold` — `folding(.caseInsensitive…)`
   плюс `lowercased()`); при повторе ключа берётся первое определение.
2. Ссылки в порядке обхода: если определение найдено — номер `ix` (по первому упоминанию), счётчик `def_count` определения++ ,
   `ref_ix` ссылки = этот счётчик; ключ ссылки — `range.location` (ссылки внутри определений получают `ref_ix` в порядке обхода, а не вывода). Не найдено — вывод текстом `[^метка]`.
3. Определения без ссылок не выводятся; остальные идут в конец документа в порядке `ix`.

Вывод: `<sup class="footnote-ref"><a href="#fn-LABEL" id="fnref-LABEL[-REFIX]" data-footnote-ref>IX</a></sup>` (`LABEL` — метка определения «как написана»,
через `escape_href`; `-REFIX` — только если `ref_ix > 1`). Раздел: перед первым определением
`<section class="footnotes" data-footnotes>\n<ol>\n`, в конце документа `</ol>\n</section>\n`. Определение: `<li id="fn-LABEL">\n`, дети, закрытие —
`</li>\n`. Обратная ссылка ставится в конец последнего абзаца определения (` <a href="#fnref-LABEL" class="footnote-backref" data-footnote-backref
data-footnote-backref-idx="IX" aria-label="Back to reference IX">↩</a>` перед `</p>`); если последний ребёнок — не абзац, то после детей и `\n`.
При `def_count > 1` для каждого `i` в `2…def_count` добавляется ` <a href="#fnref-LABEL-i" class="footnote-backref" data-footnote-backref
data-footnote-backref-idx="IX-i" aria-label="Back to reference IX-i">↩<sup class="footnote-ref">i</sup></a>`. Абзац в плотном списке внутри
определения: проверить побайтно на корпусе (в cmark у такого абзаца нет `</p>` и backref пишется по другому пути).

### 2.7. `tagfilter`

В cmark-gfm фильтр (`title textarea style xmp iframe noembed noframes script plaintext`) срабатывает только вместе с `CMARK_OPT_UNSAFE`.
Страница `UNSAFE` не ставит (единственное место — `MarkdownHTMLMediaService.swift:1527`, внутренняя проверка, не вывод), поэтому сырой
HTML заменяется комментарием, а `tagfilter` в U3.1 не нужен. Реализуется в U3.2, только если `preserveRawHTMLBlocks` начнёт писать сырой HTML в тело
(проверить там). Это расхождение с формулировкой главного плана — см. «Спорное», п. 3. Примеры spec 652 и ext 22 остаются в списке намеренных расширений.

### 2.8. Пустой экран

`isPreview && !forExport` и текст — только пробельные символы: тело = `<p class="lac-empty">` + экранированный `L10n.tr("预览为空。…")` + `</p>`
(в старом коде проверяется текст после подготовки; в U3.1 — исходный `text`; U3.3 добавит случай «только комментарии `%%`»).

### 2.9. Выход за пределы U3.1

Подсветка, `highlightCache`, `data-lac-math`, `<nav data-lac-toc>`, `data-lac-diagram`, медиа, `<aside>` алертов и выносок.

## 3. ID и номера заголовков: перенос, а не копия

- **ID.** Не считаются в адаптере. `Heading.id` и `headingIDs` заполняет ядро U2.3 через `MarkdownHeadingAnchors.Allocator`
  (тот же файл `Models/MarkdownPresentation.swift`, тип остаётся на месте). Сегодня Allocator вызывается в `MarkdownRenderer.installTableOfContents`
  (`var anchors`, ~1712; вызов ~1758, вставка `<span id>` ~1847 и `headingIDs` ~907). Адаптер читает `id` из узла; пустой `id`
  (заголовок в таблице, картинке, определении сноски) — без `<span>`. Старые строки удалит U4.4, дубля алгоритма нет.
- **Номера.** Не копия, а вызов существующего `MarkdownHeadingNumbering.applying(to:enabled:)` (`MarkdownPresentation.swift:144`; считает только по `level`).
  Адаптер собирает `[MarkdownHeading]` из заголовков модели с непустым `id` и `!isUnreliable` (аналог «confirmed» в старом коде: заголовок с известной позицией),
  вызывает его один раз за страницу и пишет `<span data-lac-heading-number="N. "></span>` первым ребёнком `<hN>` (экранирование п. 2.1).
  Тот же номер нужен оглавлению (U3.2) — поэтому он хранится в словаре «позиция заголовка → номер», а не пересчитывается.
- Оглавление, `lac-anchor-N` (`namedAnchors`) и `aliases` — U3.2.

## 4. Тест: сверка U0.3 для нового адаптера

Файл `MarkdownSpecConformanceTests.swift` (269 строк) не заменяется: старый тест продолжает проверять `MarkdownRenderer` до U4.4.
Правки (одна подзадача, п. 5, подзадача e):

1. Тело `outcomes` выносится в `outcomes(render: (String, MarkdownSyntaxOptions) -> String, inlineMath:)`; проверка из `testConformance` —
   в `checkConformance(all:, lists:, minimum:)`. Поведение старого теста не меняется.
2. Новый тест `testConformanceHTMLRenderer`: `render = MarkdownHTMLRenderer.renderPage(markdown, darkMode: false, syntax:).body`;
   нормализатор `SpecHTMLNormalizer` тот же (обёртки таблиц и `<pre>` адаптер пишет так же, `data-lac-*` убирает нормализатор).
3. Списки: `intentionalExtensions` те же, кроме записей, которые в U3.1 «проходят случайно» (spec 138 и ext 12: сырой `<del>`/`<br>` теперь заменяется
   комментарием, как и ожидание после нормализации). Они переходят в `pendingU32` с `fixIn: "U3.2"` и причиной; проверка «запись устарела» для них
   инвертируется: в U3.1 обязаны **совпасть**, в U3.2 возвращаются в `intentionalExtensions`. Остальные узлы U3.2/U3.3, не попавшие в спецификацию, спорных
   примеров не создают (в spec нет `$`, `==`, `[toc]`).
4. Нижняя планка: `matches ≥ minimumMatches (685)`. Допускается ровно столько расхождений, сколько записано в списках; несовпадение без записи падает.
   После U3.2 `pendingU32` пуст, и планка 685 сохраняется без поправки; новый список ошибок `knownDefects` пуст.
5. Первый прогон — в режиме `LAC_SPEC_REPORT` (файл вне репозитория); каждое несовпадение: ошибка адаптера (чинится) либо новая запись с причиной и `rule`.
6. Дополнительно прямое сравнение со старым рендером: тест `testHTMLRendererMatchesLegacyBytesOnSpecCorpus` — на всех 702 примерах те же настройки, строки `body` равны
   побайтно (без нормализатора), кроме ключей в `pendingU32`/намеренных расширений. Ловит переносы строк и атрибуты, которые нормализатор прячет. Вариант с
   `includeSourcePositions: true`: сравниваются только номера строк начала всех `data-sourcepos` (колонки и конец — в отчёт для U3.4).
7. Контрольные тесты адаптера на модели (`MarkdownHTMLRendererTests.swift`, ~250 строк, образец — соседние тесты рендера): экранирование и адреса (таблица символов,
   кириллица/CJK/эмодзи, опасные схемы), `ol start`, плотный и свободный список, задачи (с отметкой и без, `data-lac-checked-task`), метки стилей списков и `listDepths`,
   таблица с выравниванием и `colspan`, обёртка таблицы, `<pre>`, заголовки с ID/номерами/пустым ID, сноски (две ссылки на одну, ссылка внутри определения, неиспользованное определение,
   несуществующая метка), `HARDBREAKS`/`NOBREAKS`, `data-lac-whitespace` (предпросмотр и экспорт), пустой экран, `\r\n`. Ожидания — точные строки; позиции в UTF-16.

## 7. Риски

- **Мелкие отличия переносов строк/атрибутов** — главный риск плана; смягчение — побайтное сравнение п. 4.6 и порядок атрибутов из п. 2.
- **Склеенные `.text`.** Если U2.3 сливает соседние текстовые узлы cmark (например, до и после `[`), число `<span data-lac-whitespace>` изменится: U2.3 обязано хранить узлы как cmark; проверить контрольным тестом.
- **Нормализация метки сноски** (`cmark_utf8proc_case_fold`) в Foundation неточная для редких символов; дубликаты определений в cmark решает `bsearch` — для одинаковых меток порядок не гарантирован, тест на дубль — только «не падает».
- **`range` у списков и пунктов** может дать другой конец, чем cmark; влияет только на `data-sourcepos` (п. 2.5).
- **`alt`** картинки строится ядром (`Image.alt`) — в U3.1 доверяем; если расходится с `plain`-режимом cmark (разрыв → пробел), правится в U2.3.
- **Проверка только на Linux:** `L10n`, `UTType` и WebKit — заглушки; HTML на Mac проверяется в U9.3.

## Спорное (для утверждения)

1. **Модель не хватает `colspan`/`rowspan`.** Предлагаю добавить в `Table.Cell` поля `colspan: Int`, `rowspan: Int` и вывести ячейки-заполнители из списка (или пометить `isFiller`); без этого `TABLE_SPANS` не воспроизвести. Правка U1.1/U2.3a до начала U3.1.
2. **Пять файлов вместо трёх** и файлы `+Media`/`+Obsidian` с поведением «простой текст» уже в U3.1: так U3.2 и U3.3 идут параллельно, не касаясь основного `switch`. Альтернатива: один `switch`, U3.2 и U3.3 строго по очереди.
3. **`tagfilter` в U3.1 не делаем** (мёртвый код в безопасном режиме); главный план его перечисляет.
4. **Алерты GitHub** в плане этапа 3 не названы; предлагаю U3.3 (рядом с выносками), до этого вывод как цитата.
5. **Сверка:** новый тест не заменяет, а дополняет старый (удаляется в U4.4); в U3.1 записи 138 и ext 12 временно «совпадают».
6. **`data-sourcepos`:** колонки в UTF-8 как у cmark; конец контейнеров может отличаться — вписывается в «Намеренные изменения HTML».

## Решения основного агента

1. В `MarkdownDocumentModel.Table.Cell` добавлены `colspan` и `rowspan` (значения cmark, 0 — заполнитель); U2.3 заполняет их через `cmark_gfm_extensions_get_table_cell_colspan/rowspan`.
2. Принято пять файлов: `+Media` и `+Obsidian` в U3.1 выводят свои узлы так, как их сейчас видит cmark без расширений (обычный текст/сырой HTML), а не пустыми заглушками; U3.2 и U3.3 заменяют эти ветки и идут параллельно.
3. `tagfilter` применяется только там, где сырой HTML выводится (как у cmark при `UNSAFE`); формулировка главного плана уточнена.
4. Алерты GitHub — в U3.3, до этого — обычная цитата.
5. Принято: 138 и ext 12 возвращаются в список расширений в U3.2.
6. Допущения для U2.3 (соседние `.text` не склеиваются; `alt` картинки — по правилам `plain` cmark) записаны в `U2.3-plan.md`.

7. Из плана U3.2: U3.1 оставляет три точки подключения — функция адреса картинки (с обёрткой `data-lac-centered-image`), выбор вывода блока кода (диаграмма/подсветка/обычный `<pre>`), писатель текста, умеющий объединять соседние `.text`/`.emoji` в один `data-lac-whitespace`.

8. Из плана U4: типы `MarkdownRenderedPage`, `MarkdownTypography`, `MarkdownRenderedMath`, `MarkdownRenderedDiagram` переносятся из `MarkdownRenderer.swift` (строки 1–390) в новый `Preview/MarkdownRenderedPage.swift` в U3.1a (перенос; pbxproj и `lib-files.txt` вносит основной агент).

9. Сноски в модели — в порядке позиции; адаптер упорядочивает их по первой ссылке, как cmark.
