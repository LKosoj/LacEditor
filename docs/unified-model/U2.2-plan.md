# U2.2. Маскировка: `Preview/MarkdownSourceMask.swift`

Статус: план (код не менялся). Дата замеров: 2026-11-05. Номера строк даны по рабочей копии (в ней много чужих незакоммиченных правок — не откатывать).
Прочитано: `docs/markdown-unified-model-plan.md` («Архитектурные решения» п. 2, 3, 5, 7, 9; задачи U2.2, U2.3, U3.3, U5a, U7.4), `um-common.txt`, `docs/unified-model/U2.1-plan.md`, `Models/MarkdownDocumentModel.swift` (типы U1.1).

## 0. Коротко

- **Рекомендация по главному вопросу (п. 2):** гибрид. Front matter, `%%…%%` и CriticMarkup маскируются **до cmark**, а запреты (код, формулы, HTML-блоки, таблицы) определяются **лёгким построчным предварительным проходом** (вариант «а»), который можно заменить точными диапазонами из дерева (тот же вход функции). `[[…]]` и `![[…]]` **до cmark не маскируются**: они распознаются **после** разбора по текстовым узлам (вариант «в»), как это уже делают редактор и панель. Это отступление от формулировки п. 2 главного плана (там перечислены и скобки wiki/embed) — см. «Спорные решения», №1.
- **Контракт маски:** длина в UTF-16 и позиции CR/LF не меняются, байты UTF-8 — меняются. Поэтому `MarkdownSourcePositions` (бывший `Source`) в U2.3 строится **от маскированного текста**, а строки для узлов берутся из исходного текста по диапазонам. Старая `maskedFrontMatter` сохраняет байты и в новое ядро не годится.
- В U2.2 меняются только новые файлы (`MarkdownSourceMask.swift`, тест); существующие распознаватели (`CriticMarkupService.items`, `MarkdownObsidianComment.ranges`, `MarkdownNoteEmbed.items`, `MarkdownWikiLinkExtractor.links(textRanges:…)`, `frontMatter`) **вызываются как есть**, без копирования и без правки.

## 1. Что делает код сейчас (точные правила)

### 1.1. Порядок в `MarkdownRenderer.renderPage` (`Preview/MarkdownRenderer.swift`, 413–486)

Каждый шаг **заново разбирает** результат предыдущего (полный `MarkdownPresentationParser.parse`, чтобы получить запрещённые диапазоны):

| # | Строки | Шаг | Условие | Разборов |
|---|---|---|---|---|
| 1 | 421–428 | `CriticMarkupRender.prepare(text, mode, syntax)` | передан `critic` | 1 (внутри `items`, если есть `{++` и т. п.) |
| 2 | 432–436 | `MarkdownObsidianComment.hidden` | `hidesObsidianComments` или `appliesTo(documentURL:)` и есть `%%` | 1 |
| 3 | 437–444 | `MarkdownNoteEmbed.prepare` | есть `![[` | 1 |
| 4 | 445, 489–493 | `substitutingWikiLinks` → `MarkdownWikiLinkExtractor.links(in:)` + `MarkdownWikiLinkRewriter.rewrite` | `wiki != nil` и есть `[[` | 1 |
| 5 | 445 | `MarkdownCalloutRender.separatingTitles` | всегда | 0 (задача U2.5/U3, не U2.2) |
| 6 | 574 | `maskedFrontMatter` в `renderBody`, затем единственный cmark для вывода | всегда | 1 (вывод) |

То есть в худшем случае 5 разборов одного текста. После cmark: `CriticMarkupRender.finalize` (466), `MarkdownNoteEmbed.finalize` (467–470), `MarkdownCalloutRender.transform`.
Порядок важен: критик → `%%` → встраивания → wiki. Комментарий `%%` видит текст после критика, встраивание — текст после скрытия комментариев (поэтому `![[…]]` внутри `%%` не встраивается — тест `testHeadingCalloutAndEmbedInsideCommentAreNotRendered`).

### 1.2. Front matter (`MarkdownPresentationParser.swift`)

- `frontMatter(_:)` — 1175–1209 (`struct FrontMatter { range, markers }` — 1170–1173). Правила: первая строка — `---` (допускаются U+FEFF в самом начале и хвостовые пробелы/табы) с переводом строки; закрытие — первая строка `---` или `...` (тоже с хвостовыми пробелами/табами); без закрытия — `nil`; `range` — от 0 до конца закрывающей строки **без** её перевода строки; `markers` = [открывающий, закрывающий] по 3 символа. Границы строк CR/LF/CRLF. Предварительный проход по строкам, cmark не нужен.
- `maskedFrontMatter(_:frontMatter:)` — 1211–1217: каждый **байт** UTF-8 диапазона, кроме `\n`/`\r`, → пробел. UTF-8 сохраняется (тест `testFrontMatterBoundariesPreserveComplexContentAndLaterOffsets`: `masked.utf8.count == source.utf8.count`), **UTF-16 не сохраняется** (кириллица 2 байта → 2 пробела). Работает, потому что `Source` строится по **исходному** тексту, а cmark получает маску: совпадают байтовые столбцы.
- Вызовы: `parse` (1766–1767), `MarkdownRenderer` 574, `MarkdownSemanticDocument` 91–92, `MarkdownImageUploadService` 371/404/869/903, `MarkdownClipboardCopyService` 415; сама `frontMatter` — ещё ~25 мест (список в `rg`, группа U7.4).
- Запретов нет: front matter возможен только в начале текста.

### 1.3. CriticMarkup

Распознавание — `CriticMarkupService.items(in: NSString, window:, excluded:)` (`Services/CriticMarkupService.swift`, 48–86; чистая функция от текста и запрещённых диапазонов):
- Открытие `{++`, `{--`, `{~~`, `{>>`, `{==` (`openSpec`, 210–217: три символа, 2-й = 3-му; перед `{` чётное число `\`). Закрытие `++}`, `--}`, `~~}`, `<<}`, `==}`.
- `body` (219–238): один проход вперёд до закрытия своего вида; вложенное открытие (`{++` и т. п.) → внешняя правка отбрасывается, поиск идёт с вложенной; пустая строка (только пробелы, табы и `>`; `isBlankLine` 265–276) или конец текста → не правка. Правка может занимать несколько строк внутри абзаца.
- Подмена: внутри ищется первая `~>`; нет — не правка.
- Запреты: `excluded` — открытие внутри запрещённого диапазона пропускается, весь диапазон правки не должен пересекать запрещённые (`blockingRange`, `intersects`, 282–301).
- Результат `CriticMarkupItem { kind, range ({…}), content, separator }`.
- Откуда запреты: `CriticMarkupRender.items(in:syntax:)` (`Services/CriticMarkupRender.swift`, 91–99) делает **полный разбор** `MarkdownPresentationParser.parse(...).elements` и берёт `MarkdownElementIndex.excludedRanges` (`Models/MarkdownPresentation.swift`, 1850–1887). Запрещены виды: `frontMatter`, `codeBlock`, `mathBlock`, `table`, `htmlBlock`, `code` (строчный), `formula` (строчная). Редактор (`EditorCoordinator` 1673, 4047, 6177) берёт те же диапазоны из готового разбора.
- Быстрая проверка `mayContainMarkup` — 72–89 (есть `{` и два одинаковых из `+ - ~ > =` за ним).

Преобразование для HTML — `CriticMarkupRender.prepare` (125–170) и `finalize` (173–~300):
- `.result`/`.original`: **текст переписывается до cmark** по `CriticMarkupService.resolutions` (принятие/отклонение), разбор идёт уже по результату; длина и строки меняются.
- `.show`: (137–168) выбирается свободный блок из 0x20 символов Private Use Area (`freeBase`, 327–339, пользовательские PUA учитываются — тест `testUserPrivateUseCharactersSurvive`). Вставка `{++x++}` → `insOpen x insClose` (3 символа → 1), удаление — `delOpen/delClose`, выделение — `hlOpen/hlClose`, подмена `{~~a~>b~~}` → `delOpen a delClose insOpen b insClose` (`~>` исчезает), комментарий → `cmOpen` + цифры номера (тоже PUA) + `cmClose`, а каждый перевод строки внутри комментария заменяется на `\n` + `filler` (строка не становится пустой, число строк прежнее). Текст комментария уходит в побочную таблицу `comments`. Длина **не сохраняется**.
- `finalize`: символы → теги `<ins class="critic-ins">`, `<del …>`, `<mark class="critic-hl">`, `<span class="critic-comment" … aria-label=…>&#9998;</span>`; маркеры внутри атрибутов тегов (href, id, alt) вырезаются; правка, пересёкшая границу блока (абзац, пункт, ячейка…), закрывается перед закрытием контейнера и открывается заново (`tagStack`, `reopenTags`); строки-наполнители вместе с предыдущим переводом строки/`<br />` удаляются.
- Почему нельзя оставить сырой текст до cmark: `--`/`--}` под `SMART` превращаются в «–» (литерал узла перестаёт совпадать с исходником, позиции становятся «неподтверждёнными»); `~~`/`~>` — зачёркивание GFM (cmark-gfm принимает и одиночный `~`); `==` — выделение (`MarkdownPresentationParser.highlightRanges`, 1220); тело `{>>…<<}` — произвольная разметка и строки. Сами `{++ ++}` cmark не трогает.

### 1.4. Комментарии Obsidian `%%…%%` (`Preview/MarkdownObsidianComment.swift`)

- `appliesTo(documentURL:)` (11): только локальные копии заметок хранилища (`…/Application Support/<приложение>/Vaults/`). Вызывающий передаёт `hidesObsidianComments` отдельно (встроенные заметки, экспорт). Для модели — одно булево `isVaultNote` (уже есть в `MarkdownDocumentModel.Options`, строка 36).
- `mayContainComment` (16–27, 29–31): есть ли `%%`.
- `ranges(in:window:excluded:)` (37–82; чистая функция): ищет пары `%%`; **открытие** внутри запрещённого диапазона пропускается; **закрытие** внутри запрещённого диапазона пропускается (поиск идёт дальше); перед открытием нечётное число `\` — не открытие; незакрытый `%%` — текст, поиск прекращается; диапазон — от первого `%` до последнего `%` закрывающей пары; комментарий может содержать пустые строки и целые блоки кода (код внутри «проглатывается»). Запреты — те же `excludedRanges` (89–93: полный разбор).
- `hidden(_:syntax:)` / `hidden(_:ranges:)` (96–98, 108–167): **удаляет** текст комментария (длина меняется), CR/LF внутри сохраняет. Если комментарий занимает строки целиком и стоит внутри абзаца (`isInsideParagraph`: до него в строке только пробелы/префиксы цитаты и списка, после — только пробелы, строки выше и ниже не пустые), в начало и после каждого перевода строки вставляется U+200B, чтобы строка не стала пустой и абзац не разорвался. Иначе строки комментария становятся **пустыми** (разрыв абзаца, пустая строка между блоками — это нужно: комментарий между блоками не создаёт абзац).
- `removed` (102, 169–) — вырезание для Pandoc, к U2.2 не относится.
- Редактор: `reapplyObsidianCommentColors` (`EditorCoordinator` ~6190–6215), предел 300 тыс.

### 1.5. Встраивания `![[…]]` (`Preview/MarkdownNoteEmbed.swift`)

- `items(in:excluded:)` (60–101): `![[` вне запрещённых диапазонов; чётное число `\` перед ним; до `]]` в пределах строки; внутри нет `\`, `\0`, `[[`; `parse` (104–121): `цель#раздел|псевдоним` (первый `|`, затем первый `#` слева от него), цель пустая — не встраивание; `kind(forTarget:)` (53–58) по расширению (картинка / вложение / заметка); `isBlockEmbed` (124–147): строка целиком из встраивания (отступ ≤3 пробела, после — пробелы/табы), сверху и снизу пустая строка или край текста. Запреты — полный разбор (240) через `excludedRanges`; текстовых узлов не требует.
- `prepare` (231–262): картинки и вложения → `![имя](путь)`/`[имя](путь)` или `*Вложение недоступно*` (`fileReplacement`, 281, приватная; ищет файл рядом с документом и от корня); блоки-заметки (при наличии провайдера) → абзац `LACEMBED<n>Z` (токен выбирается так, чтобы не встречаться в тексте — `testEmbeddedNoteCannotForgeMarker`). Длина меняется, число строк нет.
- `finalize` (325–379): подмена `<p>маркер</p>` на врезку; лимиты (20 встраиваний, 1 МБ суммарно, 64 КБ на заметку); раздел по `#`; вложенный `renderPage(wiki: nil, embeds: nil)` — глубина 1; `flatten`.

### 1.6. Wiki-ссылки

- Распознавание: `MarkdownWikiLinkExtractor.links(textRanges:excluded:text:)` (`Services/MarkdownWikiLinkExtractor.swift`, 12–49) принимает **подтверждённые текстовые фрагменты** cmark-разбора (`wikiTextRanges`, `MarkdownPresentationParser.swift` 1941–1946, берутся из `MarkdownEmojiCandidateExtractor`) и запрещённые диапазоны; соседние фрагменты сливаются в серии; ссылка не может пересечь границу узла (выделение, код, ссылка и т. п. рвут серию). Правила: `[[` без `!` перед ним (`![[` — встраивание), нечётное число `\` перед `[[` — не ссылка, закрытие `]]` в пределах серии без `[`, CR, LF, U+2028/2029 внутри; `parsed` (75–108): первый `|` → псевдоним (пустой — не ссылка), первый `#` слева от него → заголовок, цель обрезается по пробелам/табам, пустая цель без заголовка и `\`/`\0` в цели — не ссылка. `markerRanges` = диапазоны от `[[` до начала отображаемого текста и от его конца до `]]`.
- Запреты (3448–3466): диапазоны ссылок, картинок, таблиц, **заголовков**, формул (блочных и строчных), ruby, HTML-блоков, audio/iframe/details, блоков кода, диаграмм, разрывов страниц, оглавления, сносок (ссылка и определение), span-ов-ссылок. Узлы кода и строчного HTML в серии текста не участвуют сами (`wikiTextRanges.removeAll { blocked($0) }`, 3417).
- Подстановка для HTML: `substitutingWikiLinks` (489–493; **ещё один полный разбор** через `MarkdownPresentationParser.parse(includeWikiLinks: true)`) и `MarkdownWikiLinkRewriter.replacements/rewrite` (`MarkdownWikiLinkResolver.swift`, 203–239): `[[…]]` → `[отображаемый текст](относительный адрес)` (текст экранируется — разметка внутри не работает) либо просто отображаемый текст, если цель не найдена/неоднозначна/без адреса. Длина меняется, число строк нет.
- Редактор: те же `wikiLinks`, диапазон ссылки — `.link` span с `markerRanges` (3467–3469). Только при `includeWikiLinks`.

## 2. Главный вопрос: можно ли маскировать до cmark, если запреты требуют блоков

### 2.1. Как каждый вид влияет на дерево cmark, если его не трогать

| Вид | Влияние на cmark без маски | Нужна маска до cmark? |
|---|---|---|
| front matter | `---` → линия или setext-заголовок; YAML → абзацы, `#` — заголовки, `[toc]` — оглавление | Да (сейчас уже так). Запретов нет — только начало текста |
| `%%…%%` | пустая строка внутри рвёт абзац; `#`, `-`, ``` внутри создают блоки; обратные кавычки/`$`/`<` внутри открывают строчные элементы, пересекающие границу комментария | Да. Запреты нужны |
| CriticMarkup | `--` → «–», `~~`/`~>` → зачёркивание, `==` → highlight, тело `{>>…<<}` — любая разметка и строки; `{++`, `++}` безобидны | Да, но только разделители и тела комментариев. Содержимое `{++…++}`/`{--…--}`/`{==…==}`/подмены остаётся разметкой. Запреты нужны |
| `[[…]]` | `[x]` становится ссылкой только если есть определение `[x]: …` (редко); `*`, `` ` ``, `<` в псевдониме рвут текстовые узлы; `\|` в ячейке таблицы режет ячейки (но в таблицах wiki не распознаётся) | **Нет**: структуру не ломает, а распознавание и сейчас идёт после разбора по текстовым узлам |
| `![[…]]` | `![` пробует стать картинкой, но без определения `[x]: …` остаётся текстом; блочное встраивание — обычный абзац | **Нет**: достаточно распознавания после разбора |

### 2.2. Варианты

**(а) Предварительный построчный проход для запретов, затем маска, затем один разбор.** Так делают нынешние функции там, где дерева ещё нет: `MarkdownNoteEmbed.section` (190–219: ограждения и ATX без cmark), `StyleProseMask` (186–240), `MindMapDocumentParser` (30–62), `SearchIndexChunker` (56–72). Плюсы: один разбор, сложность линейная, быстрый выход, если токенов нет. Минусы: запреты определяются приближённо (вложенность контейнеров, отступный код после абзаца, HTML-блоки, таблицы, строчный код); ошибка = комментарий в коде скрыт или не скрыт.

**(б) cmark → дерево → найти разрешённые участки → маска → второй разбор.** Точно, но запрещено п. 7 («один разбор на версию») и сегодня именно это и делается (до 5 разборов). Отбрасывается.

**(в) Маскировать только то, что ломает cmark; остальное распознавать после разбора по текстовым узлам.** Для wiki и embed подходит полностью (таблица 2.1). Для `%%` и критика не подходит: они ломают дерево **до** того, как его можно построить.

**Рекомендация: (а) для front matter, `%%` и критика + (в) для `[[…]]` и `![[…]]`**, плюс проверка предположений после разбора:
1. Предварительный проход строит оценку запрещённых диапазонов (правила 4.2). Это вход `excluded:` функции маскировки; тот же вход можно подать **точными** диапазонами из дерева.
2. U2.3 после разбора сравнивает: пересчитывает критик и комментарии на точных диапазонах дерева (`MarkdownElementIndex.excludedRanges`). Результат совпал — единственный разбор. Расхождение (редкий случай: токен внутри кода при неточной оценке) — вариант (г) ниже.
3. Wiki и embed считаются после разбора на тех же `excluded` и текстовых фрагментах (функции U2.2, 4.4).

**(г) Запасной путь при расхождении** — решение за основным агентом (спорное №2): либо один повторный разбор с точными диапазонами (виден в счётчике полных разборов, ожидается ≈0 на реальных документах), либо без запаса и без проверки (оценка = истина, расхождения фиксируются в «Намеренных изменениях»). Рекомендую сначала измерить расхождения тестом 7.4 на корпусе U0 и решить по числу.

Почему не «всё после разбора по узлам» для критика: сам cmark искажает разделители (`--`, `~~`, `==`), а `{>>…<<}` с пустыми строками внутри не восстановить из дерева, где он уже распался на блоки.

## 3. Контракт маскировки и заменяющие символы

### 3.1. Что сохраняется

- Длина в UTF-16 и положение каждого CR/LF (CRLF остаётся парой). Заменяется **каждая единица UTF-16** отдельно (суррогатные пары не сохраняются, но и половинок не остаётся — заменяются обе). Байты UTF-8 **не** сохраняются.
- Следствие для U2.3 (записать в план U2.3): `MarkdownSourcePositions(maskedText, …)` и все сравнения «подстрока диапазона = литерал cmark» работают по **маскированному** тексту (раскладка по строкам и UTF-16 та же, столбцы пересчитываются от маски); тексты узлов (заголовки, подписи, комментарии, цели wiki) берутся из **исходного** текста по диапазону. Старый контракт «маска по байтам + `Source` по исходному» не переносится: он невозможен, когда пустую (пробельную) строку нужно собрать из кириллицы.

### 3.2. Какие символы

| Зона | Чем заменяется | Основание |
|---|---|---|
| front matter | ASCII-пробел на каждую единицу UTF-16, CR/LF на месте | как сейчас (пробелы → пустые строки, ничего не создаётся) |
| разделители критика (`{++`, `++}`, `{--`, `--}`, `{~~`, `~~}`, `~>`, `{==`, `==}`, `{>>`, `<<}`), все знаки внутри `{>>…<<}` кроме CR/LF | заменитель-символ `P` | как `Markers` в `CriticMarkupRender` (PUA) |
| `%%…%%`, строка целиком из комментария и пробелов, **не** внутри абзаца | ASCII-пробел (строка пустая) | как `hidden`: пустая строка рвёт абзац и не создаёт новый |
| `%%…%%` в остальных случаях (внутри абзаца, посреди строки) | `P` | как U+200B в `hidden`; строка не пустая, отступ «4 пробела → блок кода» не возникает |

`P` — один и тот же символ на документ: первая свободная единица PUA (U+E000…U+F8FF), не встречающаяся в тексте (как `freeBase`); если заняты все — U+FFFF. Результат хранит `placeholder`, чтобы U2.3 мог вычистить `P` из литералов, если понадобится. Для cmark `P` — не пробел и не пунктуация (`cmark_utf8proc_is_space` — `Preview/…`/vendored `utf8.c` 249–254 и `is_punctuation` 256–…, `cmark_ctype.c` 8–24: управляющие и PUA в обоих списках отсутствуют), то есть тот же класс, что у нынешних PUA-маркеров и U+200B.
Тройка `{++` из одного маркера теперь становится тремя `P`: для правил `*`/`_` важен один символ рядом с разделителем — класс тот же, результат тот же.

### 3.3. Где результат совпадает с нынешним HTML, а где нет (п. 4 задания)

| Случай | Сейчас | После маски | Совпадает |
|---|---|---|---|
| разделитель выделения рядом с `{++`/`++}` | маркер PUA | `P` | да |
| текст комментария критика | маркер + цифры + маркер, строки-наполнители | `P`… и CR/LF на месте | да (строка не пустая) |
| `**` у границы `%%…%%` на одной строке (`*a%%c%%*`, `**%%c%% x**`) | комментарий удалён, соседние символы соприкасаются | между ними `P` | **нет** (граничный случай; в «Намеренные изменения») |
| комментарий в начале строки перед `#`/`-` (`%%c%%# H`) | после удаления строка начинается с `# H` → заголовок | строка начинается с `P` → абзац | **нет**, редкий |
| комментарий строкой между блоками | пустая строка | пустая строка (пробелы) | да |
| комментарий строкой внутри абзаца | U+200B на строку | `P` на строку | да |
| режимы критика `.result`/`.original` | текст переписан **до** разбора, разбор идёт по результату | разбор один и тот же для всех режимов, правка применяется адаптером | **нет**, когда удаление меняет выделения вокруг (`*a {--b--}*`) — «Намеренные изменения» |
| wiki: разделитель `**` вплотную к `[[…]]` | найденная цель → `[`, не найденная → буква | `[` (скобки не маскируются) | только как у найденной цели |

## 4. Устройство `MarkdownSourceMask.swift`

### 4.1. Типы и API (черновик; `Sendable`, `Equatable`, без AppKit)

```swift
enum MarkdownSourceMask {
    struct Options: Equatable, Sendable {
        var syntax: MarkdownSyntaxOptions
        var isVaultNote: Bool          // `%%…%%`
        var detectsFrontMatter: Bool
        var includesCritic: Bool       // как Includes.criticMarkup
    }
    enum Kind: Equatable, Sendable {
        case frontMatter
        case comment                   // `%%…%%`
        case critic(CriticMarkupKind)
        case wikiLink                  // только после разбора
        case noteEmbed                 // только после разбора
    }
    struct Segment: Equatable, Sendable {
        var kind: Kind
        var range: NSRange             // весь участок, UTF-16 исходника
        var markerRanges: [NSRange]    // служебные знаки: `{++`/`++}`, `%%`/`%%`, `---`/`---`, `[[`/`]]`, `![[`/`]]`
        var contentRange: NSRange      // между разделителями; у подмены — вся пара; у wiki — `displayRange`
        var separatorRange: NSRange?   // `~>` у подмены
        // wiki/embed
        var target: String?; var heading: String?; var alias: String?
        var embedKind: MarkdownNoteEmbedItem.Kind?
        var isBlockEmbed: Bool
        // `%%`
        var occupiesWholeLines: Bool
        var keepsParagraph: Bool
    }
    struct Result: Equatable, Sendable {
        var text: String               // маскированный текст, та же длина в UTF-16 и те же CR/LF
        var segments: [Segment]        // отсортированы по `range.location`
        var placeholder: UInt16
        var isIdentity: Bool           // ничего не замаскировано: text == исходник
    }
    static func mask(_ text: String, options: Options, excluded: [NSRange]? = nil, isCancelled: () -> Bool = { false }) -> Result
    // после разбора:
    static func linkSegments(in text: NSString, textRuns: [NSRange], wikiExcluded: [NSRange], embedExcluded: [NSRange], …) -> [Segment]
}
```

Имена уточняются при разработке. Обязательное: чистые функции, отмена через `isCancelled`, быстрый выход без токенов (`mayContainMarkup`, `mayContainComment`, `contains("---")` у начала) — для обычных документов стоимость нулевая, как сейчас.

### 4.2. Алгоритм `mask`

1. Front matter (если `detectsFrontMatter`): вызов `MarkdownPresentationParser.frontMatter(text)` (код остаётся на месте; перенос — спорное №6). Диапазон → пробелы кроме CR/LF; сегмент `.frontMatter` с `markerRanges`. Продление `range` на конец закрывающей строки (как в `parse`, 1776–1781) оставить решением U2.3.
2. Запреты `zones`: если передан `excluded` — берём его; иначе оценка предварительным проходом (4.3). Front matter всегда входит в запреты.
3. Критик (если `includesCritic`): `CriticMarkupService.items(in: text, excluded: zones)`. Для каждой правки сегмент: `range`, `markerRanges` = первые три и последние три единицы (у подмены плюс `separator`), `contentRange` = `item.content`.
4. Комментарии (если `isVaultNote` и есть `%%`): `MarkdownObsidianComment.ranges(in: text, excluded: zones ∪ диапазоны критика-комментариев)` — точное повторение порядка «критик → `%%`»: тела `{>>…<<}` в нынешнем потоке уже заменены маркерами, и `%%` в них не виден. Для каждого диапазона считаются `occupiesWholeLines` и `keepsParagraph` — **правила `hidden` (`isInsideParagraph`, `afterPrefix`, `isBlankLine`) переносятся/вызываются, не переписываются**: сейчас они `private` внутри `hidden(_:ranges:)` (108–167) — в U2.2 выносятся в `internal static` функции той же перечисленной enum (правка `MarkdownObsidianComment.swift` на 2–3 строки для видимости), логика без изменений. Если вызывать нечем без правки — допустим минимальный перенос с удалением из `hidden` (решение за основным агентом).
5. Пересечения: критик целиком внутри комментария — сегмент критика отбрасывается; частичное пересечение — отбрасывается сегмент критика (его разделители остаются обычным текстом, видны); комментарий внутри содержимого критика — оба сохраняются (вложение).
6. Сборка маски: копия единиц UTF-16; шаг 1 → пробелы; шаги 3, 4 → `P` или пробел по таблице 3.2; CR/LF не трогаются. Пробел вместо `P` ставится только для единиц комментария на строках, где кроме комментария и пробелов ничего нет и `keepsParagraph == false`.
7. Результат отсортирован; `isIdentity`, если сегментов нет.

### 4.3. Оценка запретов предварительным проходом (правила)

Один линейный проход по строкам (CR/LF/CRLF). Запрещённый диапазон — целые строки (кроме строчного кода). Для каждой строки считается «содержимое после контейнеров»: до 3 пробелов, затем повторно `>` с необязательным пробелом и маркеры списка (`-`, `+`, `*`, `\d{1,9}[.)]` + пробел/таб/конец строки) с сопутствующим отступом. Это приближение, поэтому результат проверяется (2.2, п. 2).
- **F1. Ограждённый код.** Открытие: ≥3 `` ` `` (в info-строке нет `` ` ``) или `~`; закрытие: тот же символ, не короче, дальше только пробелы/табы. Незакрытый блок идёт до конца документа (внутри цитаты — до строки без `>`).
- **F2. Блок формулы `$$`.** Правила — как в `MarkdownMathExtension` (уточнить при разработке; зависят от `syntax`).
- **F3. Отступный код.** Строка с отступом ≥4 столбцов (таб = 4) после пустой строки или в начале текста и вне пункта списка; продолжается строками с отступом ≥4 и пустыми строками между ними.
- **F4. HTML-блоки.** Начало (до 3 пробелов): `<!--` … `-->`; `<?` … `?>`; `<![CDATA[` … `]]>`; `<!X`; `<script|pre|style|textarea` … закрывающий тег; открывающий/закрывающий тег блочного имени (список CommonMark) или полный тег на строке одним (только не после строки абзаца) — до пустой строки.
- **F5. Таблицы.** Строка с `|`, за ней строка-разделитель `:?-+:?` через `|`; диапазон — до первой пустой строки.
- **F6. Строчный код.** Внутри абзацев (подряд идущих непустых строк вне F1–F5): серия `` ` `` длины n закрывается ближайшей серией той же длины в абзаце; диапазон — от начала открывающей до конца закрывающей серии (может пересекать строки).
- **F7. Строчные формулы `$…$`.** Не оцениваются предварительным проходом (правила зависят от `inlineMath`, `legacyInlineMath`, `strictMode`); ловит проверка по дереву.
Как и сегодня, не запрещены: строчный HTML, ссылки, заголовки, цитаты, списки (в `excludedRanges` их нет).

### 4.4. После разбора: wiki и embed

`linkSegments` вызывается U2.3 с данными дерева; в U2.2 пишется и проверяется на строках, где дерева нет, подаваемыми вручную диапазонами.
- Wiki: вызов `MarkdownWikiLinkExtractor.links(textRanges:excluded:text:)` с теми же `textRuns` и `excluded`, что в `parse` (3448–3466); результат `MarkdownWikiLink` → `Segment(.wikiLink, markerRanges, contentRange = displayRange, target, heading, alias)`.
- Embed: вызов `MarkdownNoteEmbed.items(in:excluded:)`; `markerRanges` = `![[` (3 единицы) и `]]` (2 единицы), `contentRange` = между ними, `target/heading/alias/kind/isBlock` — из `MarkdownNoteEmbedItem`. Ссылки внутри `![[…]]` на `[[` не ищутся (в `items` внутренний `[[` запрещён; в extractor `![[` пропускается).
- Embed внутри комментария `%%`/комментария критика не находится сам (там `P`, `![[` нет); отдельной проверки не нужно — в нынешнем потоке то же получалось из порядка шагов.
- Embed и wiki пересекающиеся с границами узлов (`*![[a*]]`) — решение U2.3 (не вкладывать, оставить текстом).

## 5. Как адаптеры получат всё, что давали `prepare`/`finalize` (п. 3 задания)

Адаптеры работают по диапазонам исходника; маска нужна только cmark. Служебные знаки текст-узлов исключаются из вывода по `markerRanges`, а не по символу `P`.

**HTML-адаптер (U3.3):**
- CriticMarkup: сегменты `.critic(kind)` вложены в поток строчных узлов как обёртка; `.show` — `<ins class="critic-ins">`/`<del class="critic-del">`/`<mark class="critic-hl">`/`<span class="critic-comment" role="note" tabindex="0" aria-label=… title=…>&#9998;</span>`, метка — `CriticMarkupRender.commentLabel(исходная подстрока contentRange)`; подмена выводит `del` для первой половины и `ins` для второй, `separator` не печатается. Правка, пересёкшая границу блока (абзац, пункт, ячейка), закрывается перед границей и открывается заново, правила `reopenTags` и `tagStack` из `finalize` (173–~300) переносятся в запись HTML — **это единственное место, где логика `finalize` нужна по существу**.
  - `.result`/`.original`: адаптер пропускает/печатает содержимое по `CriticMarkupService.resolution(of:accept:in:)` (107–121) на узлах, которые попали в диапазон правки; текст перед разбором не переписывается (отличие — таблица 3.3).
  - Строки-наполнители, `<br />` перед ними и цифры комментариев исчезают: их больше нет.
- `%%` (`isVaultNote`): сегменты с `occupiesWholeLines && !keepsParagraph` не дают узлов (в дереве пустые строки), модель может добавить блок `.comment` по сегменту (U2.3, как в `MarkdownBlockNode.Kind.comment`); сегменты внутри абзаца — строчные `.comment`: HTML их не печатает, остальные адаптеры печатают как нужно. `hidesObsidianComments`/`appliesTo(documentURL:)` вычисляются снаружи, в `Options.isVaultNote`; для встроенной заметки — как сейчас (`hidesComments` пробрасывается).
- Wiki: `MarkdownInlineNode.wikiLink` + `MarkdownWikiLinkContext.relativeHref(for:)`/`fileAddress(for:)` (`MarkdownWikiLinkResolver.swift` 143–180) как в `MarkdownWikiLinkRewriter.replacements` (204–224): найден → `<a href>` с экранированным отображаемым текстом, иначе только текст (кеш по `цель#заголовок`).
- Встраивания: строчные `image`/`attachment` строятся как узел картинки/ссылки с адресом из `fileReplacement` — функция **приватная**, перед U3.3 её нужно открыть (внутренняя) или перенести; блочные заметки — по `MarkdownNoteEmbed.finalize` (кеш, лимиты, раздел, вложенный разбор встроенной заметки **моделью** с глубиной 1, `flatten`).
- `data-sourcepos` указывает на исходный текст без сдвигов — преимущество маскировки.

**TextKit-адаптер (U5a):** позиции `Segment.range`/`markerRanges` совпадают с позициями текстового хранилища; цвета правок и приглушение `%%` — из сегментов (`criticElementIndex`, `obsidianCommentCache` удаляются), служебные знаки — общим механизмом маркеров (скрытие вне курсора), wiki и embed — как `MarkdownWikiLink.markerRanges`. Команды `applyCriticMarkup` и `CriticMarkupService.suggestion/resolutions` остаются и берут правки из тех же сегментов (`CriticMarkupItem` можно собрать обратно из `Segment`).

## 8. Риски

1. **Оценка запретов неточна** (вложенные контейнеры, отступный код в списках, HTML-блоки, строчные формулы). Последствие — комментарий в коде скрыт или комментарий не скрыт, и разметка внутри него живёт. Смягчение: сравнение с деревом (тест 6.4), проверка в U2.3, запасной разбор (2.2г).
2. **Маска внутри ложно найденного кода меняет структуру** (закрывающее ограждение попало в комментарий). Ловится проверкой по дереву; только при расхождении.
3. **Граничные случаи выделения у комментариев и режимы `.result`/`.original`** (3.3) — расхождение с нынешним HTML, нужно в раздел «Намеренные изменения HTML» главного плана и в эталоны U0 (до U3.4 эталон намеренно расходится).
4. **Локальный разбор T5** (`MarkdownLocalParser`): маска — функция всего текста. Правка, открывающая или закрывающая `{++`/`%%` далеко от места ввода, меняет маску в нескольких блоках. Сегодня T5 уже отказывается («есть front matter», «есть `]:`»); в U2.3/U2.5 добавить отказ «маска изменилась» (сравнение `segments` до и после).
5. **Старые вызовы `maskedFrontMatter`** (7 мест, байтовый контракт) остаются на старой функции до U7.x; в новом ядре не использовать. Две функции с разными контрактами существуют до удаления последнего вызывающего (допустимо: правило «двух копий» — про один и тот же контракт).
6. **Пользовательский PUA в тексте:** `P` выбирается свободным; если свободного нет — U+FFFF. Покрыть тестом (аналог `testUserPrivateUseCharactersSurvive`).
7. **Производительность:** документ без `{`-токенов, `%%`, `![[` и `---` в начале — выход без прохода; документ с токенами — один линейный проход + `NSString`-поиск, как у нынешних функций; на 300 тыс. символов с `%%` предел редактора (`obsidianCommentCache`) снимается только в U5a, замеры — на Mac.
8. **Правка текста до разбора (`Prepared`-подобные побочные таблицы) исчезает:** `comments`, `markerBase`, `token` больше не нужны; адаптеры не обязаны искать маркеры в HTML.

## 9. Спорные решения для основного агента

1. **Wiki и embed не маскируются до cmark** (отступление от п. 2 главного плана): структуру не ломают, а распознавание после разбора по текстовым узлам — точная копия нынешней семантики редактора и панели. Маскировка по построчной оценке потребовала бы запретов для заголовков, ссылок, картинок, ruby, сносок и т. д., которых предварительный проход не знает, и изменила бы смысл (псевдонимы с `*`, `` ` `` стали бы ссылками). Если принять — поправить п. 2 главного плана («маскируются front matter, `%%`, разделители CriticMarkup; wiki и встраивания распознаются после разбора»).
2. **Запасной второй разбор** при расхождении оценки и дерева: да/нет (2.2г). Рекомендую решить после измерения (тест 6.4); по умолчанию в U2.2 — только функция с параметром `excluded:`.
3. **Контракт «UTF-16 + строки, не байты»** и `MarkdownSourcePositions` от маскированного текста: подтвердить для U2.3 (влияет на U2.1 не меняется, тип принимает любой текст).
4. **Выбор `P` и пробелов** для `%%` (таблицы 3.2, 3.3): согласиться с расхождениями в граничных случаях выделения.
5. **Режимы критика не влияют на разбор** (одна модель на все режимы; правка применяется адаптером): намеренное изменение HTML для `.result`/`.original` в граничных случаях.
6. **Где живёт front matter.** План U7.4 называет `Preview/MarkdownFrontMatter.swift` «функциями из U2.2», главный план п. 5 требует переноса, а не копии. Варианты: (A) в U2.2 вынести `FrontMatter` и `frontMatter(_:)` в `Preview/MarkdownFrontMatter.swift`, в парсере оставить однострочные пересылки до U7.4 (~25 вызовов не трогаются); (B) переименовать все вызовы сейчас, как в U2.1 (расширяет задачу, пересекается с U2.1/U7.4); (C) ничего не переносить, маска вызывает функцию парсера (минимум). Рекомендую (C) для U2.2 и перенос в U7.4, поправив формулировку «функции из U2.2» в плане U7.4, либо (A), если нужен файл раньше.
7. **Распознаватели не переезжают в U2.2:** новая функция вызывает `CriticMarkupService.items`, `MarkdownObsidianComment.ranges`, `MarkdownNoteEmbed.items`, `MarkdownWikiLinkExtractor.links(textRanges:…)`. Двух копий нет; физический перенос — U5a.1/U7.5 вместе с удалением старых вызовов.
8. **Пересечения сегментов** (4.2, п. 5): критик внутри комментария — отбрасывается; частичное — отбрасывается критик. Подтвердить.
9. **`isBlock` у embed:** построчное правило (`isBlockEmbed`) или «единственное содержимое абзаца верхнего уровня» по дереву. В U2.2 переносится построчное (как сейчас); решение о замене — U2.3.
10. **`fileReplacement` и `existingFileHref` (`MarkdownNoteEmbed`, 281–308) приватные** — для U3.3 понадобятся внутренними; можно открыть в U3.3, не в U2.2.
