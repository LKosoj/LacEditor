# U2.5. Дополнительные данные модели

Статус: план (код не менялся). Дата замеров: 2026-11-05. Номера строк — по рабочей копии: `Preview/MarkdownPresentationParser.swift` (далее «парсер», 4770 строк; U2.1 уже перенёс `Source` в `MarkdownSourcePositions.swift`, обращения переименованы), `Models/MarkdownDocumentModel.swift` (321 строка), `Models/MarkdownPresentation.swift`.

## 0. Главные решения (что выбрано и почему)

Принцип: **каждый вид данных переносится одним из трёх способов; копий старой логики не остаётся.**

- **Группа A. Функции по дереву cmark** (берут `root`, `MarkdownSourcePositions`, текст, `mathExtension`). Переезжают в общий файл как есть; ядро вызывает их внутри `MarkdownMathExtension.withDocument` (пока дерево живо), старый парсер вызывает те же функции. Сюда: текст для чтения, кандидаты эмодзи и места текста (умные замены, автодополнение, wiki), индекс блоков, участки верхнего регистра, `headingData` (заголовок и эмодзи).
- **Группа Б. Чистые функции по диапазонам и тексту** (без узлов). Общие для обоих: `rawHTMLRanges` из `htmlRanges`, слияние `fenceBlockedRanges`, слияние `unreliable`, сборка `MarkdownElementIndex`, часть «умные кавычки/тире/многоточие/серии пробелов» из кусочков текста.
- **Группа В. Данные, которые старый парсер собирает по ходу обхода и они держатся на его внутренних доказательствах** (`confirmedInlineRange`, `plainMultiline*`, `itemStartColumn`, `htmlContextText`): элементы статус-строки, контекст ограждений, структурные замены (`softBreak`, отступы абзацев). Для модели их считает **новый проход по узлам модели** (`MarkdownBlockNode`/`MarkdownInlineNode`: диапазоны, `containerPrefixes`, `isUnreliable` уже есть). Старый парсер свою сборку сохраняет до U8: вызвать новую функцию он не может, потому что у него нет модели. Сходимость доказывает тест-сверка «модель против старого `MarkdownPresentation`» на корпусе и на тестах парсера. Это единственное место, где «без копий» выполняется как «старая логика удаляется в U8, новая написана заново по другим входным данным», а не как общий вызов (см. спорное №1).

Новые файлы:
- `Preview/MarkdownDocumentExtras.swift` — группы А и Б (перенос функций, общие точки входа).
- `Preview/MarkdownDocumentParser+Extras.swift` — группа В и сборка: `fillExtras(model, scan, …)`, вызываемая ядром (`MarkdownDocumentParser.swift`, U2.3) после обхода.
- Остаются на месте: `Preview/MarkdownReadableTextParser.swift`, `Services/MarkdownEmojiCandidateExtractor.swift`, `Models/MarkdownBlockIndex.swift`, `Models/MarkdownReadableText.swift` (правки только ссылок на переехавшие функции).

### Порядок внутри ядра (для U2.3, чтобы оно оставило точки)
1. `withDocument` → `root`, `MarkdownSourcePositions` (как парсер, стр. 1767–1769).
2. **До обхода**, только если включены `.emoji` или (`.wikiLinks` и в тексте есть `[[`): `MarkdownDocumentExtras.textScan(...)` → кандидаты, места, `emojiByNode`, `wikiTextRanges`. Так делает и парсер (стр. 1942): результат нужен обходу — `Heading.emoji`, `uppercaseRuns`, узлы `.emoji`, `.wikiLink`.
3. Обход (U2.3/U2.4): узлы модели, `isUnreliable` (по `source.range(node) == nil` для типов из стр. 1884–1888), `htmlRanges` и `htmlRangesAvailable`, множества `confirmedHTML` / `htmlImages`.
4. **После обхода**: `readableText` и `blockIndex` (за один вызов, как стр. 3367), `rawHTMLRanges`, затем проход по модели (`fillExtras`): `elements`, `fence`, `smartReplacements`, `unreliableRanges`.
5. HTML-путь (`includes` без `.emoji/.readableText/.elementIndex/.blockIndex/.editorContext`) пропускает пп. 2, 4 целиком; единственные постоянные расходы — `isUnreliable` и `headingIDs`, которые нужны и ему.

## 1. Разбор по видам данных

### 1.1. Текст для чтения (`readableText`, `includes.readableText`)
1. Сейчас: `MarkdownReadableTextParser.build(root:source:text:mathExtension:inlineMath:onTopLevelBlock:isCancelled:)` (`Preview/MarkdownReadableTextParser.swift`, 111 строк). Вызывается из парсера на стр. 3367 при `includeReadableText`; нужны `root`, `source` (`range`, `tableCellPositions`, `tableInlineRange`), исходный текст, `mathExtension`, множество узлов inline-формул (`mathInline`), коллбэк по верхнеуровневым блокам (даёт `readableEnds` для индекса блоков). Позиции без подтверждения → `unconfirmed` (блок локальный разбор не берёт). Типы `MarkdownReadableText` — `Models/MarkdownReadableText.swift` (164 строки).
2. Куда: функция остаётся в своём файле (она уже общая и принимает дерево). Ядро вызывает её после обхода тем же образом; старый парсер продолжает вызывать ту же функцию (изменений нет). `MarkdownInlineTextProjection` (`Services/MarkdownInlineTextProjection.swift`) не трогаем.
   Единственная правка: ядро разбирает **маскированный** текст (U2.2), а читаемый текст сверяет написание с исходным. Решение: в `build` передаётся исходный `raw`, а диапазоны масок (front matter уже вне блоков; `%%…%%`, CriticMarkup из U2.2) добавляются в `unsupportedRanges`. Тогда выделение, затрагивающее маску, получает `nil` и копируется обычным путём. Без масок (флаги `isVaultNote`/`criticMarkup` выключены) результат побайтно совпадает с прежним.
3. Поле: `MarkdownDocumentModel.readableText: MarkdownReadableText?` — подходит, правок модели нет. `blockIndex.blocks[i].readableEnd` заполняется тем же вызовом (поэтому `.readableText` вместе с `.blockIndex` строятся одним проходом).
4. Тесты: `MarkdownReadableTextTests` (12), `MarkdownEmojiStatisticsTests`, `MarkdownEmailSourceTests`, `MarkdownLocalParseTests` (склейка `readableEnd`); эталон — поле `readableText` в `BaselineSupport.swift` (стр. 459–462, U0). Нужны новые: `MarkdownDocumentExtrasTests.testReadableTextFromModelEqualsPresentation` на корпусе U0 с кириллицей, CJK, эмодзи, `\r\n`; тест маски (`%%…%%` в заметке хранилища → `text(in:)` на выделении над маской равен `nil`).

### 1.2. Кандидаты эмодзи, места автодополнения, умные замены, `smartRawHTMLRanges` (`includes.emoji`)
1. Сейчас:
   - `MarkdownEmojiCandidateExtractor.candidates(in:source:text:isCancelled:onSmartRange:onTextRange:onCandidate:)` (`Services/MarkdownEmojiCandidateExtractor.swift`, 151 строка; обходит текстовые узлы, пропускает код, картинки, пользовательские узлы, неподтверждённые ссылки, текст в сыром HTML-контексте и под HTML-тегами, которые не подтверждены парой; строка 132–134 вызывает `MarkdownPresentationParser.underlines` и `inlineHTMLPairs`). Парсер зовёт его на стр. 1942–1948, если `includeEmojiCandidates || wikiEnabled`. Коллбэки: `onSmartRange` → `smartTextRanges` (и `wikiTextRanges`), `onTextRange` → `emojiCompletionRanges`, `onCandidate` → `emojiByNode` (нужен заголовкам и верхнему регистру).
   - Затем: фильтрация по `blockedHTML` (стр. 3415–3418) и по `overlapsMedia` (стр. 2936) — это **показ**, не данные документа.
   - `smartRawHTMLRanges`: стр. 3342–3365 (из `htmlRanges`, `htmlContextText` и `MarkdownImageUploadService.HTMLContext.consume`); `nil`, если `htmlRangesAvailable == false`.
   - `textReplacements` вида `.smart`: стр. 2150–2166 (кусочки текста → «“ ” ‘ ’ – — …»), см. 1.3.
2. Куда:
   - `MarkdownDocumentExtras.textScan(root:source:text:includes:isCancelled:)` → `TextScan { candidates, completionRanges, smartRanges, wikiTextRanges, byNode }`. Внутри вызывает существующий `MarkdownEmojiCandidateExtractor.candidates` (функция остаётся, копии нет); коллбэки заполняют поля по флагам (`.emoji` — все, `.wikiLinks` — только `wikiTextRanges`). Старый парсер вызывает `textScan` вместо своего блока на стр. 1942–1948.
   - `MarkdownDocumentExtras.rawHTMLRanges(htmlRanges:available:contextText:text:isCancelled:) -> [NSRange]?` — вынос стр. 3342–3365 без изменений; парсер вызывает его же.
   - Ядро собирает `htmlRanges`/`contextText` в обходе (блок «подтверждение HTML» из рендера, U2.3); если U2.3 уже использует `HTMLContext`, `rawHTMLRanges` вызывается из той же точки. Промежуточный вход из ядра: `(htmlRanges: [NSRange], htmlRangesAvailable: Bool, blankedPrefixText: NSString?)`, не часть модели.
   - `EmojiData` собирается как `candidates` (отсортированы по `location`, как стр. 1948) + `completionRanges` (сортировка) + `smartTextRanges` (сортировка) + `smartRawHTMLRanges`.
   - Фильтр `blockedHTML`/`overlapsMedia` **в модель не входит**: сырые данные текстовых узлов остаются в `EmojiData`, фильтрует адаптер (U5.1) по блокам HTML и медиа из модели. См. спорное №3.
3. Поле: `emoji: EmojiData?` — подходит. Заполняется только при `.emoji`. Правок модели нет. `Heading.emoji` заполняется ядром из `byNode` через `headingData` (см. 1.4).
4. Тесты: `MarkdownEmojiCandidateExtractorTests` (8), `MarkdownPresentationTests` (3), `MarkdownLayoutTests` (smart/completion), `MarkdownNativeGeneratedBlockTests` (10 обращений к `emojiCandidates`), `MarkdownHTMLMediaServiceTests` (1: кандидат внутри HTML), `EmojiShortcodeResolverTests`; эталон — `emojiCandidates`, `emojiCompletionRanges`, `smartTextRanges`, `smartRawHTMLRanges` в `BaselineSupport.swift`. Новые: данные модели == поля старой презентации до фильтра блокировок (после фильтра сравнивает U5.2); `\r\n`, эмодзи, экранирование `\:name:`, текст внутри `<script>`/`<style>`, `smartRawHTMLRanges == nil` при неподтверждённом HTML.

### 1.3. Умные замены (`smartReplacements`, `includes.editorContext`)
1. Сейчас `textReplacements` добавляется в трёх местах парсера:
   - `.smart` и `.spaces` по кусочкам текста (стр. 2147–2185; условия: `!unsupported`, не в сыром HTML, `smartPunctuation ?? true` или `!preserveEditingWhitespace`);
   - `.softBreak` и ведущие пробелы после переноса (стр. 3126–3148: `confirmedSoftBreak`, `plainMultilinePrefixes`, `fencePrefixes`);
   - пробелы у абзацев и пунктов (стр. 3150–3298: `wholeLines`, `confirmedInlineRange`, `itemStartColumn`).
   Затем отсев по `blockedText` (картинки, медиа, таблицы…; стр. 3371–3390, переменная `safeText`) и `blockedHTML`.
2. Куда:
   - (а) Чистая часть (стр. 2150–2185) — функция Группы Б `MarkdownDocumentExtras.textReplacements(pieces:text:syntax:) -> [MarkdownTextReplacement]`. Парсер вызывает её; ядро вызывает на `.text` узлах модели через `MarkdownInlineTextProjection.pieces` с теми же условиями (флаг `.editorContext`, не в сыром HTML-контексте, не в таблицах, картинках, сносках).
   - (б) Структурная часть (стр. 3126–3298) — **Группа В**: новый проход по абзацам модели (`inlines`, `containerPrefixes`, `isUnreliable`). Правила «доказательства» упрощаются: узел без `isUnreliable` считается подтверждённым. Параметры `syntax.preserveEditingSoftBreaks`/`preserveEditingWhitespace` берутся из `options.syntax`.
   - Отсев `safeText` остаётся **в адаптере** (U5.1), как «blocked»: он зависит от того, что редактор заменил картинкой. В `smartReplacements` — полный список без отсева. См. спорное №3.
3. Поле: `smartReplacements: [MarkdownTextReplacement]` — подходит; сортировка по `location`.
4. Тесты: `MarkdownPresentationParserTests` (69 проверок `textReplacements`), `MarkdownLayoutTests` (11), `MarkdownPresentationTests` (3); эталон — поле `textReplacements` в `BaselineSupport`. Новые: модель против старой презентации (список сравнивается до отсева `safeText`: в тесте старый список строится вызовом парсера без блокировок на документах без картинок/таблиц и целиком — после отсева в U5.2).
5. Риск наивысший (≈250 строк логики, тесты с вкладками, `>`, вложенными списками). Если за итерацию не сходится — подзадача **U2.5e переносится в U5.1** (адаптер считает по модели), а поле `smartReplacements` остаётся пустым до неё; это вписывается в план: данные только для TextKit.

### 1.4. Участки верхнего регистра (`Heading.uppercaseRuns`, `includes.uppercaseRuns`)
1. Сейчас: `uppercaseHeadingRuns(node,…)` (парсер стр. 1289–1420; `private static`) вызывается на стр. 3300–3312 **только если** `includeUppercaseRuns && includeEmojiCandidates` и число найденных заголовков совпало с числом узлов. Входы: узел заголовка, `source`, текст, `mathInline`, `confirmedInlineHTML`, `confirmedHTMLImages`, `preserveEditingSoftBreaks`, `emojiByNode`; внутри `inlineHTMLPairs`. Пустой результат (`nil`) — заголовок не подтверждён. `headingData` (стр. 1253–1287) — заголовок и эмодзи заголовка.
2. Куда: обе функции в `MarkdownDocumentExtras` как `internal static` (Группа А, сигнатуры без изменений); парсер вызывает их оттуда. Ядро вызывает в момент построения узла заголовка: `emoji` из `headingData`, `uppercaseRuns` — если `includes ⊇ [.emoji, .uppercaseRuns]`. Промежуточный вход из ядра — `confirmedInlineHTML: Set<OpaquePointer>` и `confirmedHTMLImages: Set<NSRange>` (ядро строит их при подтверждении HTML, как парсер стр. 2287+). Модельный тип `MarkdownHeading.UppercaseRun` уже в `MarkdownPresentation.swift` и используется `Heading.uppercaseRuns` как есть (U1.1 вынес типы).
   Договорённость с U2.3: `headingData` как «заголовок» (`Heading.title`) — работа U2.3; U2.5 лишь следит, чтобы в ядре и парсере была одна функция. Кто переносит первым — тот и переносит, второй вызывает.
3. Поле: `MarkdownBlockNode.Heading.uppercaseRuns` — подходит. Условие `.uppercaseRuns` требует `.emoji`: записать в комментарии `Includes.uppercaseRuns` (сейчас этого нет) — минимальная правка модели.
4. Тесты: `MarkdownPresentationParserTests` (20 проверок `uppercaseRuns`, `testUppercaseHeadingRuns*`), `MarkdownLayoutTests` (7), `MarkdownOutlineTests` (2), `MarkdownInlineHTMLTests` (1). Новый: сверка `Heading.uppercaseRuns` модели с `MarkdownHeading.uppercaseRuns` старой презентации на заголовках с `<u>`, `<br>`, `<img>`, формулами, setext, составными символами.

   - В контроллере `FenceContext` строится из полей презентации плюс `codeOpenings` из `codeBlocks` (стр. 1864–1909 `MarkdownPresentationController.swift`) — остаётся в адаптере.
2. Куда: Группа В. `fence(of model)`: `blockedRanges` — целые строки блоков перечисленных видов (из `range`) плюс `frontMatter.range`; незакрытое верхнеуровневое ограждение без тела: `CodeBlock.isClosed == false` и пустой `bodySegments` → без первой строки; `blockedEOF` — конец блока равен `textLength` и блок не закрыт; `containerLines` — из `containerPrefixes` абзацев и пустых контейнеров: `line`, `sourcePrefix` (текст префикса из исходника), `continuationPrefix` (`ContainerPrefix.continuation`); условия «только ASCII-префикс, число `>` равно глубине, ранние пункты» вынести в чистую функцию Группы Б, переиспользуемую для проверки префикса (`simpleEmptyFencePrefix` уже статическая — сделать `internal`). Слияние диапазонов — общая функция Группы Б (`mergedBlockedRanges`), парсер вызывает её же.
   Блоки, в которых позицию подтвердить нельзя (`isUnreliable`), дают `isAvailable = false`.
3. Поле: `fence: FenceContext?` (`nil` без `.editorContext`) — подходит. `FenceContext.containerLines` использует существующий `MarkdownFenceContainerLine`. Правок нет. Замечание: `U2.4` изменила `CodeBlock`/`bodySegments` — набор тестов 1.8 проверяет итоговые данные, а не способ получения.
4. Тесты: `MarkdownPresentationParserTests`: `testEmptyContainersProvideConfirmedFencePrefix`, `testFenceContainerLinesConfirmParagraphPrefix`, `testFenceContextTracksOpaqueLinesIndependentlyOfPresentation`, `testIndentedFenceAndClosingWhitespaceUseConfirmedContent`, `testCodeBodyTabDoesNotInvalidateFenceCoordinates` (стр. 1318–1454); эталон — четыре поля в `BaselineSupport`. Новые: сверка модели со старой презентацией на тех же документах и на 6 примерах U2.4 (незакрытые блоки в цитате и пункте, `\r\n`).

### 1.9. Wiki-ссылки (`withWikiLinks`, `includes.wikiLinks`)
1. Сейчас: `wikiEnabled = includeWikiLinks && text содержит "[["` (стр. 1771). Подтверждённые текстовые диапазоны (`wikiTextRanges`) приходят из `extractor.onSmartRange` (стр. 1942); после сборки основных данных и фильтра `blockedHTML` (стр. 3417) формируется список `excluded` (ссылки, картинки, таблицы, заголовки, формулы, ruby, HTML-блоки, медиа, детали, блоки кода, диаграммы, разрывы страниц, оглавление, сноски, span-ссылки; стр. 3445–3466) и вызывается `MarkdownWikiLinkExtractor.links(textRanges:excluded:text:)` (`Services/MarkdownWikiLinkExtractor.swift` стр. 12). Результат — `wikiLinks` в `MarkdownPresentation` (`withWikiLinks`, стр. 948) и span `.link` (стр. 3468). Старый путь для HTML: `MarkdownRenderer.substitutingWikiLinks` → `MarkdownWikiLinkExtractor.links(in:)`, которая вызывает полный `MarkdownPresentationParser.parse` (стр. 8 файла).
2. Куда: распознавание — работа ядра U2.3/U2.2 (узлы `.wikiLink`); U2.5 фиксирует контракт: ядро получает `wikiTextRanges` из `textScan` и вызывает `MarkdownWikiLinkExtractor.links(textRanges:excluded:…)` (функция остаётся). Правила `excluded` — контексты, где `[[…]]` остаётся текстом; их перечень из стр. 3445–3466 записывается в комментарий ядра и покрывается тестами. `withWikiLinks` в адаптере (U5.1) собирает `[MarkdownWikiLink]` из узлов `.wikiLink`: `range` — `node.range`, `markerRanges` — `node.markerRanges`, `displayRange`, `target`, `heading`, `alias` — из `WikiLink`.

4. Тесты: `MarkdownWikiLinkTests` (6), `MarkdownWikiLinkResolverTests`, `MarkdownWikiLinkRewriterTests`, `MindMapLinksTests`, `MarkdownBaselineDocumentsTests`; эталон — поле `wikiLinks`. Новый: `model.wikiLinks == presentation.wikiLinks` на документах `MarkdownWikiLinkTests`, плюс «в коде, заголовках, таблицах и ссылках остаётся текстом».

## 4. Риски

- **Производительность HTML-пути.** `textScan` (обход текстовых узлов и эмодзи) и `readableText` (обход всего дерева) нельзя запускать «на всякий случай». Правило: без флага вызова нет; `wikiLinks` в предпросмотре — только при `[[` в тексте (проверка `range(of:)` до разбора, как стр. 1771). Единственное постоянное — `isUnreliable` и `unreliableRanges`, они дешёвые (в обходе).
- **Маскированный текст.** Эмодзи/читаемый текст/умные замены считаются по тексту, где `%%…%%` и CriticMarkup заменены служебными символами. Решение: маски исключаются из `completionRanges`, `smartRanges`, `unsupportedRanges` читаемого текста (точный список — после U2.2).
- **Различия настроек cmark:** парсер использует `HARDBREAKS`, ядро — нет (решение плана). Данные, которые зависят от `linebreak` (`uppercaseRuns` на `<br>` и жёсткий перенос, читаемый текст `linebreak`), надо проверять: ядро получает `softbreak` там, где парсер `linebreak`. Правило: в `uppercaseRuns` и читаемом тексте `softbreak` и `linebreak` обрабатываются одинаково (разделитель `\n`/пробел по настройке), тест на двух вариантах.
- **Неподтверждённые позиции.** `unconfirmed` в читаемом тексте (`hasUnconfirmedReadable`) — условие запрета локального разбора; ядро должно давать его тем же способом (позиции берутся из `MarkdownSourcePositions`, поэтому совпадает).
- **Двойное владение.** Пока живёт старый парсер, три места Группы В существуют дважды (старое — в обходе парсера, новое — в проходе по модели). Защита — сверка на корпусе (п. 3.1); устаревшее удаляется в U8.
- **Зависимость от U2.3/U2.4.** Группы А/Б можно делать сразу (они не зависят от ядра), Группу В — после U2.3 (нужны узлы с `isUnreliable`, `containerPrefixes`, `CodeBlock.isClosed`).

## 5. Спорные решения

1. **«Без копий» для Группы В.** Контекст ограждений, индекс элементов и структурные замены невозможно вызвать из старого парсера (у него нет модели), а они завязаны на его внутренние доказательства. Выбрано: писать заново по модели и доказывать равенство сверкой; старое удаляется в U8. Альтернатива — не переносить, а считать их в адаптере U5.1 из модели (тогда поля `elements`, `fence`, `smartReplacements` исчезают из модели). Выбрано оставить в модели: так их получает и U7 (строка состояния, команды «Вставить блок кода»), не только TextKit.
2. **Противоречие в главном плане.** Задача U5.1 перечисляет «`textReplacements`, верхний регистр, контекст ограждений, `blocked`, `withWikiLinks`/`withElements`» как данные, переносимые «из разбора редактора» в адаптер, а U2.5 и поля модели (`smartReplacements`, `fence`, `elements`, `uppercaseRuns`) относят их к модели. Принято: данные считает U2.5, U5.1 только копирует их в `MarkdownPresentation`, отсеивает по `blocked` и собирает `withWikiLinks` из узлов. Нужно поправить текст U5.1 в главном плане (в этой задаче не правится).
3. **Фильтр показа (blocked) не входит в модель.** Отсев кандидатов эмодзи, мест автодополнения, умных диапазонов и замен по `blockedHTML`, `overlapsMedia`, `blockedText` старого парсера — это что редактор показывает картинкой, а не факт документа. Выбрано: модель отдаёт полный список, фильтрует адаптер. Следствие: прямые потребители `emojiCandidates` без адаптера (экспорт, теги, резолвер эмодзи: `MarkdownExportImagesService`, `PandocExportService`, `MarkdownTagReader`, `EmojiShortcodeResolver`) получают чуть больше кандидатов, чем сегодня (внутри HTML-блоков, которые редактор показывает, но не содержащих «сырого» контекста). Проверить в U7/U4; если расходятся, там же добавить общий фильтр.
4. **Читаемый текст и маски.** Различие с прежним поведением возможно только в документах с `%%…%%` и CriticMarkup при включённых флагах; решение — conservative (`unsupportedRanges`); при желании сделать текст «читаемым» по правилам редактора — отдельная задача этапа 5а.
5. **U2.5e (структурные замены) могут уйти в U5.1.** Если не сходится.

## 6. Решения основного агента

- Спорные решения 1–5 приняты, как предложено выше.
- По п. 2: текст U5.1 в главном плане уже исправлен («данные считает ядро (U2.5), адаптер их только переносит»).
- В модели после U2.3c уже есть поле `blockedHTML` (неподтверждённые теги, ruby и `<br>` с атрибутом или внутри script/template). Новых полей с тем же именем не заводить; фильтр показа U5.1 берёт блоки HTML и медиа из узлов модели и это поле.
- U2.5a выполняется параллельно с U2.4: в `MarkdownPresentationParser.swift` правки только точечные (Edit), стенд запускать под `flock`.
- Эталон U2.1 (1878 тестов) устарел: число тестов выросло. Признак готовности U2.5a — итог стенда «Настоящих падений нет» и `lac-check` с 0 расхождений, ожидания существующих тестов не меняются.
- Принятые расхождения модели со старым `MarkdownPresentation` (решение 1, у каждого есть тест с явным ожиданием):
  - `blockIndex` строится и для документа с front matter (`hasFrontMatter == true`); старый разбор давал `nil`.
  - `unreliableRanges`: многострочная ссылка в пункте списка (`1. [ссылка\n   на две](http://a.b)`) в ядре надёжна, старый разбор помечал весь пункт.
  - Маски `%%…%%` и CriticMarkup не дают кандидатов эмодзи, мест автодополнения и умных замен; старый разбор масок не знает.
  - `elements`: у голой автоссылки диапазон без пробела перед адресом (старый был на знак левее).
  - `fence`: незакрытое ограждение в контейнере блокирует только строки контейнера; строки продолжения пункта есть в `containerLines`.
- Отличие от п. 4 «Риски»: `HARDBREAKS` влияет только на вывод cmark, дерево узлов одинаково, отдельная обработка `softbreak`/`linebreak` не нужна.
  - `smartReplacements`: ограничения старого сопоставления позиций не переносятся — мягкий перенос перед жёстким (`"а\nб  \nв\n"`), после жёсткого переноса со строкой с отступом (`"а  \nб\n   в\nг\n"`; перенос «в→г» модель пока не подтверждает: позиция после отступа ненадёжна), `>` без пробела (`"> a\n>b\n"`) получают замену. У выноски заголовок (метка) и тело — разные блоки, переноса-пробела между ними нет.
