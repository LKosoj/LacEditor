## 0. Что делаем простыми словами

Сегодня `MarkdownRenderer.renderPage` правит ТЕКСТ до cmark (прячет `%%`, ставит служебные символы вместо `{++`, подменяет
`[[…]]` на `[…](…)`, `![[…]]` на заглушку, дописывает два пробела к строке `> [!тип]`), а после cmark правит ГОТОВЫЙ HTML
(`finalize`, `transform`). Новый адаптер ничего не переписывает: он идёт по узлам модели и сразу пишет нужный HTML.
Файл `+Obsidian.swift` (в U3.1 это заглушка «как простой текст») заменяется целиком; основной `switch` U3.1 не правится.

Порядок старого потока (критик → `%%` → встраивания → wiki → выноски) в адаптере не нужен: маска U2.2 уже учла его при разборе.

## 1. Что нужно от модели (контракт для U2.3; без него U3.3 не начинать)

Файл `Models/MarkdownDocumentModel.swift` типов не меняет, но U2.3 обязано заполнять их так:

| № | Узел | Что обязано быть в модели |
| --- | --- | --- |
| R1 | `.critic(kind)` | Правка, пересекающая границу контейнера (пункт, строка цитаты, ячейка, `**`, ссылка; через пустую строку правки нет — как в `CriticMarkupService.items`), **режется на куски по контейнерам**: каждый кусок — свой узел того же вида. Так старое «закрыть перед границей, открыть заново» (`tagStack`/`reopenTags` в `CriticMarkupRender.finalize`) делает модель, адаптеру стек тегов не нужен. `children` — узлы между разделителями; текстовые узлы режутся по границам разделителей и `~>` |
| R2 | `.critic(.comment)` | `children` пуст (тело замаскировано), текст берётся срезом исходника между `markerRanges` |
| R3 | `.critic(.substitution)` | `markerRanges` = [`{~~`, `~>`, `~~}`]; `children` — узлы «было», затем узлы «стало»; адаптер делит их по `range.location >= markerRanges[1].upperBound` |
| R4 | `.callout` | `inlines` — заголовок (узлы до первого `softBreak`/`hardBreak` верхнего уровня, без ведущих пробелов); `children[0]` — абзац с остатком первого абзаца цитаты (если есть), его `range` начинается на первой строке тела; дальше остальные блоки цитаты. Правило «выноска или обычная цитата» — `MarkdownCalloutRender.marker(in:)` (функция остаётся) |
| R5 | `.alert` | `children` = блоки цитаты; первый узел первого абзаца — текст-маркер `[!NOTE]` (адаптер заменяет его на `<strong>NOTE</strong>`), за ним `softBreak` |
| R6 | `.noteEmbed` блок | только для встраивания «в отдельном абзаце» (`isBlock`, любой вид: заметка, картинка, вложение); нет `children`/`inlines`. Остальные `![[…]]` — строчные `.noteEmbed` |
| R7 | `.wikiLink` | есть только при `Includes.wikiLinks`; поля `target/heading/alias/displayRange` как сейчас |
| R8 | `.comment` | блочный (строки целиком) и строчный — без `children`; в тексте-источнике срез остаётся |
| R9 | пустой `id` заголовка | как в U3.1 (адаптер читает `Heading.id`) |

Если R1–R5 не выполнены, U3.3 превращается в перенос `finalize` по HTML-строке — этого главный план запрещает (решение 4).

## 2. Параметры `renderPage` (добавляет U3.3)

В `MarkdownHTMLRenderer.renderPage(_ model, text:, …)` добавляются: `wiki: MarkdownWikiLinkContext? = nil`,
`critic: CriticMarkupRenderMode? = nil`, `embeds: (any MarkdownNoteEmbedProvider)? = nil` (+ `documentURL`, его добавляет U3.2; он нужен
для вложений `![[картинка]]`). `hidesObsidianComments` в модельный вход НЕ добавляется: решение «это заметка хранилища» уже в
`model.options.isVaultNote`. В удобный вход (строка → модель, U3.1) добавляются все четыре; он же строит `Includes`:
`.wikiLinks` = `wiki != nil` и в тексте `[[`; `.noteEmbeds` = (`embeds != nil` или `wiki != nil`) и `mayContainEmbed`; `.criticMarkup` = `critic != nil`;
`isVaultNote = hidesObsidianComments || MarkdownObsidianComment.appliesTo(documentURL:)`. Провайдер по умолчанию —
`embeds ?? wiki.map { MarkdownFolderNoteEmbedProvider(context: $0) }`, как сейчас (`MarkdownRenderer.swift:437`).
Правило несоответствия «модель из редактора содержит узлы, а параметр выключен» (критик `nil`, wiki `nil`): узел выводится экранированным срезом
исходника (`{++…++}`, `[[…]]` — как текст). Потребитель (U4.2) сам решает, годится ли общая модель; при несоответствии строит свою.

Конфликт правок: U3.2 тоже меняет сигнатуру `renderPage` — основной агент сливает строку сигнатуры; тела не пересекаются.

## 3. Что переносится, откуда, куда

### 3.1. CriticMarkup (`Services/CriticMarkupRender.swift`: `prepare` 125–170, `finalize` 173–300)

- **Данные:** строчные `.critic(kind)` (R1–R3). Включается только при `critic != nil`.
- **`.show`:** обёртка вокруг `children`: вставка `<ins class="critic-ins">…</ins>`, удаление `<del class="critic-del">…</del>`,
  выделение `<mark class="critic-hl">…</mark>`, подмена `<del>…</del><ins>…</ins>` (первая и вторая половина по R3, `~>` не печатается).
  Комментарий: `<span class="critic-comment" role="note" tabindex="0" aria-label="L" title="L">&#9998;</span>`, `L = attributeEscaped(commentLabel(срез))`
  (тот же `[`→`&#91;`, перевод строки → пробел — для побайтового совпадения).
- **`.result` / `.original`:** вместо `prepare`, переписывавшего текст до cmark, адаптер решает по виду правки
  (`CriticMarkupService.resolution(of:accept:in:)` 107–121 — семантика та же): печатает `children` без обёртки или ничего. Перед записью родительский
  список узлов сводится функцией `flattenCritic(children, mode)`: «молчащие» узлы убираются, а соседние `.text` склеиваются — так
  `data-lac-whitespace` даёт столько же `<span>`, сколько давал переписанный текст (эталон `export-nobreaks`, «Добавление  в строке.»).
  Абзац, у которого после этого не осталось ни узлов, ни разрывов, не выводится (старое поведение: строка становилась пустой).
- **Правила `.show` + `preserveWhitespace`:** обёртки лежат между `<span data-lac-whitespace>`, а не внутри (раньше маркер был внутри текстового
  узла) — в «Намеренные изменения» (п. 6, К).
- **Открыть (private → internal, без копий):** `CriticMarkupRender.Kind` (теги открытия/закрытия, 3 строки), `attributeEscaped`.
  `prepare/finalize/Markers/freeBase` остаются до U4.4 и там удаляются.
- Эталоны: `preview-vault/Corpus/critic`, `export-html/Corpus/critic` (`.result`), `export-nobreaks/Corpus/critic` (`.original`).

### 3.2. Комментарии `%%` (`Preview/MarkdownObsidianComment.swift`: `hidden` 96–167)

- **Данные:** блочный и строчный `.comment` (R8); существуют только если `model.options.isVaultNote`. Решение «заметка хранилища» принимает тот, кто строит
  модель (`hidesObsidianComments || appliesTo(documentURL:)`); адаптер его не пересчитывает.
- **HTML:** узел ничего не печатает. Весь код `hidden` (удаление текста, `isInsideParagraph`, U+200B) заменён маской U2.2 и пустыми узлами.
- **Пустой экран (дополнение к U3.1 п. 2.8):** подсказка `lac-empty` выводится и когда весь непробельный текст — внутри `.comment` (старое: проверка
  шла по тексту после скрытия). Реализация: функция `isVisiblyEmpty(model, text)` — проход по `text` без диапазонов `.comment`. Front matter по-прежнему «не пусто».
- Эталон: `preview-vault/Corpus/obsidian-comments` (абзац «Видимый текст  и дальше.» — два пробела остаются, как сейчас).

### 3.3. Wiki-ссылки (`Services/MarkdownWikiLinkResolver.swift`: `MarkdownWikiLinkRewriter.replacements` 203–224, `relativeHref` 143–165)

- **Данные:** строчный `.wikiLink` (R7). `wiki == nil` → текст-срез `[[…]]` (как сейчас).
- **HTML:** `href = wiki.relativeHref(for: MarkdownWikiLink(range:, displayRange:, target:, heading:, alias:, markerRanges:))` (так же строит `MarkdownNoteEmbed.finalize`);
  кэш по ключу `цель#заголовок` на страницу (как в `replacements`). Есть адрес → `<a href="ESC">` + текст + `</a>`, иначе только текст.
  `ESC` — функция адресов U3.1 (`%` не трогается). Текст — `text[displayRange]` через общий писатель текста U3.1 (экранирование, `data-lac-whitespace`).
- **Отличие от старого:** отображаемый текст выводится буквально (раньше проходил через cmark: SMART-типографика, сущности, а у ненайденной
  цели — даже разметка `[[a|*b*]]`). В «Намеренные изменения» (Ф).
- Эталон: `preview-vault/Corpus/wiki` (`<a href="a.md">`, `a#Раздел`, `#Начало`, ненайденная и неоднозначная — просто текст).

### 3.4. Встраивания `![[…]]` (`Preview/MarkdownNoteEmbed.swift`: `prepare` 231–262, `finalize` 325–379)

Три случая по узлу:

1. **Блок, вид «заметка», провайдер есть** (R6) — врезка `<section class="lac-embed">…`. Порядок вывода: `cr`, HTML врезки, `\n`. Атрибута `data-sourcepos` у врезки нет
   (как сейчас — подстановка заменяла `<p …>` целиком).
2. **Блок или строка, вид «картинка/вложение»** — абзац `<p sp>` с синтезированным узлом: картинка → `MarkdownInlineNode(.image(url: href, alt: имя, syntax: .markdown, isBlock: …))`,
   вложение → `.link`; узел пишется через ту же функцию картинок/ссылок U3.1/U3.2 (так работают `resolveLocalImages`, маркеры и `data-sourcepos`).
   Адрес даёт `existingFileHref` (private → internal; логика `fileReplacement` режется: вычисление адреса остаётся там, склейка Markdown-строки — только в старом пути
   до U4.4). Нет файла → `<em>` + экранированный `L10n.tr("附件不可用：%@")` + `</em>` (через писатель текста).
3. **Блок без провайдера, строчная заметка, превышен лимит вида** — буквальный срез `![[…]]` (в абзаце `<p sp>` для блока).

**Содержимое врезки** (замена `finalize`, лимиты и кэш — те же):
- Счётчик `number` — порядковый номер блока-заметки с провайдером в порядке документа; `number >= maxEmbedsPerPage` → `.missingNote`. Суммарные 1 МиБ и 64 КиБ на заметку, чтение цели один раз
  (`cache[target]`), `body(of:)`, `section(of:heading:)`, `limitedNote`, `blockHTML`, `flatten` — **те же функции** (private → internal где нужно; в U4.4 они остаются, `prepare/finalize/markerRange/Prepared` удаляются).
- Встроенная заметка — **другой текст**, поэтому на неё строится **своя модель**: `MarkdownDocumentParser.parse(limited, options: Options(syntax: model.options.syntax,
  includes: [], isVaultNote: model.options.isVaultNote, detectsFrontMatter: true), isCancelled: { Task.isCancelled })`. `includes: []` — вот и есть «глубина 1»:
  `![[…]]` и `[[…]]` внутри встроенной заметки остаются текстом (эталон: заметка `deep` → `<p>![[note-a]]</p>`).
- Тело — внутренняя функция адаптера «блоки модели → строка» (её выделяет U3.1a, тот же код, что у страницы) с **контекстом по умолчанию**: `forExport`, `darkMode`, `syntax` внешние;
  `includeHeadingNumbers/includeListStyles/includeSourcePositions/isPreview` — `false`; флаги U3.2 (медиа, эмодзи, подсветка, локальные картинки) — по умолчанию, как у вложенного `renderPage` сегодня; `wiki/critic/embeds` — `nil`.
  Контекст сноски/ID — новый (как сейчас: якоря встроенной заметки могут совпасть с якорями страницы — известное ограничение `export-and-preview.md`). Результат → `flatten`.
- `parse` вернул `nil` (отмена) → `.missingNote` (результат всё равно отбрасывается). Формулы и диаграммы встроенной страницы наружу не попадают (сегодня берётся только `page.body`).
- **Кэш:** готовый HTML по ключу `цель + \0 + раздел` на страницу — одна и та же врезка не разбирается дважды (учёт 1 МиБ — по первому чтению цели, как сейчас). Время: до 20 разборов ≤64 КиБ — в фоне, как весь `renderPage`; на главном потоке не вызывается.
- Эталон: `preview-vault/Corpus/embeds` (+ `[dark]`), `export-nobreaks/Corpus/embeds`.

### 3.5. Выноски Obsidian (`Preview/MarkdownCalloutRender.swift`: `separatingTitles` 94–135, `transform` 150–180, `callout(in:)` 183–270)

- **Данные:** блочный `.callout` (R4). Заголовок — `inlines`, тело — `children`. `separatingTitles` не нужен: заголовок известен из модели независимо от `NOBREAKS`.
- **HTML (по `callout(in:)`, побайтно):**
  - без сворачивания: `<div class="lac-callout lac-callout-K[ lac-callout-custom]" role="note" aria-label="A" data-sourcepos="…"><div class="lac-callout-title">TITLE</div>` … `</div>`;
  - `+`/`-`: `<details class="…" [open] aria-label="A" sp><summary class="lac-callout-title">TITLE</summary>` … `</details>`; `open` у `+` и всегда при `forExport` (`expandCollapsed`);
  - `TITLE` = `<span class="lac-callout-icon" aria-hidden="true">СИМВОЛ</span><span class="lac-callout-label">ПОДПИСЬ</span>` + (есть заголовок ? `<span class="lac-callout-text">…</span>`);
    текст заголовка — `inlines`, записанные писателем в строку; ярлык `A` = `label` или `L10n.tr("标注标签 %@：%@", label, plainText(ofHTML: заголовок))` (функция остаётся);
  - тело есть, если `children` не пуст: `<div class="lac-callout-body">` + дети + `</div>` внутри оболочки; первый абзац тела пишется обычным путём (`<p sp>…</p>`).
  - `K` = `callout.kind ?? .note`, подпись неизвестного типа — `capitalized(type)` (private → internal).
  - `data-sourcepos` оболочки — `sp` узла (он и сейчас переносится с внешней цитаты). Вложенные выноски — обычная рекурсия по `children`.
- **В адаптер перекладывается** только запись; типы `MarkdownCalloutKind` (`symbol`, `label`, `colorGroup`) и `MarkdownObsidianPreviewStyle.css` остаются на месте.
- Эталон: `preview-vault/Corpus/callouts` (4 вида + обычная цитата). Заодно исправляется `export-nobreaks`: при `preserveWhitespace` старый `transform` выноски не узнаёт
  (маркер лежит внутри `<span data-lac-whitespace>`), эталон сейчас — простая цитата (п. 6, И).

### 3.6. Алерты GitHub (решение 4 к U3.1)

- **Данные:** `.alert` (R5). **Текущий код:** `MarkdownRenderer.swift:2456–2477` (оболочка `CUSTOM_BLOCK` + `<strong>LABEL</strong>` вместо маркера), правило распознавания — `MarkdownPresentationParser.alert` 1148 (переезжает в U2.3).
- **HTML:** `cr`, `<aside class="lac-alert lac-alert-note">`, затем обычная цитата `<blockquote sp>` с детьми (первый узел абзаца заменён на `<strong>NOTE</strong>`), `cr`, `</aside>`, `\n`.
  Класс — из белого списка (`Alert.rawValue.lowercased()`). Эталон `preview-vault/Corpus` (`typora-parity`, строки 453–464): `<strong>NOTE</strong><br />\nтекст`, при `NOBREAKS` вместо `<br />` — пробел.

## 6. Кандидаты в «Намеренные изменения HTML» (для U3.4)

А. `data-sourcepos`: колонки и конец (не начало!) у абзацев с wiki-ссылками (`wiki.md`, абзацы 3 и 5: эталон `3:1-3:120` — длина уже переписанного текста), с `%%` (`obsidian-comments` 3:1-3:43), с подменой/комментарием CriticMarkup, у строки-маркера выноски (старое: +2 пробела) — теперь по исходнику.
Б. `.result`/`.original`: старый рендер переписывал текст до cmark, и многострочная правка `{--a\nb--}` сдвигала номера строк **всех** следующих блоков; теперь строки верные.
В. Тело выноски: `<p data-sourcepos>` первого абзаца начинался со строки маркера (3:3), теперь — с первой строки тела (4:3).
Г. `%%` внутри абзаца: нет невидимого U+200B (две соседние строки дают два `<br />` подряд или два пробела при `NOBREAKS`); правило в `docs/agents/markdown-editor.md` (стр. 49) и `export-and-preview.md` (стр. 41) обновить в U4.4.
Д. Граница выделения у `%%` и режимы критика по таблице 3.3 U2.2 (`*a%%c%%*`, `%%c%%# H`, `*a {--b--}*`): тот же вид, другая разметка.
Е. Номера `headingIDs` не зависят от режима критика (раньше `.result` считал ID по переписанному тексту).
Ж. Wiki-текст — буквально (без SMART, сущностей и разметки); строчное `![[заметка]]` — срезом исходника (без SMART).
З. Встраивание при `preserveWhitespace`: раньше `<section>` попадал внутрь `<p><span data-lac-whitespace>…</span></p>` (невалидный HTML); теперь `<section>` на уровне блока.
И. Выноски при `preserveWhitespace` теперь распознаются (раньше показывались простой цитатой).
К. `.show`/`.result` с `preserveWhitespace`: `<span data-lac-whitespace>` вокруг каждого куска текста между обёртками (в `.result`/`.original` куски склеены — как раньше).
Л. Неправильная вложенность (`{++a **b++} c**`, правка, закрытая внутри ссылки): раньше мог выйти невалидный HTML, теперь вложенность верная.

Эталон переписывается только для пунктов А–Л; остальные отличия — ошибки адаптера.

## 7. Риски

1. **R1–R5 — главная зависимость.** Если U2.3 не режет правки по контейнерам или не делит заголовок/тело выноски, U3.3 не собирается без возврата к разбору готового HTML.
2. **Склейка текстов.** `flattenCritic` обязан склеивать соседние `.text` только после удаления молчащих узлов; иначе в `export-nobreaks` меняется число `<span data-lac-whitespace>`.
3. **Разбор встроенных заметок** (≤20 по ≤64 КиБ) — единственный новый разбор в HTML-пути; нужна отмена и кэш (п. 3.4). Замеры — на Mac.
4. **Согласованность `Includes` и параметров** (п. 2): общая модель редактора содержит критик/wiki всегда; предпросмотр обязан передавать то же `critic/wiki`, что строил бы сам.
5. **Слияние сигнатуры** с U3.2 (п. 2) и общий `switch` U3.1: правятся только заглушки в `+Obsidian.swift`; имена хуков — как в U3.1a.
6. **Локализация:** новых строк нет (все ключи `标注·…`, `批注：%@`, встраивания — существуют); `L10n.tr` на стенде — заглушка, язык `en` в тесте.
7. **Пустой экран** при критике `.result` на тексте только из `{--…--}` (старое: подсказка) в адаптере не воспроизводится; если нужно — отдельное правило.

## Спорное (для утверждения основным агентом)

1. Кусочное разбиение правок в модели (R1) вместо стека тегов в адаптере — требует правки плана U2.3b.
2. Первый абзац тела выноски — отдельный `children[0]` с настоящими строками (В), а не копия `data-sourcepos` маркерной строки.
3. Старое поведение «ненайденная wiki-ссылка — разметка внутри псевдонима работает» не сохраняется (Ж).
4. `hidesObsidianComments` не входит в модельный вход (берётся из модели).
5. Файл `+Obsidian.swift` вырастет до ~570 строк; предлагаю выделить `+Embeds.swift` сразу (блочные встраивания и вложенная модель), чтобы остаться ниже 800 и не мешать правкам.
6. Правки документации `docs/agents/` (порядок обработки в `export-and-preview.md` стр. 40, U+200B, `finalize`) — в U4.4, когда у адаптера появятся потребители.
