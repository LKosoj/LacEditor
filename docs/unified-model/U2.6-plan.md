## 1. Тест `LacEditorTests/MarkdownDocumentModelCorpusTests.swift`

Идея: тест сам, независимо от ядра, разбирает тот же текст через cmark, обходит дерево и сравнивает найденное со значениями модели. Так ловится расхождение между «что сказал cmark» и «что записало ядро». Ядро для сравнения не используется.

### 1.1. Корпус (готовые помощники из `BaselineSupport.swift`, ничего нового не изобретаем)

- `BaselineCorpus.spec()` — 672 примера, `BaselineCorpus.extensions()` — 30; `BaselineCorpus.documents()` — 38 документов (`Fixtures/MarkdownBaseline`, `Verification/Fixtures`, `Fixtures/RenderBaseline/Corpus`). Всё это `[BaselineItem]` (`id`, `text`).
- `BaselineCorpus.crlfDocuments()` — те же документы с `\r\n`. Для spec/ext копию с `\r\n` делаем в тесте: `BaselineCorpus.crlf(item.text)` (сам `crlf` уже есть; он сначала нормализует через `lf`).
- Не использовать `documents(for:)`: фильтр `nondeterministicMedia` нужен только эталонам HTML (порядок обхода словарей рендера). У ядра такой недетерминированности быть не должно; если `note-media` и `media-av` дадут разные результаты между прогонами, это ошибка ядра.
- Базовый LF-текст: `BaselineCorpus.lf(item.text)` (документы корпуса уже с `\n`, но так надёжнее).
- Документов с NUL в корпусе нет; тест проверяет `!text.utf8.contains(0)` и иначе падает (ядро для NUL может вернуть `nil`).

### 1.2. Наборы настроек (по образцу `PresentationBaselineSet`)

Локальный `enum CorpusModelSet: CaseIterable` с функцией `options -> MarkdownDocumentModel.Options` и `maskOptions`:

| Набор | `syntax` | `includes` | `isVaultNote` | Корпус |
| --- | --- | --- | --- | --- |
| `editor` | `.init()` | все девять `Includes` | `true` | spec, ext, документы, документы CRLF |
| `editorLoose` | `.init(strictMode: false, legacyInlineMath: true, smartPunctuation: false)` | все девять | `true` | spec, ext, документы, документы CRLF |
| `minimal` | `.init()` | `[]` | `false` | документы, документы CRLF |

`detectsFrontMatter: true` везде. Набор `editorLoose` нужен потому, что он меняет разбор заголовков и формул (`looseHeadings`) и `SMART`. Включения нужны все, чтобы маска содержала CriticMarkup и `%%`: именно там маскированный текст отличается от исходного.

Вызов ядра: `MarkdownDocumentParser.parse(text, options: …, isCancelled: { false })` → `XCTUnwrap`. Если в U2.3 сигнатура будет иной, правится одна строка в helper `model(_ text:, _ set:)`.

### 1.3. Как получить значения cmark (helper `CmarkReference`)

1. Маска: `let mask = MarkdownSourceMask.mask(text, options: …)` с теми же параметрами, что у ядра (`syntax`, `isVaultNote`, `detectsFrontMatter`, `includesCritic`). Разбирать нужно `mask.text`: ядро разбирает его же.
2. Дерево: `MarkdownMathExtension.withDocument(mask.text, options: SMART? | CMARK_OPT_TABLE_SPANS | CMARK_OPT_FOOTNOTES, includeInline: syntax.inlineMath, legacyInlineMath:, strictMode:, sourceForPositions: text) { root, mathExtension, mathInline in … }`. `SMART` — если `syntax.smartPunctuation ?? true`. Без `HARDBREAKS`/`NOBREAKS` (как ядро по U2.3). Тот же путь, что `MarkdownFormattingServiceTests` (строка 27).
3. Обход: рекурсия `cmark_node_first_child`/`cmark_node_next` (как в `MarkdownSpecConformanceTests.rawFragments`, там `cmark_iter`). Имя узла — `cmark_node_get_type_string`. Список узлов собирается в порядке документа.
4. Функции cmark по сравнениям:

| Что | Функции cmark |
| --- | --- |
| код: тело | `cmark_node_get_literal` у `code_block`, у которого `cmark_node_get_syntax_extension(node) != mathExtension` (блок формулы — не код) |
| код: info | `cmark_node_get_fence_info` (nil → `""`) |
| код: ограждён ли | `cmark_node_get_fenced(node, &length, &offset, &char)` — есть в `cmark-gfm.h:470`; `!= 0` ↔ `isFenced` |
| заголовок: уровень | `cmark_node_get_heading_level` |
| заголовок: текст | собственный обход в тесте (не вызывать `MarkdownPresentationParser.headingText`: он переедет в U2.3, и сравнение перестанет быть независимым): склейка literal узлов `text` и `code` (табы → пробел), `softbreak`/`linebreak` → пробел, затем обрезка пробелов и переводов строк — те же правила, что у `headingData` (строки 1203–1231 парсера) |
| ссылка, картинка: адрес | `cmark_node_get_url`; у картинки ещё `cmark_node_get_title` и текст `alt` (склейка literal потомков по тому же правилу) |

| ячейка: текст | склейка literal потомков `text`/`code`, `softbreak`/`linebreak` → `\n`; потомки других видов — см. 1.4 |

### 1.4. Какие поля сравниваются (точный список из главного плана → проверки)

Каждая проверка собирает два плоских списка в порядке документа: из cmark и из модели (рекурсивный обход `blocks`/`children`/`inlines` по `kind`), и сравнивает попарно. Один `XCTAssertEqual` на список, `message` — `id документа`, набор настроек, номер элемента.

1. **Блоки кода.** Список модели: `.codeBlock` (не `.mathBlock`). Для каждого: `info == cmark info`; `isFenced == (cmark_node_get_fenced != 0)`; склейка отрезков из `bodySegments` (+ `bodyPadding[i]` пробелов перед отрезком, `\n` между ними, `\n` в конце; пустые `bodySegments` → `""`) по **исходному** тексту (`NSString.substring(with:)`, UTF-16) побайтно равна `cmark literal` и равна `CodeBlock.literal` модели. Ни у одного блока на корпусе нет `isUnreliable` (U2.4: для 702 примеров прототип дал 0 расхождений и 0 ненадёжных). Блоки внутри таблиц и картинок cmark не создаёт, фильтры не нужны. Дополнительно: пересечение любого отрезка тела с участком маски (`mask.segments` видов `frontMatter`/`comment`/`critic`) должно быть пустым — иначе маска «съела» код.
2. **Текст заголовков.** `Heading.title == cmark-текст` (правило 1.3); `level` равен; `headingIDs` модели равен списку `id` заголовков без `inUnsupportedContainer` (сверка id между собой, в порядке документа, по `MarkdownHeadingAnchors.Allocator` в тесте — проверка согласованности, не вместо U3). Заголовки в таблицах/картинках/сносках cmark тоже перечисляет: их `id == ""` и они не в `headingIDs`.
3. **Адреса ссылок и картинок.** `.link` модели: `url == cmark url`, title равен. `.image`: `url`, `alt`, `title`. Ссылки внутри картинки в модели отсутствуют (U1.1 п. 4.3), поэтому в списке cmark такие ссылки отбрасываются (предок `image`). Автоссылки и ссылочная форма (`reference`) сравниваются так же (cmark уже раскрывает определение). HTML-формы (`<a href>`, `<img>`) в cmark — узлы `html_inline`/`html_block`: сравнивать их нечем, пропускаются (модель-`Link.form == .html`, `Image.syntax == .html`).
4. **Текст ячеек.** Для каждой строки/ячейки: `Table.alignments` равны; число строк и ячеек равны; `isHeader` равен; «текст» ячейки модели (склейка `.text`/`.code` по `inlines`, `softBreak`/`hardBreak` → `\n`) равен тексту ячейки cmark. Сравнение только для ячеек, где все потомки обеих сторон из простого набора (`text`, `code`, `strong`, `emphasis`, `strikethrough`, `softBreak`, `hardBreak`); ячейки с формулами, эмодзи, HTML, ruby, wiki, критиком, ссылками-картинками пропускаются со счётчиком (см. п. 1.6). `Cell.virtualSeparators` и `column` — только «column растёт на 1 + virtualSeparators».
5. **Маркеры.** Для каждого узла (и блок, и строчный, на любой глубине): каждый `markerRange` лежит в `[0, textLength]` и внутри `range` узла; маркеры одного узла попарно не пересекаются (`a.lower < b.upper && b.lower < a.upper` — признак пересечения; пустые диапазоны на границе допустимы); маркеры узла не пересекаются с маркерами его детей. Проверяется и у `isUnreliable`-узлов (у них маркеры пусты, `range` может быть целыми строками). Проверка «ребёнок внутри родителя» уже в U2.3 (`MarkdownDocumentParserTests`), здесь не дублируется.
6. **LF и CRLF с точностью до сдвига.** См. п. 1.5.
7. **Маскированный текст той же длины.** `mask.text.utf16.count == text.utf16.count`; `model.textLength == text.utf16.count`; позиции `\n`/`\r` в `mask.text` и в `text` те же (сравнить массивы смещений); вне `mask.segments` текст совпадает посимвольно (UTF-16); `mask.isIdentity` ↔ `segments.isEmpty` (кроме сегментов `wikiLink`/`noteEmbed`, их в маске нет). Проверяется для маски и каждого набора и для LF, и для CRLF.

### 1.5. Алгоритм сравнения LF и CRLF

Даны LF-текст `T` и `T' = BaselineCorpus.crlf(T)`; модели `M = parse(T)`, `M' = parse(T')`.

1. Таблица сдвигов: `breaks` — отсортированные UTF-16-смещения всех `\n` в `T` (`T` без одиночных `\r`; обеспечивает `BaselineCorpus.lf`). `shift(p) = p + (число смещений из breaks, строго меньших p)`. Диапазон `(loc, len)` → `(shift(loc), shift(loc+len) − shift(loc))`. Это верно и для диапазона, начинающегося на `\n` (он превращается в диапазон с `\r\n` в начале), и для заканчивающегося сразу перед `\n` (конец не захватывает `\r`). Проверка в начале теста: для `T`, у которого `breaks` пуст, `shift` тождественна.
2. Запись обеих моделей в текст тем же `BaselineDump` (из `BaselineSupport.swift`): он выводит `NSRange` как `loc+len`, строки — через `BaselineText.quoted` (`\r` → `\\r`, `\n` → `\\n`). Единственная правка помощника — необязательное свойство `var mapRange: ((NSRange) -> NSRange)?`, применяемое в `inline` к значению `NSRange` перед печатью (3 строки). Для `M` ставим `mapRange = shift`, для `M'` — нет.
3. Из дампа `M'` удаляется разница строк: в тексте дампа `\\r\\n` заменяется на `\\n` (то же для дампа `M`, для симметрии). Причина: cmark нормализует перевод строки в `literal` блоков кода, но не гарантированно в `literal` html-блока и в `displayHTML`; сдвиг есть у позиций, а не у строк. Если на корпусе окажется, что даже после этого строки различаются из-за **расхождения ядра**, это ошибка ядра и она чинится, а не скрывается нормализацией.
4. `XCTAssertEqual(dump(M, mapRange: shift), dump(M', nil))`, при несовпадении — первая отличающаяся строка (`BaselineStore.difference` уже умеет). Сравниваются все поля модели, включая `options`, `revision` (`nil`) и `textLength`: у `M'` длина равна `shift(T.length)`, поэтому `textLength` `M` сдвигается так же (в дампе это `Int`, не `NSRange`; сравнить отдельным assert `M'.textLength == shift(M.textLength)` и исключить поле из дампа через `excluded`-список — по образцу `PresentationBaselineSet.excludedFields`).
5. Помощник `BaselineDump` пока запрещает URL/Date/UUID (`problems`). Если модель содержит `URL` (медиа), дампер дополняется веткой `URL → absoluteString`; проверка `dump.problems == []` остаётся в тесте.
6. Ожидаемые исключения из сдвига нет: `isUnreliable` в CRLF-копии должен совпадать с LF. Если не совпадает — это ошибка U2.3/U2.4 (граница `\r` в `bodySegments`), не повод ослаблять тест.

### 1.6. Пропуски и нижние планки (чтобы пропуск не превращался в тихое «всё проходит»)

- Значения cmark (заголовки, адреса, ячейки) берутся из маскированного текста; ядро записывает значения по исходному (риск 1 в U2.3: в `title` не должно быть заменителя). Если диапазон узла пересекает участок маски вида `frontMatter`/`comment`/`critic`, узел пропускается со счётчиком. Код (п. 1.4.1) не пропускается никогда.
- Тест собирает счётчики «сравнено / пропущено» по видам и печатает их; нижняя планка отдельным assert: spec+ext — сравнено не меньше 91 блока кода (U2.4: 91 блок в 702 примерах), пропущено 0; заголовки, ссылки, картинки, ячейки — не меньше значений первого прогона на стенде (записываются в тест константами, как «нижняя планка» в U0.3).
- На spec/ext `isUnreliable == false` у всех блоков кода; у остальных видов — не проверяется (в spec/ext бывают честные «ненадёжные» узлы).

## 4. Риски

1. **Зависимость от U2.3–U2.5.** Тест нельзя написать «вслепую»: сигнатуры `parse`, `mask`, поля `CodeBlock` взяты из планов. Первый шаг порядка — сверка.
2. **Независимость.** Если взять `headingText` из старого парсера, тест перестанет быть независимым и сломается при переносе (U2.3). Поэтому правила заголовка переписаны в тесте.
3. **Пропуски из-за маски.** Слишком широкое «пересекает маску → пропустить» может скрыть ошибку; защита — счётчики и нижние планки (п. 1.6), код не пропускается никогда.
4. **CRLF и строки модели.** `displayHTML`, `html literal`, `svg(Data)` могут содержать `\r\n` в CRLF-копии: тест нормализует эти строки, ядро — нет. Если это окажется ошибкой ядра, нормализацию строки сужать до конкретных полей, а не оставлять глобальной.
5. **Недетерминированность медиа** (`note-media`, `media-av`, порядок словарей рендера): ядро и дамп детерминированы по построению, но если дамп нестабилен — найти причину; в список `nondeterministicMedia` их не добавлять без причины.
6. **Нижние планки** могут устареть при изменении корпуса: константы записываются в одном месте с комментарием и подтверждаются первым прогоном.
7. **Правка `BaselineSupport.swift`** (общий помощник U0) может задеть тесты эталонов: изменение только добавляющее (`mapRange == nil` → прежнее поведение).
8. **Удаление стенда необратимо** (118 МБ): перед удалением убедиться, что `lac-writer-check` собирает корпус (шаг 4); новый стенд для корпуса не нужен, это `lac-writer-check`.
