# Правила версий LacEditor

## Цель

Эти правила управляют тремя вещами сразу:

1. История Git остаётся понятной: видно, откуда пришло каждое изменение.
2. Версия приложения, номер сборки Xcode и тег Git согласованы между собой.
3. У каждой версии есть описание изменений на русском языке для пользователя, разбитое на разделы «Добавлено», «Улучшено» и «Исправлено».

## Номер версии

Официальная версия записывается как `мажорная.минорная.патч`, например `1.4.2`:

- Мажорная: есть несовместимые изменения или продукт перешёл на новый стабильный этап, например с `1.0.0` на `2.0.0`.
- Минорная: добавлены новые функции с сохранением совместимости, например с `0.1.0` на `0.2.0`.
- Патч: только совместимые исправления ошибок или небольшие улучшения, например с `0.1.0` на `0.1.1`.

Номер версии должен совпадать во всех этих местах:

- файл `VERSION` в корне проекта;
- `MARKETING_VERSION` в Xcode;
- заголовок версии в `CHANGELOG.md`;
- тег Git `v<версия>`, например `v0.2.0`.

`CURRENT_PROJECT_VERSION` — внутренний номер сборки, который только растёт. При каждом официальном выпуске он увеличивается минимум на 1 и не уменьшается и не сбрасывается вместе с версией.

## Ветки

- `main`: всегда собирается, содержит только проверенную работу.
- `feature/<имя>`: разработка новой функции.
- `fix/<имя>`: обычное исправление ошибки.
- `hotfix/<версия>`: срочное исправление выпущенной версии.
- `release/<версия>`: когда нужно несколько проверок или сборок-кандидатов.
- `codex/<имя>`: рабочая ветка, созданная Codex.

Ветки живут недолго: после проверки они вливаются в `main`, а несвязанные функции в одной долгой ветке не накапливаются.

## Сообщения коммитов

Коммиты используют префиксы Conventional Commits, текст можно писать естественным и точным русским языком:

```text
feat: поддержка файлов JavaScript и подсветки синтаксиса
fix: исправлен сброс нумерации вложенных списков Markdown
perf: ограничен диапазон подсветки в больших файлах
refactor: разделены чтение и запись файлов и состояние вкладок
docs: дополнены правила выпуска версий
test: добавлены основные проверки поиска и замены
build: подключён Apple Generic Versioning
chore(release): v0.2.0
```

Один коммит решает одну задачу. Не использовать описания вроде «обновил код» или «исправил проблему», из которых не видно, что изменилось.

## Журнал изменений

Каждая ветка, заметная для пользователя, обязана обновить раздел «Не выпущено» в `CHANGELOG.md`:

- Добавлено: новые форматы файлов, команды, возможности интерфейса и рабочие сценарии.
- Улучшено: производительность, взаимодействие, раскладка, читаемость или поведение существующих функций.
- Исправлено: неверное поведение, сбои, ошибки отображения или данных.
- Изменено: меняется привычный способ работы, но это не обязательно добавление или исправление.
- Безопасность: изменения разрешений, приватности, защиты данных или безопасности зависимостей.

Как писать:

- Описывать, что получает пользователь, а не внутренние классы и не список файлов.
- Одна запись — одно изменение, при необходимости с указанием ситуации.
- В исправлении указывать, при каких условиях и какая ошибка возникала.
- Не выдавать рефакторинг, форматирование и добавление тестов за функции для пользователя.
- Не указывать одно изменение сразу в нескольких разделах.
- В разделе выпускаемой версии не оставлять статусы работы: «в текущей ветке», планы и незавершённость.

## Порядок выпуска

1. Выбрать версию и перенести содержимое раздела «Не выпущено» под заголовок
   `## [версия] - ГГГГ-ММ-ДД`, указав дату запуска следующего шага.
2. В разделе «Не выпущено» вернуть пустые подразделы «Добавлено», «Улучшено» и «Исправлено» для следующей работы.
3. Создать заметки к выпуску `docs/releases/<версия>.md`. В них указать версию и номер сборки, который получится на следующем шаге.
4. Запустить скрипт подготовки выпуска:

   ```bash
   ./Scripts/prepare-release.sh 1.1.0
   ```

   Скрипт обновляет `VERSION` и маркетинговую версию Xcode, увеличивает номер сборки и запускает полную проверку выпуска. `Config/UIExperiment.xcconfig` он не меняет: `MARKETING_VERSION` и `CURRENT_PROJECT_VERSION` в этом файле нужно обновить вручную.
5. Прочитать описание версии, убедиться, что оно полное, без внутренних терминов и с верной датой.
6. Создать коммит и аннотированный тег:

   ```bash
   git status --short
   git add VERSION CHANGELOG.md LacEditor.xcodeproj/project.pbxproj Config/UIExperiment.xcconfig docs/releases/1.1.0.md <другие проверенные файлы этой версии>
   git commit -m "chore(release): v1.1.0"
   git tag -a v1.1.0 -m "LacEditor v1.1.0"
   ```

   Не использовать `git add .`: проверять каждый путь, чтобы в версию случайно не попали черновики, временные файлы и другая невыпущенная работа.

7. Если настроен удалённый репозиторий, отправить ветку и тег:

   ```bash
   git push origin main
   git push origin v1.1.0
   ```

8. Собрать файлы выпуска. Скрипт выполняет проверку выпуска и официальную упаковку, создаёт в `dist/`
   `LacEditor-<версия>-arm64.zip` и `.sha256`, а затем печатает команду для загрузки на GitHub Release:

   ```bash
   ./Scripts/build-production.sh
   ```

9. При создании выпуска на GitHub или GitLab загрузить эти два файла и использовать `docs/releases/<версия>.md`.

## Проверки выпуска

Скрипт выпуска проверяет следующее:

- `VERSION`, маркетинговая версия Xcode и `CHANGELOG.md` совпадают.
- Файл проекта Xcode корректен.
- SwiftPM успешно собирает Debug и Release.
- Основные проверки JSON, Markdown, поиска и замены и сворачивания пройдены.
- Xcode успешно собирает Release.

Для версий, затрагивающих интерфейс, нужна также ручная проверка:

- светлая и тёмная темы;
- изменение размера главного окна и перетаскивание разделителя Markdown;
- открытие, правка и сохранение поддерживаемых форматов файлов;
- подтверждение несохранённых изменений, меню и горячие клавиши;
- сценарии, упомянутые в журнале изменений.

Для официального кандидата также обязательно выполнить `./Scripts/run-acceptance.sh` и пройти ручные сценарии интерфейса по
`ACCEPTANCE_TESTS.md`. Результаты приёмки сохраняются в `AcceptanceReports/`; при провале сценариев P0 или P1
тег версии создавать нельзя.

## Срочные исправления

Срочное исправление начинается с ветки от тега выпущенной версии, например:

```bash
git switch -c hotfix/1.0.1 v1.0.0
```

В ветку попадают только исправление и необходимые проверки. Версия получает новый номер патча, запись идёт в раздел «Исправлено», а по завершении ветка вливается и в `main`.
